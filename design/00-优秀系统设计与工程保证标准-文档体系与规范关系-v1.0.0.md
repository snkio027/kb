## 摘要

“优秀系统设计与工程保证标准”不是若干相似文章的集合，而是一套分层、可裁剪、可审计的工程规范体系。它将系统设计拆分为五类相互配合但职责不同的制品：

```text
方法论基础
  -> 治理与符合性
  -> 论证、证据与裁决
  -> 生产就绪与运行韧性
  -> 操作手册、模板、案例与自动化
```

任何单篇文档都不能独立完成系统治理：方法论给出推导逻辑，治理规范定义谁必须做什么，证据规范定义“凭什么相信”，运行标准定义生产系统如何持续保持可接受行为，操作手册则把这些原则转化为阶段、门禁与项目制品。

本套系坚持三个控制原则：

1. **Markdown 是唯一权威源**：排版格式不得成为平行事实来源；
2. **规范权威按主题划分**：不以文件编号或篇幅替代语义边界；
3. **所有裁剪必须显式**：允许风险匹配的轻量化，不允许静默省略关键状态、责任、风险或证据。

# 1. 套系目标与非目标

## 1.1 目标

本套系用于建立以下组织能力：

- 从业务问题、约束、风险和工作负载推导架构，而不是从组件反推理由；
- 将关键正确性、安全性、活性、持久性、资源和运行目标表达为可证伪性质；
- 明确权威状态、稳定身份、变更权限、技术 Owner 和运营 Owner；
- 对重复、乱序、部分成功、过载、依赖退化、恢复和迁移建立可执行语义；
- 将设计主张映射为机制、验证、证据、门禁和运行反馈；
- 允许不同风险等级采用不同厚度的流程，同时保持认识论边界不被削弱；
- 让标准、项目文档、自动化规则和发布证据能够互相追溯。

## 1.2 非目标

本套系不用于：

- 规定所有项目必须采用相同架构、语言或基础设施；
- 以文档数量、模板完成率或 Gate 数量替代风险降低；
- 通过中央审批替代明确所有权和自助式工程能力；
- 对未编码、未验证或超出覆盖范围的性质作绝对正确性承诺；
- 将探索项目强行套入核心生产系统的全部流程；
- 把操作手册、案例或自动化实现提升为不可挑战的最高原则。

# 3. 规范权威与冲突裁决

## 3.1 按主题确定权威

规范权威不采用简单的“文件编号越小越高”模型，而按主题划分：

| 主题 | 最终权威文档 |
|---|---|
| 核心术语、系统定义、认识论边界、关键设计原则 | `ESD-METHOD-001` |
| 适用范围、风险分级、角色、职责分离、例外、符合性声明 | `ESD-GOV-001` |
| Claim、Argument、Evidence、Evidence Envelope、证据时效与裁决充分性 | `ESD-ASSURANCE-001` |
| SLO、运行模式、发布、回滚、恢复、容量、值班、事故与生产韧性 | `ESD-OPS-001` |
| Stage/Gate 默认流程、可复用模板、检查清单和参考案例 | `ESD-REFERENCE-001` |
| 文档组成、状态、文件命名、版本关系和套系冲突规则 | `ESD-SUITE-000` |

## 3.2 冲突处理顺序

发生冲突时必须按以下顺序处理：

1. 判断冲突是否来自术语误用、适用范围不同或版本不兼容；
2. 根据上表确定该主题的权威文档；
3. 若权威文档仍存在歧义，创建标准解释记录，而不是由项目自行发明永久语义；
4. 在解释完成前，高风险项目对相关结论保持 `UNKNOWN`；
5. 若项目确需偏离规范，通过 ADR 或 Exception 明确记录，不能修改事实描述来伪造符合。

## 3.3 方法论与操作手册的关系

`ESD-METHOD-001` 与 `ESD-REFERENCE-001` 的关系为：

```text
METHOD
  定义：为什么、是什么、能够证明到什么范围

REFERENCE
  实例化：按什么顺序工作、提交什么、如何评审与复用
```

操作手册可以提供默认流程，但不能：

- 把所有目标都泛化为 invariant；
- 把无证据状态解释为通过；
- 通过模板省略状态身份、Owner、失败语义或资源上界；
- 用项目便利改变方法论中的权威边界。

# 4. 规范性级别

## 4.1 文档级别

| 级别 | 含义 |
|---|---|
| `normative-foundation` | 定义术语、原则和不可被下位材料静默改变的语义 |
| `normative-control` | 定义体系组成、角色、生命周期、符合性与裁决控制 |
| `normative-domain` | 对特定主题提供强制工程要求，如证据或生产运行 |
| `operational-reference` | 提供默认流程、模板、示例和推荐实践 |
| `informative` | 解释、案例、教程和背景，不单独形成强制要求 |

## 4.2 需求用语

核心规范统一采用以下词义：

- **必须（MUST）**：不满足会破坏关键正确性、安全性、恢复能力、生产可控性或标准自身可信度；
- **不得（MUST NOT）**：会形成不可接受风险或破坏认识边界；
- **应（SHOULD）**：默认要求，偏离必须记录理由、风险、Owner 和复审触发；
- **可以（MAY）**：由风险、成本和局部约束决定；
- **未知（UNKNOWN）**：当前证据不足，不能合理判断为符合或不符合；
- **不适用（NOT_APPLICABLE）**：经论证后与当前对象无关，并有 Reviewer 接受该论证。

## 4.3 Requirement ID

从本套系新增的规范性要求应拥有稳定 ID：

```text
GOV-REQ-###
ASSUR-REQ-###
OPS-REQ-###
```

要求 ID 一经发布不得重用于不同语义。删除的要求保留为 `RETIRED`，避免历史裁决失去引用对象。

# 5. 套系版本与文档版本

## 5.1 双版本模型

每篇文档同时包含：

```yaml
suite_version: "1.1.0"
version: "1.0.0"
```

- `suite_version` 表示该文档被哪一版整体标准采用；
- `version` 表示该文档自身的语义版本；
- 单篇文档可以独立升级 Patch 或 Minor，不要求所有文档同步变更；
- 当规范关系、核心术语或套系组成出现不兼容变化时，提升 suite Major。

## 5.2 版本规则

| 变化 | 文档版本 | 套系版本 |
|---|---|---|
| 排版、链接、错字，不改变语义 | Patch | 通常不变 |
| 新增兼容要求、模板或解释 | Minor | 可能提升 Minor |
| 删除或改变既有强制语义 | Major | 必须评估 Major |
| 新增核心规范但不破坏既有语义 | 新文档 `1.0.0` | 提升或保持 Minor，由 Suite Owner 决定 |
| 改变权威边界或冲突规则 | Major 或 Minor | 至少提升 Minor |

## 5.3 兼容性声明

每次发布必须声明：

- 与哪些文档版本组合经过校准；
- 是否存在暂时未更新的 companion document；
- 哪些自动化规则仍停留在旧语义；
- 是否存在迁移期或双轨解释；
- 哪些历史裁决需要重新评审。

# 6. 文档生命周期

## 6.1 状态

| 状态 | 含义 |
|---|---|
| `DRAFT` | 内容仍可发生显著变化，不应用作强制生产裁决 |
| `CANDIDATE` | 语义基本稳定，正在试点和收集反例 |
| `BASELINE` | 已批准，可作为规范或正式参考 |
| `DEPRECATED` | 仍可读取，但不得用于新项目；有明确替代物 |
| `SUPERSEDED` | 已被新版本完全取代 |
| `WITHDRAWN` | 因错误或风险被撤回，不应继续引用 |

## 6.2 状态转换

```text
DRAFT -> CANDIDATE -> BASELINE -> DEPRECATED -> SUPERSEDED
                       \-> WITHDRAWN
```

状态转换必须记录：

- 决策日期；
- 决策主体；
- 变更摘要；
- 影响分析；
- 迁移要求；
- 替代版本；
- 对既有项目和证据的影响。

## 6.3 复审触发

以下任一事件触发相关文档复审：

- 重大事故或近失事件暴露规范缺口；
- 关键术语在多个项目中产生不一致解释；
- 大量 Exception 指向同一不可执行要求；
- 新法律、合规、安全或业务硬约束；
- 工作负载或基础设施范式显著改变；
- 自动化规则无法忠实表达当前规范；
- 至少每 12 个月一次基线复审。

# 7. 风险等级与使用剖面

套系统一采用 `R0–R3`：

| 等级 | 典型场景 | 默认使用方式 |
|---|---|---|
| `R0 — Exploration` | 可删除实验、无真实高敏数据、无生产依赖 | 阅读方法论摘要；使用最小 Brief 与退出条件 |
| `R1 — Bounded Production` | 内部或有限用户、影响可隔离 | 应用治理规范的最小制品与基础证据 |
| `R2 — Core Production` | 核心数据、收入、跨团队依赖、持续运行 | 完整 Stage/Gate、Assurance Case、Production Readiness |
| `R3 — High Assurance` | 资金、安全、合规、人身风险或大爆炸半径 | 独立评审、职责分离、持续证据、严格例外和漂移检测 |

风险等级决定流程厚度，不改变以下底线：

- 无权威状态不得进入生产；
- 不可逆副作用必须有身份、提交和恢复语义；
- 所有可增长资源必须有界；
- 高后果 `UNKNOWN` 不得静默放行；
- 例外必须有 Owner、期限、补偿控制和退出路径。

# 8. 角色与阅读路径

## 8.1 按角色阅读

| 角色 | 必读路径 |
|---|---|
| 架构师 / 技术负责人 | `METHOD -> GOV -> ASSURANCE -> REFERENCE -> OPS` |
| Design Author | `REFERENCE -> METHOD -> GOV -> ASSURANCE -> OPS` |
| SRE / Operational Owner | `OPS -> REFERENCE -> GOV -> ASSURANCE` |
| Assurance Reviewer | `ASSURANCE -> METHOD -> GOV -> REFERENCE` |
| Security / Compliance Reviewer | `GOV -> METHOD -> ASSURANCE -> OPS` |
| Release Authority | `GOV -> ASSURANCE -> OPS -> 项目 Production Readiness Decision` |
| 标准 Owner | 全部核心文档，并维护本索引 |

## 8.2 按任务阅读

| 任务 | 最短路径 |
|---|---|
| 新系统立项 | `REFERENCE Stage 0–3` + `METHOD 6–8` + `GOV 风险分级` |
| 重大架构变更 | `GOV 变更分类` + `REFERENCE Stage 4–9` + `ASSURANCE` |
| Production Readiness | `OPS` + `ASSURANCE` + `REFERENCE Gate 9` |
| 事故后改进 | `OPS 事故治理` + `ASSURANCE Assurance Delta` |
| 例外或 break-glass | `GOV 例外治理` + `ASSURANCE 决策记录` |
| 建立 CI 门禁 | `ASSURANCE Evidence Envelope` + 后续 `ESD-AUTO-001` |

# 9. 标准、模板、案例与自动化的边界

## 9.1 标准

标准定义：

- 必须满足的性质；
- 角色与责任；
- 裁决状态；
- 证据质量；
- 生命周期和例外规则。

## 9.2 模板

模板是标准的实例化容器，不是标准本身。模板字段可以增加，但不得：

- 删除规范要求的语义；
- 将 `UNKNOWN` 隐藏为未填写；
- 用单一勾选框替代必要论证；
- 把项目特例提升为全局规则。

## 9.3 案例

案例用于说明一种符合性实现，始终是非规范性的。案例中的技术选型、数值和架构不得被解释为默认要求。

## 9.4 自动化

自动化只能确定性裁决已编码属性。任何自动化输出必须说明：

- 检查了什么；
- 没有检查什么；
- 绑定了哪个制品与配置；
- 工具失败时的状态；
- 证据时效与失效条件。

未执行、工具异常或覆盖不足必须返回 `UNKNOWN`，不得默认成功。

# 10. 文件、链接与单一事实来源

## 10.1 文件命名

核心文件采用：

```text
NN-中文标题-vMAJOR.MINOR.PATCH.md
```

文档 ID 存放在 Front Matter，不使用文件名替代稳定身份。

## 10.2 权威源

- Markdown 文件是唯一权威源；
- PDF 是不可变发布视图；
- 网页是导航与阅读视图；
- 表单和门户是模板实例化入口；
- CI Schema 是已编码子集；
- 任何派生物都必须标明源文件版本和 digest。

## 10.3 交叉引用

项目和标准引用必须优先使用：

```text
Document ID + Document Version + Requirement ID
```

示例：

```text
ESD-ASSURANCE-001 v1.0.0 / ASSUR-REQ-012
```

不得只写“按设计规范执行”，因为这无法审计具体要求和版本。

# 11. 套系治理

## 11.1 Suite Owner

Suite Owner 负责：

- 维护文档地图和权威边界；
- 协调跨文档术语与版本；
- 接受或拒绝标准变更提案；
- 组织周期复审；
- 防止重复规范和互相矛盾的要求；
- 确保 `UNKNOWN`、证据绑定、状态权威等核心语义不被弱化。

Suite Owner 不应独自批准涉及自身高风险变更的全部证据和例外。

## 11.2 变更提案最低内容

```text
proposal ID
affected documents / requirements
problem and evidence
proposed semantic delta
compatibility impact
migration plan
automation impact
open unknowns
reviewers and decision authority
```

## 11.3 标准解释记录

当规范存在真实歧义但尚不需要修改正文时，可以发布 `Interpretation Record`。记录必须：

- 引用具体文档与要求；
- 描述歧义；
- 给出临时解释和适用范围；
- 有到期或并入正文的计划；
- 不得长期替代正式版本更新。

# 12. 符合性声明的最小形式

任何声称“符合本标准”的系统或变更，至少必须说明：

```yaml
system_or_change: "..."
risk_tier: "R0|R1|R2|R3"
suite_version: "1.1.0"
applicable_documents:
```

# 13. 当前发布基线

本套系 `1.1.0` 的核心关系为：

```text
ESD-SUITE-000
  controls the document system

ESD-METHOD-001
  defines semantics and epistemic boundaries

ESD-GOV-001
  defines applicability, roles, exceptions and conformance

ESD-ASSURANCE-001
  defines assurance argument, evidence and decision sufficiency

ESD-OPS-001
  defines production readiness and operational resilience

ESD-REFERENCE-001
  turns the above into stages, gates, templates and examples
```

后续模板库、CAN 完整参考设计、自动化规范和领域 Profile 应在该关系下扩展，不得重新复制一套核心方法论。

# 附录 B：结论

这套标准的质量不取决于文档数量，而取决于边界是否清楚、要求是否可执行、证据是否可信，以及项目能否从规范一路追溯到运行事实。文档体系本身也必须遵循系统工程原则：单一权威、显式状态、可逆变更、版本化契约、失效检测和可审计裁决。
