## 快速开始

对一个新系统或重大变更，最小工作流是：

```text
0. 定义问题、目标、非目标和风险等级
1. 建立工作负载、SLO、约束与假设
2. 登记关键性质及其优先级
3. 明确状态、身份、所有权和边界契约
4. 建模失败、一致性、提交与恢复
5. 推导架构、平面、流水线和运行模式
6. 计算资源上界、容量、成本与控制回路
7. 设计契约、安全、演进、迁移与操作
8. 建立验证、证据和变更暴露计划
9. 通过生产准入，并持续监测假设与证据漂移
```

任何阶段出现以下情况，都不得以“后续补充”为由自动通过：

- 关键状态没有权威 Owner；
- 高后果性质没有精确作用域；
- 重复、部分成功或 ACK 顺序不明确；
- 关键资源无上界；
- 生产完成语义和恢复权威不明确；
- 关键证据无法绑定当前制品、配置或环境；
- 关键假设无 Owner、无监测或已失效；
- 高风险例外没有范围和到期时间。

# 1. 操作模型

## 1.1 角色

| 角色 | 责任 |
|---|---|
| Design Author | 维护问题、假设、性质、方案、风险与证据链 |
| Semantic Owner | 定义业务语义、状态身份、契约与兼容规则 |
| Operational Owner | 负责 SLO、容量、发布、恢复、on-call 与事故响应 |
| Security / Compliance Reviewer | 审查信任边界、权限、审计和硬约束 |
| Platform / SRE Reviewer | 审查资源、故障、可观测性、发布和恢复 |
| Assurance Reviewer | 检查主张、验证、证据覆盖和认识边界 |
| Decision Authority | 根据风险、证据和例外做最终门禁裁决 |

高风险变更中，提出方案、评价证据和最终批准不得由同一非受控主体兼任。

## 1.2 门禁状态

下表为 [GOV §8.3](./03-系统设计与工程保证治理及符合性规范-v1.0.0.md) 的阅读摘要；受控状态及裁决权限以该处为准，不维护独立 Gate 状态机。

| 状态 | 含义 |
|---|---|
| `GO` | 强制条件满足，证据与当前对象绑定，剩余风险在阈值内 |
| `CONDITIONAL_GO` | 可在明确范围、期限、Owner、监测和撤销条件下放行 |
| `NO_GO` | 已知违反关键要求，或风险不可接受 |
| `UNKNOWN` | 证据不足、已过期、无法复现、作用域不清或关键假设未验证 |
| `NOT_APPLICABLE` | 经论证与记录后确实不适用 |

`UNKNOWN` 不是较弱的 `GO`。对高风险性质，`UNKNOWN` 默认阻断生产放行。

## 1.3 评审原则

评审顺序必须从语义到机制：

```text
Problem -> Property -> State -> Failure -> Resource -> Architecture -> Technology
```

不应从“为什么不用某组件”开始，也不应让架构图的视觉完整性掩盖状态和失败语义缺失。

# 2. 风险分级与裁剪

## 2.1 风险等级

下表为 [GOV §4](./03-系统设计与工程保证治理及符合性规范-v1.0.0.md) 的使用摘要。R0–R3、Gate 0–9 和 §19 成熟度模型是本套系的治理选择，不是外部标准的统一分级。

| 等级 | 典型场景 | 后果 | 默认保证深度 |
|---|---|---|---|
| R0 — Exploration | 一次性实验、无真实敏感数据、可随时删除 | 局部、可逆 | 最小 Problem Brief、数据边界、退出条件 |
| R1 — Bounded Production | 有限用户或内部系统，影响可隔离 | 中等、可恢复 | 关键性质、Owner、失败语义、资源上界、基础证据 |
| R2 — Core Production | 核心数据、收入、跨团队依赖、持续运行 | 高、恢复昂贵 | 完整阶段与门禁、容量/恢复模型、运行模式、证据绑定 |
| R3 — High Assurance | 资金、安全、合规、人身风险或大爆炸半径 | 极高或不可逆 | 独立审批、组合保证、元不变量、例外治理、持续漂移检测 |

风险等级必须根据**后果、暴露半径、不确定性和不可逆性**确定，不能只根据项目规模或 QPS。

## 2.2 裁剪规则

允许裁剪执行材料，但不得裁剪认识边界。任何裁剪必须记录：

```text
omitted requirement
reason
risk level
compensating control
owner
expiry / review trigger
```

以下内容即使在 MVP 中也通常不可省略：

- 核心数据身份与权威来源；
- 不可逆外部副作用；
- 认证、授权和租户隔离；
- 外部长期契约；
- 资源硬上限与删除/退出路径；
- 无法回滚的数据或 Schema 变化。

## 2.3 采用剖面

### Exploration Profile

```text
Problem / Non-goals
Data and trust boundary
Irreversible decisions
Hard resource cap
Exit / deletion criteria
```

### Production-Lite Profile

在 Exploration 基础上增加：

```text
Critical Property Register
State Ownership
Failure / Recovery Matrix
Basic capacity estimate
Operational Owner
Smoke / contract / fault evidence
```

### Core Production Profile

增加：

```text
Boundary Contracts
Operating Modes
Capacity and recovery model
Change Envelope
Evidence binding and freshness
Production Readiness Gate
```

### High-Assurance Profile

增加：

```text
Property precedence
Independent reviewer / approver
Assurance meta-invariants
Exception and break-glass governance
Evidence drift automation
Assurance delta after incidents
```

# 3. Stage 0：Problem Brief 与风险定级

## 3.1 输入

- 业务背景、当前问题或机会；
- 主要参与者和决策主体；
- 当前系统事实与已知事故；
- 交付窗口和初始预算。

## 3.2 必须产出

```text
Problem statement
Goals
Non-goals
Success metrics
Failure consequences
Risk tier
Decision deadline
Initial unknowns
```

## 3.3 关键问题

1. 解决的是业务问题、运营问题还是技术便利？
2. 不做什么，防止哪些范围膨胀？
3. 失败会造成延迟、数据错误、资金损失、安全问题还是不可恢复损坏？
4. 什么结果可以客观证明项目成功？
5. 这是系统新建、迁移、扩容、可靠性修复还是成本优化？

## 3.4 Gate 0：Problem Validity

`GO` 条件：

- 问题、价值和非目标清楚；
- 成功标准可检验；
- 风险等级有依据；
- 不以预选技术作为问题定义。

典型 `NO_GO`：

- “因为要上 Kubernetes/微服务/AI”；
- 问题无法与任何业务或运营后果关联；
- 不知道失败影响却直接承诺架构。

# 4. Stage 1：Workload、SLO、约束与假设

## 4.1 工作负载最小字段

| 维度 | 内容 |
|---|---|
| Arrival | 平均、峰值、突发时长、增长率 |
| Size | item/byte 分布、p99、硬上限 |
| Work | CPU、I/O、网络、压缩、fan-out、外部调用 |
| Shape | 热点、租户偏斜、读写比、顺序、重复、迟到 |
| Modes | 正常、峰值、恢复、重放、依赖降容 |
| Retention | 保留期、重建时间、存储增长 |

## 4.2 SLO 与恢复目标

必须分别记录：

```text
availability
latency / completion time
freshness / lag
correctness or error budget where meaningful
RPO
RTO
recovery catch-up objective
capacity headroom target
```

正确性硬约束不得藏在 error budget 中。

## 4.3 约束与假设登记

约束至少分为：业务、技术、组织、经济、安全/合规和时间。假设必须可证伪，并关联 Owner、证据、监测信号、失效阈值和响应。

## 4.4 Gate 1：Inputs Are Decision-Ready

`GO` 条件：

- 已覆盖真实峰值和恢复负载；
- 工作负载单位明确；
- SLO 与硬正确性分离；
- 团队技能、预算和运维约束已进入模型；
- 关键假设可监测且有复审条件。

`UNKNOWN` 条件：

- 只有平均值，没有尾部和硬上限；
- 无法估计恢复积压；
- 成本数据缺失且连粗估范围都没有；
- 关键外部依赖语义未确认。

# 5. Stage 2：Critical Properties 与优先级

## 5.1 产出物

- `Critical Property Register`；
- `Property Precedence Matrix`；
- Safety、Liveness、Durability、SLO、Assumption 和 Policy 分类；
- 每项性质的违反后果和验证义务。

## 5.2 编写规则

弱表述：

```text
系统应可靠、幂等、高可用。
```

强表述：

```text
对相同 source URI + immutable source version/checksum 与 pipeline_semantic_version，
Result Store 在任意可观察时刻最多存在一个 committed completion manifest；
冲突执行只能返回 ALREADY_COMMITTED 或进入 reconciliation，不能覆盖正式结果。
```

每项关键性质必须包含：身份、作用域、时间语义、假设、保证、允许降级、权威边界、Owner、验证覆盖和证据失效规则。Safety、有界/无界活性与 SLO 的验证义务以 ASSURANCE §5.2 为准，不要求无界活性由有限运行前缀直接证伪。

## 5.3 Gate 2：Semantic Integrity

`GO` 条件：

- 高后果风险均有对应关键性质；
- 性质可判定，不是愿望；
- 性质冲突已有优先级；
- `UNKNOWN` 和 allowed degradation 被明确；
- 每项性质拥有 Owner 和验证义务。

典型 `NO_GO`：

- “exactly once” 没有定义作用域；
- 可用性在事故现场可以任意覆盖数据完整性；
- 对未知输入默认继续执行。

# 6. Stage 3：State、Identity、Ownership 与 Boundary Contract

## 6.1 State Inventory

对每份状态记录：

```text
state name
business meaning
stable identity
authoritative / derived / ephemeral / evidence / configuration
authoritative store
mutation authority
technical owner
operational owner
security owner
retention
recovery source
conflict semantics
```

## 6.2 Boundary Contract

对关键边界记录：

```text
Assumptions
Guarantees
Violation behavior
Identity and version
Timeout / retry / ordering / duplicate semantics
Capacity assumptions
Verification
Owner
```

## 6.3 Gate 3：Authority and Composition

`GO` 条件：

- 每份权威状态唯一；
- 复制、缓存和派生状态不会伪装成多权威；
- 技术与运营 Owner 明确；
- 上游 Guarantee 能满足下游 Assumption；
- 违反边界契约时行为显式、有界、可观测；
- 跨团队边界与 Bounded Context 基本对齐。

典型 `NO_GO`：

- 多个服务直接修改同一业务表但无人裁决；
- 依赖本地内存恢复关键事实；
- 服务 API 只定义成功响应，不定义重复、冲突和超时。

# 7. Stage 4：Failure、Consistency、Commit 与 Recovery

## 7.1 Failure Matrix

至少覆盖：

- 请求或消息重复；
- 乱序、迟到和部分可见；
- 网络 timeout 与请求结果未知；
- worker crash、进程重启和 consumer rebalance；
- 写入成功但 ACK 失败；
- ACK 成功但业务提交失败；
- 依赖变慢、不可用或返回陈旧数据；
- 磁盘写满、内存耗尽、连接池耗尽；
- 配置错误、版本不兼容和权限变更；
- 区域或控制面故障；
- 恢复期间新流量与积压竞争。

每项失败记录：检测、可能已发生的副作用、权威裁决、自动动作、人工动作、重试安全性、最大影响、恢复目标和证据。

## 7.2 Consistency Decision

对每个关键状态明确：

```text
visibility requirement
ordering requirement
atomicity boundary
isolation requirement
conflict behavior
staleness tolerance
coordination mechanism
availability / latency trade-off
```

## 7.3 Commit Protocol

必须区分业务状态、执行尝试和交付位置：

```text
business:
  DISCOVERED -> ACCEPTED -> RUNNING -> OUTPUT_STAGED
    -> AUTHORITATIVELY_COMMITTED
  alternative dispositions:
    QUARANTINED / PERMANENTLY_REJECTED

uncertain operation:
  OUTPUT_STAGED -> RECONCILIATION_REQUIRED
    -> authority resolution -> committed / safe final disposition / still unresolved

delivery:
  durable disposition -> delivery-specific acknowledgement eligibility
    -> confirmed delivery position update
```

`RECONCILIATION_REQUIRED` 是未决责任，不是业务终态；一次 attempt 返回不等于任务完成。`QUARANTINED/PERMANENTLY_REJECTED` 只有在业务合同允许、处置已持久化且无悬而未决副作用时，才构成该处理操作的终止处置，不等于成功。隔离后的修复/重放仍须有具名责任。

条件创建或其他外部副作用至少区分四种调用结论：

| 结论 | 含义与后续责任 |
|---|---|
| `CONFIRMED_SUCCESS` | 权威系统确认请求已生效，继续按业务协议推进 |
| `CONFIRMED_NO_EFFECT` | 有合同级证据确认本次请求没有且不会迟到生效，可按同一意图安全重试或终止 |
| `CONFIRMED_CONFLICT` | 权威条件检查拒绝创建；读取并核对既有事实，不能仅凭冲突码判定等价 |
| `UNKNOWN` | 超时、连接中断或不可解释返回；由 reconciliation 持续承担责任 |

超时可能发生在远端成功之后；即使权威读取暂时 not-found，原请求仍可能在途并稍后成功。不得由一次空读推出“确定未发生”，也不得更换幂等键重新提交同一意图。必须写明后端条件写入、读取一致性、幂等键作用域/保留期与迟到请求语义；具体后端不满足前提时，本协议不能直接采用。

责任移交至少记录 OperationIdentity、原请求/候选摘要、未知窗口、暂存数据位置、具名接收 Owner、持久化接收确认、重试预算、截止时间、告警升级与重启恢复规则。在接收确认之前原 Owner 不得释放责任；截止时间到达只触发升级，不把未知变成失败。移交可结束当前 attempt，但是否允许推进消息位置须由交付合同另行定义。CAN 案例采用 §16.11 的保守策略：未决状态不推进对应 Kafka 位置。

## 7.4 Gate 4：Failure Semantics Are Closed

`GO` 条件：

- 部分成功和未知结果有明确处理；
- ACK 顺序与业务完成语义一致；
- 重试有稳定身份和预算；
- 幂等由原子机制构造，不依赖“通常不会重复”；
- 恢复从权威状态出发；
- 降级、隔离和恢复模式已定义。

典型 `NO_GO`：

- 依赖消息中间件标签宣称端到端 exactly-once；
- 超时后一律重试不可逆操作；
- 回滚只描述切换旧镜像，忽略数据已经变化。

# 8. Stage 5：Architecture、Planes、Pipeline 与 Modes

## 8.1 架构图最低要求

架构图必须能够表达：

- 权威状态与派生状态；
- 数据流、控制流、管理流和证据流；
- trust boundary 与 mutation authority；
- sync / async 边界；
- commit、ACK 和可见性边界；
- 背压方向；
- failure domain 与 isolation boundary；
- 正常、降级和恢复路径。

只画服务方框和箭头不构成完整架构。

## 8.2 平面划分

```text
Data Plane:
  高频传输、计算、解码、查询或业务执行

Control Plane:
  策略、调度、路由、配置和收敛

Management Plane:
  发布、升级、诊断、恢复、人工操作

Assurance Plane:
  验证、证据、门禁、例外、漂移判定
```

平面可以部署在同一进程中，但责任、权限和失败语义必须区分。

## 8.3 Fast Path / Slow Path

Fast Path 应只处理已验证、常见、可缓存的正常输入。损坏、未知版本、冲突、人工裁决和长期补偿应进入显式 Slow Path 或 Quarantine，而不是把热路径变成无限分支。

## 8.4 Operating Mode Matrix

至少定义：

| Mode | Entry | Hard Properties | Allowed Degradation | Forbidden | Exit |
|---|---|---|---|---|---|
| NORMAL | 关键依赖健康 | 全部硬性质 | 无 | 猜测、旁路提交 | — |
| DEGRADED | 依赖或容量下降 | 完整性、安全、资源上界 | 延迟、完成率 | 将未知结果标正式 | 依赖恢复并校验积压 |
| RECOVERY | 故障后重新收敛 | 权威状态、可追踪重放 | 暂停新接纳 | 用临时状态强行完成 | reconciliation 完成 |
| QUARANTINE | 输入或语义未知 | 隔离、审计、不可污染正式结果 | 活性 | 自动猜测修复 | 人工/规则裁决 |
| MAINTENANCE | 计划变更 | 数据和权限边界 | 可用性 | 未声明数据迁移 | 迁移验证完成 |
| EMERGENCY | 正常控制面阻断关键恢复 | 审计、时限、最小权限 | 正常审批路径 | 无期限 break-glass | 补偿审查完成 |

## 8.5 Gate 5：Architecture Preserves Semantics

`GO` 条件：

- 架构能够逐项解释关键性质如何被维护；
- 平面和权限边界合理；
- 快慢路径与故障隔离明确；
- 运行模式可判定、可观测、有退出条件；
- 技术组件是推导结果，而不是前置约束的伪装。

# 9. Stage 6：Resource Bounds、Capacity、Economics 与 Control Loops

## 9.1 Resource Budget

必须为以下资源定义上界：

```text
inflight work
inflight bytes
queue depth / queued bytes
threads / tasks / permits
connections / file descriptors
cache and temporary disk
retry attempts / retry time
reconciliation backlog
per-tenant share
```

## 9.2 Queue Contract

每个队列记录：目的、容量单位、容量值、生产/消费速率、满载行为、背压方向、公平性、数据持久性、drain/crash 语义、指标和 Owner。

## 9.3 Capacity Worksheet

最小计算：

```text
input rate
x work per input
= CPU / I/O / network demand

inflight bytes
= arrival byte rate x residence time

required service rate
>= peak arrival rate + recovery catch-up rate
```

同时评估：

- 单节点与集群上限；
- N-1 或目标故障域降容；
- 扩容和冷启动延迟；
- 恢复积压的清空窗口；
- 外部依赖限额；
- 热点与租户公平；
- 尾延迟和排队时间。

## 9.4 Economic Model

至少提供 C1 粗估：

```text
compute
storage read/write
network
message / request charges
retained evidence
replay / recovery
operational overhead
```

并给出单位成本和置信等级。无法计算时必须标为 `UNKNOWN`，不能写“成本可接受”。

## 9.5 Control Loop Register

| 字段 | 内容 |
|---|---|
| Controlled Variable | queue age、lag、utilization、error rate 等 |
| Sensor / Delay | 信号、窗口、采样和延迟 |
| Controller | admission、autoscaling、retry、routing 等 |
| Actuator | permits、replicas、traffic weight、feature flag |
| Bounds | 动作上下限和速率 |
| Interaction | 与其他控制回路的耦合 |
| Safe Default | 控制器失败时的默认行为 |
| Verification | 仿真、故障注入或历史回放 |

## 9.6 Gate 6：Stable Operating Region

`GO` 条件：

- 所有可增长资源有界；
- 背压能够传播到真正可控的上游；
- 峰值、故障降容和恢复容量满足目标；
- retry amplification 有上界；
- 控制回路不存在明显正反馈放大；
- 单位成本有模型和监测路径；
- 新增复杂度有 Owner 和回收条件。

典型 `NO_GO`：

- async everywhere + unbounded queue；
- 只算稳态，不算恢复；
- autoscaling 被当作无限容量；
- 每层各自重试且没有共享 deadline。

每项关键性质建立：

| Claim | Mechanism | Verification | Evidence | Coverage | Limitations | Freshness | Owner |
|---|---|---|---|---|---|---|---|

验证应组合：类型/静态检查、单元与属性测试、契约/集成测试、负载、故障注入、恢复演练、策略检查、运行监控和人工审查。

## 11.3 Assurance Meta-invariants

生产流水线必须检查：

- 缺失或过期证据不转为 `PASS`；
- required checks、验证器和豁免规则的修改本身受门禁；
- 高风险审批职责适当分离；
- 证据不可静默修改；
- 保证面不可用时不默认放行；
- 运行漂移会使相关结论失效；
- 例外和 break-glass 有范围、到期与补偿复审。

## 11.4 Change Envelope

重要变更必须定义：

```text
semantic delta
assumptions
maximum exposure
blast-radius boundary
representative traffic / corpus
observation window
success criteria
abort conditions
rollback / forward-recovery
owner and decision authority
evidence to retain
```

## 11.5 Gate 8：Evidence Is Decision-Grade

`GO` 条件：

- 每项高风险性质有适当验证；
- 证据与当前制品、配置、环境绑定；
- 覆盖和限制被明确记录；
- 性能证据使用代表性负载与统计方法；
- 故障与恢复证据覆盖关键边界；
- Change Envelope 有自动或明确的停止条件。

`UNKNOWN` 条件：

- 只展示测试数量或覆盖率，没有对应性质；
- 性能数据来自不同硬件或不同制品；
- 没有验证重复、崩溃或依赖退化；
- canary 没有预定义成功和退出条件。

# 12. Stage 9：Production Readiness 与持续保证

## 12.1 Gate 9：Production Admission

生产放行前必须确认：

```text
all mandatory gates resolved
all blocking UNKNOWN resolved or explicitly rejected

operational owner ready
runbooks and dashboards available
rollback / forward-recovery viable

evidence retained and traceable
```

## 12.2 放行后的持续保证

运行时必须持续观察：

- 工作负载是否越过假设范围；
- 关键依赖、Schema、策略和配置是否漂移；
- 证据是否到期或失效；
- 关键性质对应的语义指标是否异常；
- retry amplification、queue age 和 recovery debt；
- 单位成本和容量 headroom；
- 例外是否到期；
- Assurance Plane 是否可用且未被绕过。

## 12.3 Incident → Assurance Delta

重大事故、近失事件或长时间 `UNKNOWN` 必须产生至少一项保证增量：

```text

new assumption / boundary contract
new failure scenario
new mechanism
new verification
new runtime evidence or alert
new authority / runbook
revised capacity or economic model
revised ADR
```

# 14. Architecture Review 会议操作

## 14.1 会前材料

Reviewer 应在会前获得：

- 一页 Decision Brief（§13.1.1）及链接的 Design Dossier（§13.1.2）；
- 风险等级；
- Critical Property Register；
- State / Ownership 与 Failure Matrix；
- 至少一个备选方案；
- 容量粗算；
- 关键未知和需要会议裁决的问题。

没有这些材料时，会议很容易退化为现场看图和技术偏好辩论。

## 14.2 会议顺序

推荐顺序：

1. 作者用五分钟说明问题、非目标和风险；
2. 先审关键性质与状态权威；
3. 再审失败、提交、资源和恢复；
4. 然后审架构是否维护这些语义；
5. 最后才讨论技术选型、实现与优化；
6. 明确 `GO / CONDITIONAL_GO / NO_GO / UNKNOWN`；
7. 每个未决项必须有 Owner、期限和阻断级别。

## 14.3 Reviewer 应避免

- 用个人熟悉度替代约束分析；
- 用“业界都这样”替代性质证明；
- 在未理解权威状态前建议拆服务；
- 只审正常路径；
- 用更多监控掩盖语义不清；
- 把所有问题都推成“实现细节”；
- 追求文档完整度而忽视真实高风险缺口。

## 14.4 评审记录

每次评审至少记录：

```text
decision state
blocking findings
accepted residual risks
unknowns
exceptions
actions / owners / deadlines
evidence required
review trigger
```

# 15. 常见反模式与校正

## 15.1 Resume-driven Architecture

**症状**：先选 Kafka、Kubernetes、微服务、Rust、Service Mesh，再寻找需求。  
**风险**：复杂度先于价值，状态和失败语义被组件标签掩盖。  
**校正**：要求每个组件映射到具体性质、负载或运营问题；无法映射则默认删除。

## 15.2 Architecture Diagram = Architecture

**症状**：架构图精美，但没有状态权威、ACK、失败和恢复。  
**校正**：图中必须标记权威状态、提交边界、背压、信任边界与故障域；并配合 Register。

## 15.3 Microservice-first

**症状**：按名词或团队人数拆服务，每个服务共享数据库或同步级联。  
**风险**：形成分布式单体，增加协调和恢复状态。  
**校正**：优先 modular monolith 或清晰 bounded context；只有独立状态、变化率、扩展或故障隔离需求才引入分布式边界。

## 15.4 Unbounded Async

**症状**：异步下载、解压、处理和写出之间全部使用无界 channel。  
**风险**：下游变慢时内存增长、超时、重试和级联故障。  
**校正**：按 bytes 或真实成本设 permit，建立端到端背压和满载策略。

## 15.5 Exactly-once Magic

**症状**：依赖消息系统或流框架标签声称端到端 exactly-once。  
**风险**：外部副作用、重放和跨系统提交仍会重复。  
**校正**：定义业务 effect 的作用域、稳定身份、原子提交和冲突语义。

## 15.6 Retry Everything

**症状**：所有 timeout 和错误都自动重试。  
**风险**：永久错误被放大，依赖故障形成 retry storm。  
**校正**：错误分类、共享 deadline、retry budget、jitter、最大放大比和准入联动。

## 15.7 Shared Mutable Truth

**症状**：多个服务或团队直接修改同一权威表。  
**风险**：规则分散、冲突无裁决、迁移不可控。  
**校正**：单一 mutation authority，其他主体通过契约提议变更或消费投影。

## 15.8 Monitoring After Launch

**症状**：上线后再补 CPU、内存和错误率。  
**风险**：无法判断系统为什么慢、是否重复、是否使用错误版本。  
**校正**：从性质、队列、状态机和恢复模型推导语义指标。

## 15.9 Rollback Fantasy

**症状**：发布计划只写“失败则回滚”。  
**风险**：新数据、Schema 或外部副作用已使旧代码不兼容。  
**校正**：区分 binary rollback、data compatibility、reconciliation 和 forward repair。

## 15.10 Evidence Illusion

**症状**：测试很多、覆盖率高、CI 全绿，因此宣称系统正确。  
**风险**：证据没有映射性质，或与当前制品/环境无关。  
**校正**：从 Claim 开始建立 Evidence Matrix，并记录覆盖与限制。

## 15.11 Unknown Becomes Default Continue

**症状**：未知版本、未知身份或证据缺失时使用默认值继续。  
**风险**：把认识不足转换为数据污染或越权行为。  
**校正**：根据风险 fail closed、quarantine 或返回显式 `UNKNOWN`。

## 15.12 Gate Bureaucracy

**症状**：门禁数量增加，但与风险无关；团队只优化绿色状态。  
**风险**：Goodhart 化、交付停滞、真实风险反而被隐藏。  
**校正**：门禁必须关联关键性质或事故；定期删除低价值检查；按风险裁剪。

# 16. 完整案例：对象存储 CAN 分块文件处理流水线

> 本案例是协议推导与评审练习，不是已经完成实现验证的参考系统。数值、Gate 结论与反例轨迹均为说明性材料；正式设计必须用真实采样、基准、故障测试和授权记录替换。

## 16.1 场景、风险等级与 Gate 映射

- 文件发现服务将对象元数据写入 Kafka；
- 每条消息包含对象 URI、对象版本、大小、校验信息和采集元数据；
- 单个对象不超过 `40 MiB`；
- 文件由大量“业务头 + gzip member”连续组成，典型约 `3000` 个 member；
- 每个 member 属于一个车型，需要使用确定版本的 DBC 解码；
- gzip 解压后执行 CPU-heavy CAN 解析、信号解码和聚合；
- URL 数量极大，系统更关注持续吞吐、成本与可恢复性，而非单文件最低尾延迟。


### 风险等级

该系统默认按 `R2 — Core Production` 设计：它处理持续产生的生产数据，结果会被下游分析、诊断或业务流程消费，错误 DBC、重复正式结果或不可追溯输出可能形成长期数据污染。若结果进一步参与车辆安全控制、资金结算或法规判断，应提升至 `R3 — High Assurance`，增加独立审批、职责分离和持续证据漂移检测。

### Gate 映射

| 评审门禁 | 本案例对应内容 |
|---|---|
| Gate 0 | 问题、Goals、Non-goals 与风险等级 |
| Gate 1 | Workload、SLO、约束与关键假设 |
| Gate 2 | Critical Properties 与优先级 |
| Gate 3 | Source/Operation/Result Identity、状态权威与 DBC 绑定 |
| Gate 4 | 失败、提交点、ACK 顺序与恢复 |
| Gate 5 | 数据面、控制面、调度、快慢路径与运行模式 |
| Gate 6 | 有界资源、容量、恢复能力和单位经济性 |
| Gate 7 | 契约、安全、演进、运维与语言决策 |
| Gate 8 | Verification & Evidence Matrix |
| Gate 9 | Change Envelope、停止条件与生产裁决 |

## 16.2 Goals / Non-goals

### Goals

1. 高吞吐、可水平扩展；
2. 内存、任务、连接、输出和重试全部有界；
3. Kafka 重复投递和 worker crash 不产生重复正式结果；
4. DBC 身份和版本可追踪，未知或不匹配时不猜测；
5. partial output 不作为 completed result 暴露；
6. 可重放、可审计、可恢复；
7. CPU pipeline 可测量并按瓶颈优化。

### Non-goals

1. 不保证全局文件顺序；
2. 不追求每个 member 的独立超低延迟；
3. 不在第一阶段实现跨区域 active-active；
4. 不通过无限并发隐藏对象存储或 DBC Registry 变慢；
5. 不把“最新 DBC”作为隐式处理语义。

## 16.3 Workload、SLO、约束与假设

### 工作负载模型

正式设计必须从生产采样建立分布，而不是只记录均值。至少测量：

```text
files / second: average, p95, peak, burst duration
compressed bytes / file: p50, p95, p99, hard maximum
members / file: p50, p95, p99, hard maximum
compressed bytes / member and inflate ratio
vehicle-model / DBC skew
CPU seconds / member and output amplification
object-store, registry and result-store latency distribution
corrupt / unsupported / unknown-model ratio
replay and recovery workload
```

设计容量必须同时覆盖持续新流量、故障降容和积压恢复；仅验证稳态平均负载不足以支持生产结论。

### 初始 SLO 示例

| 维度 | 示例目标 | 说明 |
|---|---:|---|
| 端到端完成延迟 | `99%` 的受支持对象在目标窗口内正式提交 | 从 Kafka 可见到 completion manifest |
| 数据完整性 | 重复正式结果 `0`；未标记 partial completion `0` | 硬性质，不以延迟换取 |
| DBC 正确性 | 正式结果的 DBC identity/digest 覆盖率 `100%` | 未知必须隔离 |
| 可恢复性 | N-1 条件下在约定时间清空积压 | 必须包含持续新流量 |
| 资源安全 | RSS、临时磁盘、连接和队列始终低于硬上限 | 达到上限时停止接纳 |
| 可追溯性 | 任意正式结果可追溯 source、pipeline、config、binding 与 DBC digest | 作为发布与审计条件 |

数值必须绑定具体 workload corpus、节点规格、依赖版本和成本边界。没有这些限定的“吞吐”或“p99”不构成可复用证据。

### 关键约束

- 源对象必须可通过不可变版本或内容摘要稳定寻址；
- 单文件当前合同上限为 `40 MiB`，但 admission 仍按 bytes 而非文件数控制；
- Kafka 提供至少一次投递语义，系统必须吸收重复；
- 对象、member、车型和 DBC 分布可能偏斜；
- CPU-heavy 解码不得占用异步 I/O executor；
- 生产结果只在权威 completion manifest 提交后可见；
- DBC Registry 和 Result Store 可能超时、降级或短时不可用；
- 技术选型受既有库、团队生产经验、诊断能力和 on-call 责任约束。

### 关键假设登记示例

| ID | 假设 | 运行信号 | 失效条件 | 响应 |
|---|---|---|---|---|
| `A-01` | 单对象不超过生产合同上限 | `object_size` | 任意超限 | admission reject；复审 producer contract |
| `A-02` | member 数和 inflate ratio 处于建模范围 | members/object、inflate ratio | 超阈值或分布漂移 | quarantine；容量与格式复审 |
| `A-03` | 对象版本读取稳定 | version/checksum mismatch | 任意不一致 | 停止处理；重新读取权威版本 |
| `A-04` | 同版本 DBC artifact 内容不可变 | digest mismatch | 任意不一致 | fail closed；触发 Registry 事故 |
| `A-05` | Result Store 的 conditional create 语义可靠 | contract/fault test | 语义或实现变化 | 阻断发布；重新设计提交协议 |
| `A-06` | 当前“整对象下载”在成本与内存上优于细粒度 range | benchmark、request amplification | 对象上限/延迟目标/存储计费变化 | 重新比较 streaming/range 方案 |

假设必须有 Owner、复审触发和证据状态。失效假设不得继续作为已批准架构的隐含前提。

## 16.4 关键性质

### CP-01 — 单一正式完成结果

```text
Identity:
  OperationIdentity = canonical source URI + immutable source version/checksum
    + PipelineSemanticVersion（完整定义见 §16.5）

Guarantee:
  Result Store 最多存在一个正式 completion manifest。

Mechanism:
  staged output + create-only/conditional completion manifest。

Allowed degradation:
  确认同一 OperationIdentity 的正式结果可复用；并发候选只有满足 §16.11 的严格结果等价关系才返回 ALREADY_COMMITTED，否则进入 RESULT_CONFLICT / reconciliation。
```

### CP-02 — DBC 可追踪且不猜测

```text
每个正式输出必须包含 vehicle_model、dbc_id、dbc_version、
dbc_content_digest 与 pipeline_semantic_version。

UNKNOWN_MODEL / DBC_NOT_FOUND / VERSION_MISMATCH
必须进入显式隔离状态，不得回退到 latest 或相似车型。
```

### CP-03 — Partial output 不可见为正式完成

```text
成员级输出可以暂存，但只有 completion manifest 提交后，
下游才将该对象视为完整正式结果。
```

### CP-04 — 资源有界

```text
inflight compressed bytes、active files、CPU jobs、output bytes、
open connections、retry budget 和 reconciliation backlog 均有硬上限。
```

### CP-05 — 已接纳任务有持续责任与明确处置

```text
business dispositions: COMMITTED / QUARANTINED / PERMANENTLY_REJECTED
nonterminal responsibility: RECONCILIATION_REQUIRED
```

已接纳操作不得静默丢失。终止处置必须持久化并可恢复；隔离/拒绝不能掩盖未决提交。reconciliation 的 attempt 可以结束，但责任必须继续或持久化移交，见 §7.3。

“最终进入处置状态”属于有条件的无界活性主张，依赖公平调度、持续资源、依赖恢复及可完成的权威裁决；有限观察不能证明最终完成。另定义队列年龄、处理 deadline 和升级时间等有界运营目标，未达标按其自身 Claim 记录违反，不伪造业务终态。

## 16.5 状态与所有权

| State | Authority | Identity | Owner | Recovery |
|---|---|---|---|---|
| Discovery offset | Kafka consumer group | topic/partition/offset | Processing Platform | Kafka |
| Source bytes | Object Storage | object URI + immutable version | Data Ingestion | re-read exact version |
| DBC artifact | DBC Registry | dbc_id + version + digest | Vehicle Data Platform | immutable artifact store |
| Model→DBC binding | Versioned Binding Registry | binding version + model | Vehicle Data Platform | versioned snapshot |
| Staged outputs | Result Store staging namespace | run_id + member identity | Processing Platform | 对账后仅回收确定不再被引用、且无迟到提交可能的对象 |
| Completion manifest | Result Store | OperationIdentity | Processing Platform | authoritative read / conditional create |
| Disposition / reconciliation record | Durable responsibility ledger | OperationIdentity + attempt / handoff ID | Processing Platform；具名接收 Owner | 重启扫描、恢复对账与升级；不替代 completion authority |
| Runtime queues | Worker process | ephemeral | Runtime Owner | rebuild from durable state |
| Verification evidence | Evidence Store | evidence_id + subject digest | Assurance Owner | immutable retained record |


### 稳定身份

```text
SourceIdentity
  = canonical object URI
  + immutable object version or source checksum

PipelineSemanticVersion
  = processor version
  + output contract version
  + semantic configuration digest
  + DBC binding policy / snapshot version

OperationIdentity
  = SourceIdentity + PipelineSemanticVersion

ResultIdentity
  = OperationIdentity + output partition or range identity
```

Kafka offset、Worker 实例、临时文件路径和本次启动时间都是执行身份，不能替代业务幂等身份。重新处理同一源对象但采用不同语义版本时，应形成新的 `OperationIdentity`，而不是覆盖旧结果。

## 16.6 DBC 绑定语义

不得在 worker 执行时隐式查询“当前最新 DBC”。推荐在接纳或调度阶段解析出不可变绑定，并将实际 binding snapshot 纳入 OperationIdentity；重试、移交与重放同一操作不得再次解析“当前”绑定：

```text
DecodeBinding {
  vehicle_model
  dbc_id
  dbc_version
  dbc_content_digest
  binding_policy_version
  effective_time_basis
}
```

`effective_time_basis` 必须明确是采集时间、文件产生时间、任务接纳时间还是显式版本。否则重放相同源数据可能产生不同结果。

数据面只消费不可变 binding 和 DBC artifact；Binding Registry 不可用时，任务可以暂停或隔离，但不能猜测。

## 16.7 推荐逻辑架构

```text
Kafka
  -> Admission / Dispatcher
       -> Object Fetchers (async I/O, bounded byte permits)
            -> File Buffer / Bounded Spool
                 -> Framer
                      -> CPU Work Scheduler
                           -> Decompress + Parse + DBC Decode
                                -> Bounded Aggregation / Output
                                     -> Staging Store
                                          -> Conditional Completion Manifest
                                               -> Kafka ACK

Control Plane:
  pipeline semantic version
  DBC binding snapshot
  resource limits
  retry / quarantine policy

Management Plane:
  deploy / drain / replay / reconcile / emergency actions

Assurance Plane:
  contract tests / load tests / fault injection / evidence / gates
```

## 16.8 为什么默认避免“两遍偏移预扫描”

方案二“先下载并记录所有 gzip 偏移，再交给下游线程”是否有价值，取决于外层格式是否提供可信的压缩长度：

1. **若业务头包含经过校验的 `compressed_length`**，Framer 可以低成本单遍定位 member 边界；此时记录 offset table 有利于并行调度、重试和局部定位。
2. **若没有可信长度**，gzip/deflate 本身没有可直接跳过到末尾的固定长度字段；发现 member 结束通常需要实际解析压缩流。此时“预扫描”可能等价于先做一遍解压/解析，再由下游重复工作，得不偿失。

因此推荐：

```text
有可靠外层长度：
  single download -> cheap framing -> parallel member work

无可靠外层长度：
  single download -> one-pass decompress/framing -> decode or fused handoff
```

不得把无法证明正确的 magic-byte 搜索作为 gzip 边界算法。

## 16.9 下载与缓冲策略

由于单文件硬上限为 `40 MiB`，默认优先考虑：

```text
完整对象单次下载到 pooled buffer
  + 全局 inflight-byte permits
  + 单遍 framing
  + 不重复读取对象存储
```

这通常比为 3000 个小 member 发起大量 Range 请求更简单、更经济，也能避免对象存储请求放大。其安全前提是全局按 bytes 限制在途文件，而不是只限制文件数。

若实际吞吐使内存预算不可接受，可选择 bounded spool / mmap 临时文件，但必须增加临时磁盘上限、清理、崩溃恢复和 I/O 模型；不能把 spill 当作免费内存。

## 16.10 CPU 调度与局部性

推荐分离：

- 异步 I/O executor：对象下载和外部存储请求；
- 固定 CPU worker pool：解压、解析、DBC decode；
- 有界输出 executor：序列化与结果写入。

通常应优先融合 `decompress + parse + DBC decode`，避免把大块未压缩中间数据跨队列传递。若基准表明解压与 decode 的瓶颈、向量化或库约束明显不同，再拆分独立 CPU stage。

调度可以采用：

```text
bounded global ready queue
  + per-worker local deque / work stealing
  + DBC/model locality hint
  + fairness and starvation bound
```

不要为每个车型永久创建无界队列。局部性优化必须服从资源上界与租户公平。

批大小不应拍脑袋固定。应通过基准在以下目标间权衡：

- 调度开销；
- DBC cache locality；
- cancellation 粒度；
- 输出聚合成本；
- 公平性和尾延迟。

## 16.11 幂等与提交协议

### 16.11.1 权威提交与严格结果等价

本案例采用**严格等价**，不是仅按“首个合法结果胜出”。条件创建只保证同一 OperationIdentity 至多一个正式 manifest，不能证明不同执行得到相同业务结果。

`ResultEquivalence` 必须同时核对 OperationIdentity、规范化业务结果摘要与必要 provenance：

- 按 source member index、frame/event identity 和明确排序规则生成稳定记录序列；
- 固定字段编码、数值/浮点归一化、空值、单位、Schema 与 output contract version；
- 对 member 覆盖、错误/丢弃处置、计数、每个输出范围及总结果计算内容摘要；
- provenance 包含 source digest、pipeline semantic version、semantic config digest、binding snapshot 与实际 DBC digests；
- 排除 run_id、worker ID、临时路径、执行时间等非业务字段；若时间或顺序本身有业务含义，则不得排除。

规范化算法和摘要算法必须版本化并验证确定性；非确定性业务输出需另行设计等价合同，不得沿用此案例自动放宽比较。相同语义版本只是必要身份条件，不是结果等价证据。

对象级提交流程：

1. 接收 Kafka record；正式接纳前，持久化源身份、固定绑定、OperationIdentity 及责任记录，登记 partition、offset 与 assignment epoch；禁用自动提交。接纳记录不可写时停止接纳，不能只依赖 worker 内存保存已接纳责任。
2. 先读取持久化责任/处置记录，再权威读取 manifest。存在未闭合 UNKNOWN 或 RESULT_CONFLICT 时必须恢复对账并比较已保存候选，不得走“已有结果”快路径将其抹除。无未决记录且身份、必要 provenance、输出完整性与摘要可验证时，才可复用已有正式结果；这不宣称另一未执行候选必然等价。已持久化的合法隔离/拒绝应按合同复用处置，后续重放须显式授权，不静默覆盖原记录。
3. 无已确认可复用结果或终止处置时，将当前执行输出写入独立 run_id staging，校验成员覆盖、完整性和 error policy，生成规范化摘要与不可变 manifest 候选。在发起提交前持久化 intent（含 OperationIdentity、attempt ID、候选 digest、staging refs 与 Owner），确保进程在发送后、处理返回前崩溃也能恢复不确定责任。
4. 以完整 OperationIdentity 的无歧义编码/摘要作为条件创建键，重试保持同一键和相同请求意图。manifest 引用的输出必须先持久化；禁止覆盖正式 manifest。
5. 按 §7.3 区分调用结论：确认成功后持久化完成记录；确认无效果时按预算重试；确认冲突时权威读取既有 manifest 并比较；未知时进入持久化 reconciliation。
6. 当前候选与既有结果严格等价才记 `ALREADY_COMMITTED`。同身份、同版本但结果摘要或必要 provenance 不同，记 `RESULT_CONFLICT`，保留两个候选和差异证据，停止该操作的成功推进并升级裁决；既有 manifest 仍是权威事实，不能覆盖，也不能把冲突执行记成正常成功。
7. 只有确认成功、可验证复用或合法持久化终止处置，才标记 record 为可推进；Kafka 恢复位置仍由 §16.11.3 的分区协调器决定，不能由单个 worker 直接提交。

### 16.11.2 未知结果与责任恢复

超时后 reconciliation 使用同一 OperationIdentity 读取权威事实；not-found 仍可能与在途迟到成功并存。仅在后端合同提供“不会再生效”的确认，或安全的同键同意图重试已得到确定结论时，才能结束不确定窗口。不得把超时当作 `CONFIRMED_NO_EFFECT`，也不得因重试次数耗尽而丢弃责任。

持久化 ledger 记录候选 manifest digest、staging refs、原请求身份、已知结果、接收 Owner、重试/升级期限和交接确认。重启或接管后扫描未闭合记录；依赖不可用时保留未知并背压，超过期限升级给运营 Owner。本案例不允许仅凭“已写入 reconciliation 队列”推进该 record 的 Kafka 位置。

GC 不得仅凭 staging 年龄删除未决输出。回收必须证明没有正式 manifest 引用、没有仍可能迟到生效的写入，并已完成安全对账或确认无效果；还须通过受控状态转换阻止新执行引用待回收对象，消除检查后又被引用的竞态。否则保持受保护引用。达到存储或责任积压上限时停止接纳，不通过删除未决数据制造空间。

`QUARANTINED/PERMANENTLY_REJECTED` 作为交付终止处置，须持久化源身份、原因、处理策略版本、修复/重放 Owner 与可恢复记录，并通过协调/fencing 确认其他执行不能继续为该已终止操作发起提交、既有在途请求不会再生效。它们结束本次处理责任的方式必须可审计，不能等同于成功输出。

上述超时与幂等设计是按后端合同推导的工程选择；参考 [AWS Builders’ Library：幂等 API 与安全重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)，实际存储实现仍需单独验证。

### 16.11.3 Kafka 分区连续完成前缀

这里限定为传统 consumer group 的 KafkaConsumer 分区 offset 语义，不适用于其他逐条确认协议。提交的是每个 partition 的**下次恢复位置**，不是单条 record 的独立 ACK。基础语义参考 [Apache Kafka 4.1 KafkaConsumer API](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)。

本案例选择“分区内并发处理、按实际投递顺序的连续已处置前缀推进”：

1. 单一 consumer/coordinator 线程拥有 poll、pause/resume 与 commit；worker 只回报完成事件，不能共享调用非线程安全 consumer。
2. 每个 partition 在当前 assignment epoch 内，按 poll 实际交付顺序登记 record 与可恢复 next-position（保留相应 leader epoch 元数据）；完成表包含成功、合法隔离/拒绝或未决。只有前缀中的每条 record 都已持久化处置，才允许推进。
3. 若 offset 100 未决、101 已完成，不能提交 102；101 完成只能登记在窗口中等待。这里的“连续”指交付序列前缀，不要求数值 offset 相邻：事务控制记录、日志压实（compaction）或隔离级别过滤等可能造成间隙；应用自行跳过业务 record 则必须另有合法处置依据。
4. 前缀后仍有已交付未处置 record 时，next offset 不得越过它，使用该 record 的 offset；已处理完整批次时，使用该批次捕获的 `ConsumerRecords.nextOffsets()` 等经所用客户端合同确认的后继位置。不得把最新 poll position 用于较早的未完成批次，也不得靠逐个 offset 加一构造不存在的 record。
5. 完成事件绑定 partition、offset 与 assignment epoch。撤销时停止分发，仅在仍持有所有权且协议允许时提交安全前缀；分区丢失或新 assignment 后，旧回调不得更新新窗口或提交位置。Kafka group/generation 校验与应用 epoch 检查配合使用。
6. 提交由协调器串行管理，禁止乱序异步重试旧 offset 使已确认位置倒退；提交失败或结果未知时保留未确认状态，按客户端协议恢复，不假定 broker 已接受。重新投递通过权威 manifest/处置记录吸收重复。
7. 同时限制在途条数、字节数、完成窗口大小与最老未决年龄。前缀阻塞触及预算时 pause 相应分区并向上游背压，consumer 继续满足 poll/心跳契约；超时升级或交接责任，不跳过空洞强制提交。

Kafka 保留窗口与可接受停顿时间必须进入恢复合同；位置因保留/截断不可恢复时，应报警并从持久化接纳记录及源目录核对缺口，不得静默 reset 到 latest 并宣称无丢失。尚未接纳的发现消息如何重建，由发现服务与不可变源目录合同负责。

assignment fencing 保护的是消费协调状态，不自动撤销已经发往 Result Store 的副作用；迟到 worker 写入仍必须受同一 OperationIdentity 的条件创建与 reconciliation 协议约束。

若业务允许 member 级独立可见，可把该模式下沉到 member identity，但会增加状态、提交放大与 reconciliation 成本，需重新评审等价合同和交付边界。

## 16.12 有界资源示例

```text
max_active_files           = derived from byte budget
max_inflight_source_bytes  = B_source
max_cpu_jobs               = near measured CPU saturation point
max_queued_compressed_bytes= B_work
max_output_buffer_bytes    = B_output
max_object_connections     = object-store quota aware
max_retry_attempts         = classified by error
max_retry_time             = within end-to-end deadline
max_reconciliation_backlog = explicit operational bound
```

准入应同时受 source bytes、CPU permits 和 output pressure 约束。只按 Kafka message 数量暂停不足以控制大小差异和 CPU 成本差异。

## 16.13 容量模型

定义：

```text
lambda_f = files / second
S_c      = average compressed bytes / file
N_m      = members / file
t_d      = CPU seconds / member for decompress + decode
R_o      = output bytes / input byte
```

则：

```text
network input demand = lambda_f x S_c
member rate          = lambda_f x N_m
CPU core lower bound = lambda_f x N_m x t_d
output bandwidth     = lambda_f x S_c x R_o
```

实际 CPU 预算还要加入 framing、聚合、序列化、缓存 miss、调度开销和 headroom。

示例：

```text
lambda_f = 25 files/s
S_c      = 20 MiB/file
N_m      = 3000

t_d      = 80 microseconds/member

input bandwidth ~= 500 MiB/s
member rate     = 75,000/s
CPU lower bound = 6 CPU-seconds/s ~= 6 fully utilized cores
```

若目标利用率为 60%–70%，并考虑恢复和抖动，实际配置显著高于理论 6 核。最终数值必须由代表性语料端到端基准确定。


### 故障降容与积压恢复

仅证明正常状态下 `service_rate > arrival_rate` 不足以支持高可用结论。还必须验证：

```text
recovery_service_rate > live_arrival_rate
catch_up_time ~= backlog / (recovery_service_rate - live_arrival_rate)
```

N-1、依赖恢复、重放和 rolling upgrade 都可能与实时流量竞争相同资源。恢复速率、在线流量保护比例和最大 backlog age 必须显式建模。

### 单位经济性

至少跟踪：

```text
cost / GiB source data
cost / million gzip members
cost / vehicle-hour
cost of replay
cost of quarantine and reconciliation
cost of retained evidence
```

性能优化只有在满足关键性质、SLO 和成本边界后才有意义。更高峰值吞吐并不自动优于更稳定、成本更低且恢复能力更强的实现。

## 16.14 失败与恢复矩阵节选

| Failure | Partial Effect | Decision / Recovery |
|---|---|---|
| Kafka duplicate | 任务可能再次执行 | completion manifest 吸收重复 |
| Download timeout | 对象可能只下载一部分 | 丢弃不完整 buffer；按分类重试 |
| Object version changed | 输入身份不再稳定 | 拒绝；要求 immutable version |
| Corrupt member | 部分成员已处理 | 按合同 quarantine whole object 或显式 partial policy；不得静默完成 |
| Unknown model | 无合法 DBC | quarantine；等待 binding 修复后重放 |
| DBC Registry unavailable | binding 无法验证 | pause / degraded；不回退猜测 |
| Worker crash before manifest | staging 存在，创建请求可能仍在途 | 从 ledger/权威状态对账；未确认无效果前保护 staging，不直接按年龄回收 |
| Manifest committed, offset commit failed | 正式结果存在，恢复位置未确认 | 重投后验证复用；仅按分区连续完成前缀推进 |
| Result Store conflict | 另一执行已提交 | 比较规范化结果摘要与必要 provenance；不等价记 RESULT_CONFLICT，保留证据并裁决 |
| Conditional create timeout | 成功、未生效或在途均可能 | UNKNOWN；同键同意图对账，not-found 不结束责任 |
| Offset 101 completed before 100 | 后续结果已有，前缀有空洞 | 禁止提交 102；有界完成窗口、pause 与升级 |
| Rebalance during work | 旧 worker 仍可能完成 | epoch fencing 拒绝旧回调推进新 assignment；副作用由权威提交协议吸收 |
| Output slowdown | output queue 增长 | 背压到 CPU，再到 fetch/Kafka pause |
| Memory pressure | byte permits 接近上限 | 停止接纳；不得继续扩大队列 |

```text
files_discovered / accepted / committed / quarantined

active_files

fetch / framing / decode / commit service time
```

## 16.16 验证计划

| Property | Verification |
|---|---|
| 单一正式结果 | 重复投递、commit/ACK crash、rebalance、并发执行测试 |
| Partial 不可见 | 在每个阶段注入 crash，验证无 completion manifest 时下游不可见 |
| DBC 不猜测 | unknown model、registry timeout、version mismatch 负向测试 |
| 资源有界 | 2× 峰值、持续下游变慢、超大合法文件和混合大小压力测试 |
| 背压闭合 | 人为降低 output/DBC/object store，验证压力传播和内存稳定 |
| 恢复能力 | 积压回放、节点 N-1、进程反复崩溃和 orphan staging 回收 |
| 容量模型 | 代表性语料端到端基准，比较预测与实际误差 |
| 版本追踪 | 对任意结果追溯 source、pipeline、binding、DBC 和 config digest |

### 16.16.1 反例轨迹与预期 Oracle

以下为待实现的验证场景，不是已执行结果；项目需保存实际轨迹与 Evidence ID。

| 场景 | 最小轨迹 | 预期 Oracle |
|---|---|---|
| 越过未决 offset | 收到 100、101；101 完成，100 未决 | 提交位置不超过 100；不得提交 102 |
| offset 数值有空洞 | 实际投递 100、104；100 完成 | 可推进到 104；不要求虚构的 101–103 完成 |
| 迟到写成功 | create 超时；read not-found；原 create 随后成功 | 保持未知直至权威确认；不换键、不提前 GC |
| 发送后立即崩溃 | intent 已持久化；create 已发送；尚未处理返回 | 重启恢复未决 intent；不能按“无返回”判定无效果 |
| 同版本不同结果 | 同 OperationIdentity，两个规范化摘要不同；冲突方随后重启 | RESULT_CONFLICT 保留；重放不能用已有 manifest 快路径抹除冲突 |
| 旧 assignment 回调 | epoch E1 被撤销，E2 接管，E1 worker 返回 | 不更新 E2 完成窗口、不提交 E1 位置 |
| 责任接收方重启 | durable handoff 已确认，接收方崩溃 | 重启可枚举并恢复责任；未确认业务处置不推进 offset |

## 16.17 Rust 与 C++23 的正确决策位置

两者都能实现该流水线。决策应基于：

- 现有 DBC/压缩/解析库与复用成本；
- 团队熟练度、招聘和 on-call 能力；
- 内存安全与 unsafe/FFI 边界；
- profiling、sanitizer、fuzzing、构建和供应链能力；
- CPU 性能、编译时间和部署目标；
- 长期维护与迁移成本。

推荐用同一代表性语料实现窄范围原型，比较：吞吐、p99、RSS、CPU、崩溃注入、开发复杂度和可观测性，而不是用语言声誉替代证据。


## 16.18 Change Envelope 与示例裁决

首次生产暴露或重大语义变更应定义受控边界：

```text
population:
  selected vehicle models / tenants / object prefixes

exposure:
  max files, max source bytes, max duration, max concurrency

preconditions:
  required evidence IDs, DBC snapshot, artifact/config digests

success criteria:
  correctness, resource, latency, recovery and cost thresholds

stop conditions:
  duplicate formal result
  DBC digest mismatch
  unbounded queue / RSS growth
  queue age or retry amplification beyond threshold
  missing provenance or evidence binding

recovery:
  stop admission, drain, quarantine, reconcile, forward repair
```

建议先使用 shadow 或非权威输出验证 framing、DBC、lineage 和容量；样本必须包含大型对象、热点车型、损坏输入和依赖抖动，而不是只选最干净流量。

以下是假设已完成对应证据与授权后的裁决写法，不表示本案例真的通过 Gate；未完成的阻断项仍应 UNKNOWN/NO_GO。Gate 6 的条件只能是扩大暴露前的条件，不能作为当前暴露尚缺关键恢复能力的借口。

```text
Gate 0-5: GO
Gate 6: CONDITIONAL_GO
  scope: verified node specification and <= 2x measured peak workload
  precondition: current limited exposure has verified recovery capacity
  condition: complete N-1 catch-up benchmark before expanding beyond that scope
  expiry: 2026-10-15

Gate 7: GO
Gate 8: GO for the declared corpus and failure profile
  unknown exotic header variants: QUARANTINE

Gate 9: GO
  exposure: 5% of object bytes
  automatic abort: any hard-property violation or memory-bound breach
```

这类裁决明确区分已证明范围、剩余未知、临时条件和撤销触发，比“整体看起来可以上线”更可审计。

- [ ] 所有阻断级 `UNKNOWN` 已解决或明确拒绝放行。

13. 所有队列、缓存、任务、连接、重试和临时状态是否有界？

# 19. 团队成熟度与采用路线

| 等级 | 典型状态 | 下一步 |
|---|---|---|
| L0 — Component-driven | 先选技术，缺少问题和状态模型 | 强制 Decision Brief 与 Non-goals |
| L1 — Functional | 正常路径可用，失败与 Owner 模糊 | 建立 Property、State、Failure Register |
| L2 — Bounded | 资源有界，有基本恢复 | 增加容量、运行模式和边界契约 |
| L3 — Operable | SLO、Owner、发布和恢复明确 | 建立 Evidence Matrix 与生产门禁 |
| L4 — Evidence-driven | 关键主张有可追踪证据 | 关联假设、环境漂移和证据时效 |
| L5 — Adaptive Assurance | 结论随漂移自动失效，事故形成保证增量 | 持续防止 Goodhart 化并回收复杂度 |

推荐采用顺序：

```text
先统一术语和最小模板
  -> 在一个高价值项目试点
  -> 用真实评审和事故校准
  -> 将高确定性机械规则编码进 CI
  -> 保留人工审查处理未编码属性
  -> 建立成本、证据与漂移平台能力
  -> 定期删除低价值门禁和长期例外
```

不要试图通过一次性发布完整标准让团队“直接达到 L4”。流程厚度必须与现有能力和风险匹配，但关键状态、身份和认识边界必须从第一天保持诚实。

# 20. 文档与标准维护

## 20.1 版本规则

- 原则、术语或门禁语义发生不兼容变化：提升 Major；
- 新增兼容的模板、场景或要求：提升 Minor；
- 文字澄清、排版和不改变语义的修正：提升 Patch；
- 本文与方法论文档使用统一 suite version，但允许独立 patch。

## 20.2 复审触发

以下任一事件触发复审：

- 重大事故或近失事件；
- 关键假设失效；
- 新合规、安全或业务硬约束；
- 工作负载、成本或故障域显著变化；
- 新的分布式边界、权威状态或特权主体；
- 现有门禁频繁被例外绕过；
- 证据与生产漂移长期无法关联；
- 至少每 12 个月一次基线复审，高风险系统应更短。

## 20.3 单一事实来源

本 Markdown 文件是执行参考的唯一权威源。任何表单、门户、CI 配置或导出视图必须能够追溯到本文版本；不得维护无法同步的平行“精简版标准”。实际项目可以实例化模板，但不得静默改变规范语义。

> **最终操作原则**  
> 评审的目的不是证明设计者足够聪明，也不是让所有检查变绿，而是在代码和流量扩大之前，尽早暴露状态、失败、资源、权限、恢复和证据链中的高代价错误。最好的门禁会阻止不可接受风险，同时让低风险、可逆决策保持快速。


## 20.4 方法论与操作手册在套系中的边界

```text
ESD-METHOD-001
  定义：为什么这样设计、核心术语是什么、能够证明到什么范围

ESD-REFERENCE-001
  执行：按什么阶段工作、提交什么制品、如何评审、裁决和持续维护
```

上述两篇不独占全套规范权威；风险、Gate 与例外服从 GOV，Claim、Assumption 与 Evidence 服从 ASSURANCE，运行与恢复服从 OPS，关系由 SUITE §3.1 控制。领域 Profile 可依 GOV 授权收紧要求或裁剪执行深度，不得静默改写权威定义。

## 20.5 结论

高质量 Architecture Review 的目标不是批准一张架构图，而是阻止未经定义的状态、失败、权限、资源和未知进入生产。一个完成的设计应留下可追踪的推理链：

```text
Problem
  -> Constraints / Assumptions / Risk
  -> Critical Properties
  -> State / Identity / Ownership
  -> Failure / Consistency / Recovery
  -> Architecture / Resource Control
  -> Capacity / Economics / Evolution
  -> Verification / Evidence
  -> Controlled Change
  -> Runtime Learning
```

当团队能够在任意环节诚实回答“我们知道什么、为什么相信、覆盖到哪里、什么时候失效”，系统设计才从经验与审美上升为可治理的工程实践。
