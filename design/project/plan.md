## 2. 三项成果与权威边界

| 成果 | 要解决的问题 | 成立依据 |
| --- | --- | --- |
| 系统设计与工程保证体系 ESD | 如何推导、评审、运行和演进系统 | 真实项目能表达约束与风险，追溯证据并作出可解释决策 |
| 代码设计与实现保证体系 ECD | 系统性质如何落实到类型、所有权、模块、协议和数据布局 | 方法有可复核代码依据，语言机制的保证与剩余风险明确 |
| 受控维护与出版能力 | 内容、版本、证据与阅读制品如何保持对应 | 修改可追踪，检查范围明确，草案和正式发布不会混淆 |

核心术语及规范权威仍按 [00 §3](../00-优秀系统设计与工程保证标准-文档体系与规范关系-v1.0.0.md) 划分。风险、授权、例外与符合性沿用 [03](../03-系统设计与工程保证治理及符合性规范-v1.0.0.md)，Claim、证据和裁决充分性沿用 [04](../04-工程保证论证证据与裁决规范-v1.0.0.md)。本计划的阶段和工作包用于管理进度，不另设审批权或平行 Gate 语义。

工作顺序为：系统问题与约束 → ESD 性质与架构 → ECD 实现机制 → 项目验证与反馈 → 必要的方法修订。Markdown 权威源、证据索引、有限自动检查及受控出版共同支撑这条链。

不以文章数量、模板填满率或全绿报表作为进度；不因文档存在就推定实现完成，不因测试通过就推定批准存在。

## 3. 两条主线、两类支撑

**主线 A，优先推进 ESD 可采用性：** 草案收口 → 最小模板 → 风险匹配的采用试点 → 反馈修订 → 发布候选 → 正式基线。

**主线 B，推进 ECD 实证：** 历史资产接收 → VS-001/002 源码与证据复核 → VS-003 → 性能假设检验 → 一次跨语言映射 → 工程参考与小型模式目录 → C++23 Profile。

支撑一负责资产、进度和证据管理；支撑二负责机械检查及出版隔离。ESD 发布不等待全部语言 Profile，ECD 也不会随 ESD 发布自动成为稳定基线。

默认最多同时推进两个实质工作包；涉及同一规范语义区域的修改尽量串行。这不是要求创建多个执行代理，也不是一次授权实施所有阶段。

## 7. 最小采用包与规则反例

先从 [02 §13](../02-优秀系统设计-从约束不变量到证据-v1.1.0.md) 及 GOV、ASSURANCE、OPS 的现有模板提取，避免把历史模板整包迁入。

| 拟首批模板 | 用途 |
| --- | --- |
| `decision-brief.md` | 一页说明待决问题、推荐方案、主要风险及证据入口 |
| `design-dossier.md` | 约束、性质、状态、失败、资源与运行设计 |
| `assurance-case.md` | Claim、Argument、Evidence、反证及未知 |
| `decision-record.md` | 分开记录要求事实、例外授权、对象符合性和 Gate 决定 |
| `exception-record.md` | 范围、权限、期限、补偿与退出 |
| `runbook.md` | 前置条件、操作、验证和恢复 |

其他登记表先作 dossier 内区段或引用；不要求每个项目创建六个文件。模板中的枚举与字段应回指现行规范，不复制成新的语义权威。

规则反例优先覆盖：Exception 不改变 Claim 支持；非阻断 MUST 不能被汇总忽略；ID 存在不代表适用性正确；较大 offset 完成不能越过较小未处置记录；提交超时不代表无副作用；语义版本相同不代表结果等价。

每个反例记录“输入 → 预期结论 → 不可接受结论 → 条款 → 理由”。初期仅为 Oracle；真正执行检查器或实现测试后，才能附带执行证据。结构检查不能判断完整语义正确性，不先开发通用规则引擎。

| 候选 | 验证重点 | 启动前缺项 |

| A：kb 构建与发布流程 | Markdown 身份、内容版本、草案与发布、构建检查、批准、历史保护和恢复 | 具体变更、适用范围、风险理由、具名 Owner/Reviewer；不能因“有界”直接授予 R1 |
| B：CAN 数据处理系统 | 源身份、处理语义、接纳与所有权、正式结果、交付边界和崩溃恢复 | 获准访问的真实代码提交、配置、脱敏数据与输出系统；不能把正文案例当真实实现或直接授予 R2 |

R1/R2 是 [GOV §4](../03-系统设计与工程保证治理及符合性规范-v1.0.0.md) 的风险等级，不是阶段编号。候选待确认；离线审阅、沙箱实现和故障演练不自动授权生产操作，也不要求 kb 机械套用业务服务的全部运行制度。

真实 CAN 系统采用什么结果系统，就围绕什么权威边界推导提交和恢复；不得只为匹配参考案例而添加 manifest store、ledger 等持久组件。任何新增权威状态都要说明价值和维护成本。

[Atlas 已有记录](../examples/pilots/atlas-bootstrap-status-review.md) 保留为单评审者、固定提交的 mock 抽样示例及执行证据，不删除、不升格为两个完整采用试点。本轮主线已收回工程文档体系，不继续推进 Atlas 实施；其记录中的后续步骤是该案例的未完成事项，不是本计划自动启动的任务。

成功不是所有案例获得 GO，而是问题能被发现、结论可解释、证据可追溯且成本可衡量。记录独立评审分歧、材料准备与评审耗时、漏检及机制修改；合理 NO_GO 也可证明方法有用。未执行的缺陷注入不能算检出，命令耗时不能替代人工成本。

## 9. ECD 接收与实现验证路线

历史 `ECD-METHOD-001 v0.3.0`、VS-001/002 完成声明及相关发现目前仅由说明稿提及，不继承其验证资格。接收链为：

```text
报告 → 完整源码 → commit / 摘要 → 工具链与命令
     → 原始输出 → 适用范围 → 与当前 ESD 的兼容性评估
```

只收到报告时登记“报告已接收、证据待复核”；没有文件时登记“尚未接收”。需要重跑就生成新记录，重实现和新运行都不得冒充历史原型或历史证据。源码若有独立仓库，引用精确提交，不复制成第二份事实源。

前两切片证据接收后再启动 VS-003，重点为错误与异常边界、取消与 deadline、重试权威和预算、任务与 permit 收尾、准入先于分配、等待生产者与结果持有者上界、单一资源配置权威及部分进度/终态责任。之后检验性能假设，并做一次小型 Rust/Zig 对照映射，不并行重写三套引擎。

方法经校准后提炼小型模式目录和工程参考。C++23 Profile 沿“通用要求 → 语言表达 → 编译器保证 → 工具保证 → 剩余风险 → 验证证据”组织；既有 C++/Zig 文章不能直接作为该 Profile 或实现验证的完成证明。
