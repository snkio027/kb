## 2. 三项成果与权威边界

| 成果 | 要解决的问题 | 成立依据 |
| --- | --- | --- |
| 系统设计与工程保证体系 ESD | 如何推导、评审、运行和演进系统 | 真实项目能表达约束与风险，追溯证据并作出可解释决策 |
| 代码设计与实现保证体系 ECD | 系统性质如何落实到类型、所有权、模块、协议和数据布局 | 方法有可复核代码依据，语言机制的保证与剩余风险明确 |

核心术语及规范权威仍按 [00 §3](../00-优秀系统设计与工程保证标准-文档体系与规范关系-v1.0.0.md) 划分。风险、授权、例外与符合性沿用 [03](../03-系统设计与工程保证治理及符合性规范-v1.0.0.md)，Claim、证据和裁决充分性沿用 [04](../04-工程保证论证证据与裁决规范-v1.0.0.md)。本计划的阶段和工作包用于管理进度，不另设审批权或平行 Gate 语义。

工作顺序为：系统问题与约束 → ESD 性质与架构 → ECD 实现机制 → 项目验证与反馈 → 必要的方法修订。Markdown 权威源、证据索引、有限自动检查及受控出版共同支撑这条链。

不以文章数量、模板填满率或全绿报表作为进度；不因文档存在就推定实现完成，不因测试通过就推定批准存在。

## 3. 两条主线、两类支撑

**主线 A，优先推进 ESD 可采用性：** 草案收口 → 最小模板 → 风险匹配的采用试点 → 反馈修订 → 发布候选 → 正式基线。

**主线 B，推进 ECD 实证：** 历史资产接收 → VS-001/002 源码与证据复核 → VS-003 → 性能假设检验 → 一次跨语言映射 → 工程参考与小型模式目录 → C++23 Profile。

支撑一负责资产、进度和证据管理；支撑二负责机械检查及出版隔离。ESD 发布不等待全部语言 Profile，ECD 也不会随 ESD 发布自动成为稳定基线。

默认最多同时推进两个实质工作包；涉及同一规范语义区域的修改尽量串行。这不是要求创建多个执行代理，也不是一次授权实施所有阶段。

## 7. 最小采用包与规则反例

先从 [02 §13](../02-优秀系统设计-从约束不变量到证据-v1.1.0.md) 及 GOV、ASSURANCE、OPS 的现有模板提取，避免把历史模板整包迁入。

| 拟首批模板 | 用途 |
| --- | --- |
| `decision-brief.md` | 一页说明待决问题、推荐方案、主要风险及证据入口 |
| `design-dossier.md` | 约束、性质、状态、失败、资源与运行设计 |
| `assurance-case.md` | Claim、Argument、Evidence、反证及未知 |
| `decision-record.md` | 分开记录要求事实、例外授权、对象符合性和 Gate 决定 |
| `exception-record.md` | 范围、权限、期限、补偿与退出 |
| `runbook.md` | 前置条件、操作、验证和恢复 |

其他登记表先作 dossier 内区段或引用；不要求每个项目创建六个文件。模板中的枚举与字段应回指现行规范，不复制成新的语义权威。

规则反例优先覆盖：Exception 不改变 Claim 支持；非阻断 MUST 不能被汇总忽略；ID 存在不代表适用性正确；较大 offset 完成不能越过较小未处置记录；提交超时不代表无副作用；语义版本相同不代表结果等价。

每个反例记录“输入 → 预期结论 → 不可接受结论 → 条款 → 理由”。初期仅为 Oracle；真正执行检查器或实现测试后，才能附带执行证据。结构检查不能判断完整语义正确性，不先开发通用规则引擎。

同时补齐混合已知不满足/未知、例外过期/越权/范围不符/条件不可执行、假设“已监测但未验证”、未运行/工具错误/旧证据误作新 PASS，以及构建成功/版式美观误作系统性质证据的反例。机械检查的首批范围是 Front Matter、身份/版本、显式本地链接、按文档角色划定的重复 ID、围栏、枚举和源/发布映射；不据此宣称语义充分或组织独立性成立。

## 8. 采用案例建议与 Atlas 记录的定位

| 候选 | 验证重点 | 启动前缺项 |
| --- | --- | --- |
| A：kb 构建与发布流程 | Markdown 身份、内容版本、草案与发布、构建检查、批准、历史保护和恢复 | 具体变更、适用范围、风险理由、具名 Owner/Reviewer；不能因“有界”直接授予 R1 |

R1/R2 是 [GOV §4](../03-系统设计与工程保证治理及符合性规范-v1.0.0.md) 的风险等级，不是阶段编号。候选待确认；离线审阅、沙箱实现和故障演练不自动授权生产操作，也不要求 kb 机械套用业务服务的全部运行制度。

真实 CAN 系统采用什么结果系统，就围绕什么权威边界推导提交和恢复；不得只为匹配参考案例而添加 manifest store、ledger 等持久组件。任何新增权威状态都要说明价值和维护成本。

[Atlas 已有记录](../examples/pilots/atlas-bootstrap-status-review.md) 保留为单评审者、固定提交的 mock 抽样示例及执行证据，不删除、不升格为两个完整采用试点。本轮主线已收回工程文档体系，不继续推进 Atlas 实施；其记录中的后续步骤是该案例的未完成事项，不是本计划自动启动的任务。

成功不是所有案例获得 GO，而是问题能被发现、结论可解释、证据可追溯且成本可衡量。记录独立评审分歧、材料准备与评审耗时、漏检及机制修改；合理 NO_GO 也可证明方法有用。未执行的缺陷注入不能算检出，命令耗时不能替代人工成本。

每个候选实例拟保留一份绑定真实版本的 dossier、一份保证与决策记录、一份采用反馈及原始证据引用，避免同一事实多处复制。CAN 场景需针对实际系统覆盖未知提交、重复/乱序完成、分区移交、资源耗尽、依赖降速和责任接收方重启；这些是拟验证场景，不是本次运行结果。

## 9. ECD 接收与实现验证路线

历史 `ECD-METHOD-001 v0.3.0`、VS-001/002 完成声明及相关发现现由说明稿和已接收规划原稿提及；它们所指的方法文件、源码、报告和原始日志仍未接收，不继承验证资格。接收链为：

```text
报告 → 完整源码 → commit / 摘要 → 工具链与命令
     → 原始输出 → 适用范围 → 与当前 ESD 的兼容性评估
```

只收到报告时登记“报告已接收、证据待复核”；没有文件时登记“尚未接收”。需要重跑就生成新记录，重实现和新运行都不得冒充历史原型或历史证据。源码若有独立仓库，引用精确提交，不复制成第二份事实源。

正确性测试、Sanitizer、变异测试、并发测试和 benchmark 分别评价；某个工具缺失不得伪装为该项 PASS，也不自动否定无关的已核验设计。

前两切片证据接收后再启动 VS-003，重点为错误与异常边界、取消与 deadline、重试权威和预算、任务与 permit 收尾、准入先于分配、等待生产者与结果持有者上界、单一资源配置权威及部分进度/终态责任。之后检验性能假设，并做一次小型 Rust/Zig 对照映射，不并行重写三套引擎。

方法经校准后提炼小型模式目录和工程参考。C++23 Profile 沿“通用要求 → 语言表达 → 编译器保证 → 工具保证 → 剩余风险 → 验证证据”组织；既有 C++/Zig 文章不能直接作为该 Profile 或实现验证的完成证明。

性能验证预先声明代表性访问模式、输入、比较基线、指标、重复策略、噪声与决策阈值，允许结果推翻原偏好；微基准不自动成为真实 CAN 生产性能证据。跨语言抽查使用同一核心合同，比较静态保证、运行机制与剩余风险。

参考与模式优先追踪关键性质及高后果实现边界，不要求所有函数连接规范编号。模式条目说明问题、设计力、所有权、失败、成本、替代及不适用条件；单一实例仅称案例级候选。OOP/GoF 按实际变化轴补入，DOD 按访问模式与测量推导，不预设全面 SoA。语言 Profile 还需表达编译、运行与维护成本；示例来自可构建源或受检查片段，风格指南不替代性质映射。

## 11. 检查、发布绑定与公共证据

### 11.1 四层检查及其结论边界

| 层次 | 拟首次引入 | 可检查范围 | 不代表什么 |
| --- | --- | --- | --- |
| 结构层 | P1 | 解析、身份、版本、声明字段、本地链接、枚举与文件关系 | 不代表协议正确或要求语义充分 |
| 规范规则层 | P1/P2 | 已明确规则的合法/错误样例、状态迁移和汇总 | 不代表输入事实真实或全部语义已编码 |
| 实现验证层 | P2/P4 | 编译、测试、故障注入、Sanitizer、benchmark | 不代表未覆盖环境或生产资格 |
| 出版层 | P0/P3 | 源绑定、字体、引用、分页、文本、摘要与批准范围 | 不代表业务系统或代码性质已经符合 |

表中时间为拟引入阶段，不抹去仓库已有的局部检查，也不宣称已具备全部自动化。CI 按影响选择层次：链接修改不强制全套 C++ 压测；模板/枚举/检查器变更需对应正反例；协议或代码变更需切片验证；出版引擎变更才触发相应排版和渲染检查。先机械检查，再建议性语义评价，最后才考虑经验证、经授权的限定阻断；工具失败不能默认为通过。

### 11.2 发布包与 manifest 的增量目标

ESD 候选路线为 `2.0.0-draft.* → 2.0.0-rc.* → 2.0.0`，各次推进取决于实际批准与验收，不由本计划触发。发布包需有精确的 00–05 文档清单、语义变化/迁移说明、试点结果及未覆盖范围；文件名、正文版本、导航和相对引用以独立迁移保持一致。

在现有清单上增量绑定：

- 源 repository、commit、源树或逐文件摘要，Document ID、文档版本及套系组成。
- 相关配置、图表、模板、过滤器、锁文件摘要，以及实际工具和字体身份。
- 构建 profile、原始执行记录、输出制品摘要；区分内容源日期/可复现时间与实际构建时间。
- 候选或正式发布标识，批准记录所覆盖的内容及制品范围。

“内容可发布”与“这组最终制品可公开”可以分两步批准，但必须绑定各自对象；源、配置、制品或批准范围变化时重新确认适用性。文档不把自己的最终摘要写回自身；内容快照、构建结果与外部批准记录分别绑定，避免自引用摘要循环或沿用无关历史批准。

正式 PDF 清单可先保留 01/02 双卷；03–05 有阅读需求再安排，不要求六篇齐套出版。结构检查、视觉检查、文本复制/搜索、引用及书签按声明范围验收，未完成可访问性验证不声明 PDF/UA 合规。若后续决定升级字体/引擎，另行核对当时官方稳定版本、兼容性及支持范围，不继承历史“最新版本”数字，也不与规范语义修订捆绑。本轮不执行上述构建、升级、渲染或发布。

### 11.3 公共证据与原件保护

公开仓库仅保存获准公开的方法、样例、脱敏摘要及必要的小型证据。真实业务数据、凭据、客户标识和敏感完整日志不默认公开；使用获准的受控位置，记录保留期与访问边界。外部读者无法访问的证据不能称为公开可独立复核的证明。

来源材料先做敏感内容检查。需要脱敏时保留受控原件与其摘要，另建明确标识的脱敏副本；副本不得登记为原始字节复制。归档说明和角色放在外部资产登记，不能加入不可变原件。

## 12. 质量指标、停止条件与风险应对

### 12.1 观察实际价值

| 维度 | 需要记录的观察 |
| --- | --- |
| 可用性 | 首次实例化所需额外解释、重复误填字段 |
| 语义一致性 | 同一输入在不同 Reviewer/工具中的分类及分歧理由 |
| 缺陷发现 | 关键反例是否检出，真实项目因此修改了什么 |
| 采用成本 | 编写、证据收集、评审和维护的实际投入 |
| 证据可复核性 | 报告能否关联实际源码、命令、原始结果及适用范围 |
| 演进成本 | 规则修订需同步多少重复定义，是否出现事实漂移 |
| 出版可靠性 | 草案误发布、历史覆盖、源/版本错绑是否被拒绝 |

不以页数、文件数、全绿比例、模式数量或模板填满率作为目标。先测量实际耗时，再定优化阈值，不预设未经测量的 CI 时长承诺。

### 12.2 暂停扩张与发布的触发条件

同一义务出现多套定义、模板成本超过决策价值、没有原始证据却提升验证标签、为迁就案例反复新增无收益的持久状态、预览污染发布，或自动化无法解释状态来源时，先登记问题并修复边界、去重、缩小范围或暂停相应发布；不以增加上位文档替代处置。这些条件是后续工作的控制建议，不是本次已完成的验收结果。

### 12.3 主要风险与应对

| 风险 | 拟采取的应对 |
| --- | --- |
| 同名同版本对应不同内容 | 保存来源字节摘要与差异；只保留一个当前维护入口，历史来源单独标识 |
| 历史验证无法关联源码 | 保持待核验，必要时新建运行记录，不追认历史 PASS |
| 过拟合 CAN 案例 | 用有界工程流程作对照，区分通用要求与实例边界 |
| 规范引入过多基础设施 | 比较最小方案，说明新增权威状态的价值、成本和恢复责任 |
| 重复审批及权力层级 | 复用 GOV 授权与风险匹配流程，不把每项低风险 Markdown 编辑设成新审批层 |
| 出版工具挤占采用建设 | 先控制发布风险；完整重设计另行决定，内容与视觉分别验收 |
| 公共仓库泄露业务信息 | 公开最小必要证据；脱敏副本和受控原件分别标识 |
| 语言 Profile 退化为风格指南 | 每项建议关联性质、机制、剩余风险、成本与验证 |
