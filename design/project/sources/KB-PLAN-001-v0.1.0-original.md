# 工程文档项目建设与交付规划

> **项目目标：** 把已经形成的系统设计与代码设计思想，建设为能够被真实项目采用、通过具体反例检验、由代码和运行证据支持、以 Markdown 持续维护并受控发布的工程知识体系。
>
> **当前策略：** 暂缓增加宏观规范；先完成资产接收、草案与发布隔离、最小模板和采用试点。ESD 与 ECD 分别验收，出版与自动化服务于它们，而不成为新的主项目。

## 1. 规划边界与决策摘要

本计划以 `a67fb25` 为仓库事实快照，以历史讨论中的明确决策为约束。它不把历史助手的完成报告自动转换为当前仓库的验证结论。[S1][H1]

建议采纳以下建设方向：

| 决策 | 本项目采用方式 |
|---|---|
| 核心规模 | 保留 ESD 00–05 六篇的职责分工，不因每次发现问题增加一篇上位规范 |
| 下一主任务 | 从内容扩写转向采用、反例验证和规范维护 |
| ECD 顺序 | 接收并核验证据 → VS-003 → 性能与跨语言抽查 → 方法/参考 → 模式提炼 → 语言 Profile |
| 推进模型 | Phase 管工作范围，Milestone 记录达成，Gate 评价条件；事实、授权、执行结果分离 |
| 实施裁剪 | 采用 Core Spec / Profile / Instance 思路，不要求每个语义对象对应一个文件 |
| 正文权威 | 规范、方法、人工论证以 Markdown 为权威；代码、原始数据和执行日志保持原生事实来源 |
| 出版关系 | LaTeX 是出版层，PDF 是某个不可变源快照的派生制品，不维护第二套正文 |
| 自动化策略 | 先结构检查，再显式规则的建议性评价，最后才考虑经验证、经授权的限定阻断 |
| 发布范围 | ESD 发布不等待完整 C++/Rust/Zig Profile；ECD 发布不因 ESD 发布而自动通过 |
| 工作在制量 | 默认最多并行两项实质工作；同一规范语义区段避免并发修改 |

### 1.1 本期纳入

- ESD 六篇规范的维护、试点、采用记录和发布。
- 历史模板、案例、自动化草案与推进规范的接收、去重和语义映射。
- ECD 历史稿、纵向切片报告及其代码和证据的接收与复核。
- 现有 Markdown → LaTeX → PDF 工具链的预览隔离、可追踪构建和发布控制。
- 为上述资产服务的最小检查、证据索引和协作规则。

### 1.2 本期不纳入

不重构 `atlas/`、`c++/`、`zig/` 中的全部既有知识材料；不把 C++ G0/G1 教材视为完整 ECD 语言 Profile；不新建知识库网站、数据库、Agent 平台或通用工作流引擎；不批量补齐所有领域 Profile；不默认执行生产变更。

本项目不是收集所有优秀技术文章，而是建立一条可使用、可维护、可验证的工程方法链。

### 2.2 优先处理的出版风险

当前 `design/scripts/build.sh` 以两个旧版本文件名为输入，并将 PDF 直接复制到 `dist/${stem}.pdf`。正文已经是新草案，因此下一次按现有流程构建，可能覆盖历史 v1.1.0 文件，而不是产生独立草案预览。[S3]

`write-manifest.py` 当前记录 PDF 摘要和部分出版源摘要，但 Markdown 列表本身没有逐文件摘要；锁文件仅列出名称。新发布需要扩展为明确的源内容、工具链和批准范围绑定，而不能只记录文件名。[S4]

**优先处置：** 在下一次构建当前草案之前，隔离预览与发布路径；历史 `dist/` 文件不因普通构建改变。该项是下一工作包，不是本次已经实施的修改。

## 3. 项目产品结构：小型规范核心，加实际使用闭环

```text
ESD：系统设计、治理、证据与运行要求
  │
  ├─ 模板 / 采用剖面：把适用要求变成可填写、可审阅的输入
  │     └─ 真实项目实例：事实、选择、缺口、证据与裁决
  │
  └─ ECD：系统性质向代码结构和实现验证的精化
        ├─ 可构建的纵向切片
        ├─ 问题与设计力驱动的模式
        └─ C++23 / Rust / Zig 的机制与保证映射

共同支撑：推进记录、结构检查、证据索引、受控出版
共同反馈：试点歧义、反例、实现缺陷、运行经验 → 修订方法与要求
```

### 3.1 六篇 ESD 的职责保持不变

00 负责套系组成、版本与主题权威；01 负责方法与核心概念；02 负责默认工作流、模板和案例；03 负责风险、角色、授权与符合性；04 负责论证、证据与支持状态；05 负责生产就绪与运行韧性。项目计划只引用这些边界，不再定义平行的治理状态机。[S2]

### 3.2 历史推进规范的处理

保留 `ESD-PROCESS-001` 中 Phase / Milestone / Gate、Core / Profile / Instance、证据绑定和授权分离的价值。先做兼容性对照，识别它与 GOV、ASSURANCE 的同义、补充和冲突部分。[H2]

本期仅把必要的推进规则作为本项目的轻量执行约定：不直接导入全部字段，不增加第二套 Gate 权威，不要求低风险 Markdown 修改重复批准。后续只有实际跨项目复用需要成立时，才决定将它正式纳入配套标准还是合并到现有规范。

### 3.3 模板、案例、Profile 的区别

| 类别 | 责任 | 不应承担 |
|---|---|---|
| 规范 | 定义义务、术语和适用边界 | 保存某个项目的实时进度 |
| 模板 | 帮助项目表达规范要求 | 偷偷增加强制义务 |
| 采用 Profile | 在授权范围内定义适用要求和控制深度 | 以轻量名义取消关键事实与责任 |
| 项目实例 | 记录当前系统的事实、选择和证据 | 重新定义全局规范 |
| 参考案例 | 展示推导、反例和边界 | 冒充已经验证的生产系统 |
| 自动化 | 检查已表达且已编码的属性 | 从目录完整或 CI 绿色推导整体 GO |
| 出版层 | 生成可追踪、可读的发布视图 | 修改正文语义或发布状态 |

## 4. 推进、角色与版本约定

### 4.1 不再混用阶段、里程碑和门禁

本项目使用 `KB-` 命名空间，避免与 ESD Gate 0–9、ECD Gate M1、C++ G1/G2 混淆。

- **Phase / `KB-Pn`**：一组有共同目的的工作。
- **Milestone / `KB-Mn`**：对应成果已经达到验收条件的事件。
- **Gate / `KB-Gn`**：评价该成果是否达到退出条件的规则。

任务完成、评审通过、发布批准和实际发布分别记录。本文中的阶段表是计划，不是已经执行的验收记录。

### 4.2 角色

建议 Elliott Bai 担任项目 Owner 和范围决策人。Codex 负责获准范围内的修改、脚本、原型和执行记录；本对话中的评审作为辅助复核。需要独立人类审查的高风险活动仍按 GOV 落实，不能把多个 Agent 会话等同于组织独立性。

规划获采纳后，机械检查和已授权的低风险修改可走简化流程。规范强制语义、证据判定、批准权限、历史制品或生产对象的变更应单独审阅。

### 4.3 版本独立

ESD 草案继续沿 `2.0.0-*` 演进；ECD 保留自己的候选版本；本项目计划使用 `KB-PLAN-001 v0.x`；出版工具和规则 Schema 另记版本。不得仅因为同处一个仓库就统一升版。

正式发布按不可变源快照和精确文档清单冻结。旧文件名过渡已有说明，本期不进行全面重命名；正式发布时以单独、可审阅的迁移完成路径、导航与导出一致性。[S2]

### 6.3 默认构建只生成预览

建议在现有出版工具上增量调整，不替换技术路线：

```text
普通构建 → design/build/preview/<source-snapshot>/
候选构建 → design/build/candidate/<source-snapshot>/
显式发布 → 经批准的 design/dist/ 下新版本目录
```

最低合同：普通 build/check/render 不修改受版本控制的 `dist/`；草案 PDF 显示准确的草案版本和状态；发布操作只接收明确源快照、内容清单与批准记录；不得静默覆盖已发布版本；新制品产生后再验证其摘要。

增加负向场景：草案路径、缺失批准、版本与源内容不匹配、目标文件已存在且摘要不同，均不得被普通命令自动当作正式发布。历史 v1.1.0 保持原样。[S3]

### KB-G0

## 7. KB-P1：最小模板与检查，不整包复制十九份

### 7.1 首批模板

先从历史资产中提取六种高频模板，其他登记表嵌入 dossier 或通过引用复用：

| 模板 | 最小作用 |
|---|---|
| `decision-brief.md` | 一页说明要决定什么、为什么、主要替代、风险与证据入口 |
| `design-dossier.md` | 约束、假设、性质、状态、边界、失败、资源与运维的完整记录 |
| `assurance-case.md` | Claim、Argument、Evidence、反证、未知与覆盖范围 |
| `decision-record.md` | 要求事实、例外授权、对象符合性与 Gate 决定分层记录 |
| `exception-record.md` | 范围、权限、期限、补偿、停止条件与退出路径 |
| `runbook.md` | 可执行操作、前置、安全边界、验证与恢复 |

这些是项目使用视图，不要求每个小项目维护六个文件。小实例可以在一份 Markdown 中用稳定区段表达多个记录。采用矩阵依 GOV 的实际前提推导，避免把模板全部必填当作符合性。

字段定义引用上位规范；不手写第二套 Evidence 或 Assumption 枚举。无法直接复用的历史模板明确记录迁移，不以“内容相似”绕过语义校准。

### 7.2 首批规则反例

至少包含：

- Claim 已被反证但 Exception 获批，事实仍保留为反证。
- 非阻断 MUST 不满足，仍不能被汇总为完全符合。
- 已知不满足与未知同时存在，总状态不隐藏任一明细。
- 例外过期、越权、范围不匹配或条件不可执行，不提供有效覆盖。
- Requirement ID 存在但理由/证据不相关，不能通过语义检查。
- 假设已监测但未验证，不转换为已验证。
- 未运行、工具错误和旧证据不转换为新执行 PASS。
- 构建成功和 PDF 美观不构成系统或代码性质验证。

先保存输入、预期结果、理由和权威条款，称为“规则反例/预期 Oracle”。后来真的执行了校验器，再另记执行记录，不能把设计用例本身算作测试通过。

### 7.3 结构检查范围

首批仅编码可靠的机械属性：Front Matter 解析、身份/版本字段、声明的相对链接、重复 ID、代码围栏、文档类型、源与发布视图映射、候选规则的枚举一致性。

要求语义是否充分、Reviewer 是否具有实质独立性、外部恢复能力是否成立，仍属于人工和项目证据评价范围。Schema 通过只能证明其已编码子集符合。

### KB-G1

让一位未参与撰写的人，或经明确标注的作者自演练，在不口头补充规则的条件下完成一个实例；记录歧义而不是当场偷偷改模板。六个模板和首批反例可以引用到当前权威来源，结构检查既能接受合法样例，也能拒绝目标错误样例。

## 8. KB-P2：两个采用试点

### 8.1 试点 A：有界工程流程 / R1 候选

优先候选是 `kb` 自身的文档构建与发布流程；实际风险等级仍按 GOV 判定，不因名字叫文档而自动认定低风险。

它可用于验证：源快照绑定、草案/正式产物隔离、版本身份、错误输出、权限、历史制品保护和复原。若它不是持续服务，则不机械要求 24 小时 on-call 或复制业务服务 SLO；使用和交付风险仍应被明确处理。

最小场景：缺失字体、损坏链接、修改源文件后复用旧 manifest、未批准的草案尝试发布、预览覆盖历史 PDF、半完成发布、制品摘要不匹配。每项场景定义可观察结果与恢复步骤。

### 8.2 试点 B：数据处理系统 / R2 候选

使用已经讨论的 CAN 对象文件处理场景，优先基于获准访问的真实实现快照。是否采用某个历史项目或仓库，由实际可用代码、数据脱敏和授权决定；规划不假定外部项目当前状态。

试点至少走通一条：

```text
源身份 → 处理语义 → 接纳/所有权 → 结果提交 → 交付位置 → 崩溃恢复
```

覆盖未知提交、重复/乱序完成、分区移交、资源耗尽、依赖降速与责任接收方重启。资源和语义边界优先于极限吞吐优化。

**不预设必须增加 manifest store 或责任 ledger。**若真实项目输出到 Kafka，必须按实际输出和提交边界设计；不能把说明性对象存储案例直接移植成生产架构。每个新增持久状态都要说明原系统为何不足、它负责什么、如何恢复及其维护成本。

可先做离线审阅与沙箱故障演练，不要求为了验证文档而开放生产权限。没有真实生产演练时，结论只能覆盖对应的评审和非生产范围。

### 8.3 试点交付

每个试点仅保留：一份带真实版本的 dossier、一份保证与决策记录、一份采用反馈，以及原始证据引用。模板字段可以复用，不复制同一事实到多个登记表。

采用反馈重点记录：读者在哪些词上需要额外解释；哪些关键问题被模板发现；哪些字段重复或没有决策价值；证据收集和复审付出了什么成本；哪些规则产生误判；发现后修改了何种机制或要求。

### KB-G2

两个实例完成范围明确的评估与反馈；重要歧义有修订或明确限制；核心状态规则面对相同输入能给出一致结论；产出真实证据与预期 Oracle 明确分开。

试点系统得到 `NO_GO` 不等于规范试点失败。规范若准确识别关键缺口并形成可执行修复，可能正体现其价值。反之，所有表格绿色但未发现故意植入的关键缺陷，不能视为成功。

## 9. KB-P3：ESD 发布候选与正式发布

先根据试点反馈修订，不为了发布凑足页数或消灭全部普通未知。发布前需要关闭规范自身的阻断性矛盾，保留适用限制和未覆盖范围。

建议发布节奏为：`2.0.0-draft.* → 2.0.0-rc.* → 2.0.0`，其中每次推进由真实批准和验收记录决定，不由日期或本规划自动触发。

### 9.1 发布包

- 精确的 00–05 Markdown 文档清单及摘要。
- 相对于前版的语义变化和迁移说明，尤其是状态字段与例外模型。
- 试点范围、结果、尚未覆盖事项与批准记录。
- 文档 ID、正文版本、文件名和相对链接的一致迁移。
- 实际发布 PDF 的精确清单、源快照、工具链与摘要；不要求六篇都必须有 PDF。

首个正式 PDF 发布仍可维持 01/02 双卷。03–05 的独立出版只有在有明确阅读需求时安排，避免为了齐套重复投入排版工作。

### 9.2 出版设计维持历史批准方向

沿用 A4、数字阅读优先、软垂直节奏、ragged bottom、章节起始页承载正文、长表格/代码/Callout 的跨页契约。保留方法论连续阅读和参考手册查询阅读的区别，不重新寻找模板推翻现有设计。[H4]

不得用整页缩放、极小字号、负间距或滥用横置隐藏内容结构问题。规范性编号、代码与表格文本、交叉引用、复制搜索和书签，与视觉质量共同验收。

工具链升级单独处理：实施时核对官方稳定版本、兼容性与支持范围，再锁定已验证组合；不直接继承历史回答中的“最新版本”数字。语义修订不与整套字体/引擎升级混在同一个发布变更中。

未完成实际可访问性验证，不声明 PDF/UA 合规。当前只规划该边界，不生成或审查 PDF。[S2]

### KB-G3

批准范围与发布对象相符；所有列出的制品都能追溯源快照；普通构建不能覆盖历史版本；新文件名与元数据一致；结构与视觉问题完成声明范围内的检查；发布记录清楚标明哪些篇章有 PDF、哪些只有 Markdown。

## 10. KB-P4：ECD 接收、证据复核与第三切片

### 10.1 先继承设计，不直接继承验证资格

历史方法稿明确采用“方法主导、语言早期验证、模式后置、Profile 固化”，并把 VS-003、性能检验及跨语言抽查列为后续条件。[H1][H3]

接收 VS-001/002 时，逐项核对：

```text
报告中的源身份
→ 可获取的完整源码和构建依赖
→ 编译器、平台与命令
→ 原始测试/变异/并发日志
→ 结果所覆盖的性质与限制
→ 本项目是否能复用或需要重新执行
```

如果只找到 Markdown 报告和 README，没有对应源或原始结果，则记为“历史报告已接收，证据待复核”。不声明此前测试虚假，也不把报告重命名后算作本轮通过。若需要重建原型，使用新的源对象和执行记录，不追认成原历史运行。

源码正确性、Sanitizer、变异测试和 benchmark 分别评价。一次工具缺失只影响对应证据，不能被隐藏为 PASS，也不必把所有无关已核验设计全部作废。

### 10.2 VS-003：错误、取消、Deadline 与资源责任

以真实编译代码推进第三互补切片，重点包括：

- `expected/Result` 返回与潜在异常源之间的完整边界。
- 回调、分配、future/promise 或外部调用失败后，不遗留永不完成任务。
- 取消请求、计算结束、责任释放和可观察完成的区别。
- 协作式取消的检查点和最长不可中断单元。
- Deadline 与重试权威、重试预算的组合。
- 先准入后分配、等待中的生产者与结果持有者的数量约束。
- workspace 唯一配置权威、输出暂态重叠的记账。
- 可恢复的部分进度、隔离与运行模式。

它继承前两切片已经澄清的身份、未决副作用、view 生命周期与 settlement 边界，而不是再造一个完整数据处理系统。

### 10.3 性能验证与跨语言抽查

至少用一个代表目标访问模式的工作负载检验数据表示假设。预先定义输入、比较基线、指标、重复策略、噪声来源和决策阈值；结果可以推翻原偏好。Synthetic microbenchmark 只能支持其本身的结论，不能自动成为真实 CAN 生产性能证据。

选择同一核心合同用 Rust 或 Zig 做一个小切片，比较语言能保证什么、需要什么运行机制、有哪些无法静态排除的风险。不要同时重写完整三套引擎。

### KB-G4

至少三个互补切片形成可获取、可构建、可核验的证据；至少一项性能假设获得有范围的实测结论；至少一次跨语言映射抽查完成；关键方法修订可追踪到发现它的问题；未解决的生产边界显式保留。

达到该门禁可以支持 ECD 方法候选的批准讨论，不自动授予任何参考原型生产资格。

## 11. KB-P5：参考、模式与语言 Profile

### 11.1 ECD Reference

从真实切片提炼项目执行流程、代码评审问题和最小记录，不再重复一篇方法哲学。以“系统性质如何落到代码机制和证据”为主线，避免把所有类型、接口和函数都要求追踪到规范编号。

只对关键性质及其高后果实现边界建立明确追踪；普通局部代码使用惯常测试与评审，保持实现成本可控。

### 11.2 模式目录先小后大

首批只接收已经在切片中出现的模式：稳定身份、验证后构造、owner-bearing view、受限提交接口、有界执行器、settlement boundary、未知副作用对账、准入与责任许可。

每个条目说明问题、设计力、保护性质、所有权、失败方式、成本、替代方案、不适用条件和验证方式。只有一个实例时标为案例级候选，不把它称为普遍最佳实践。

传统 OOP/GoF 模式按实际变化轴补入。DOD 以访问模式和测量为依据，不设“全面改成 SoA”之类预先答案。

### 11.3 C++23 Profile

正式 Profile 至少包括：

```text
通用设计要求
→ C++23 可用表达
→ 编译器实际保证
→ 工具辅助检查
→ 仍需运行时/协议/人工维持的性质
→ 表达、编译、运行及维护成本
→ 验证与证据
```

House Style、格式化和命名只是附属规则，不替代上述设计映射。代码示例应来自可构建源文件或受检查的代码片段，避免正文例子和实现分别演进。

### KB-G5

Reference 可以驱动一个新实例；模式条目有真实问题来源和反例；C++ Profile 能指出保证的缺口，而不只是推荐标准库类型；与 ESD 对同一事实、权限和恢复责任的解释一致。

## 12. KB-P6：持续维护与按需扩展

Rust/Zig Profile 在共同模型下扩展；流处理、控制面、AI/Agent、实时/机器人等领域只在至少一个实际采用场景提出独有义务时新增。

不把“未来可能用到”作为新建长文档的充分理由。维护审查的重点是重复例外、失效证据、模板歧义、失去价值的规则和运行反馈，而不是不断增加检查数量。

复杂自动化在显式规则和反例稳定后逐步引入。建议性工具可以比强制门禁更早使用；自动化失败不应默认为事实通过，也不应自动夺取超出授权的发布权。

## 13. 出版与自动化工作流

### 13.1 四层检查

| 检查层 | 首次引入 | 检查什么 | 不代表什么 |
|---|---|---|---|
| 结构层 | P1 | 解析、ID、声明字段、链接、枚举及文件关系 | 不代表协议正确 |
| 规范规则层 | P1/P2 | 明确规则的合法/非法样例、状态迁移与汇总 | 不代表输入事实真实 |
| 实现验证层 | P2/P4 | 编译、测试、fault、Sanitizer、benchmark | 不代表未覆盖环境或生产资格 |
| 出版层 | P0/P3 | 源绑定、字体、引用、分页、文本、摘要和批准范围 | 不代表业务系统已经符合标准 |

CI 按变更影响执行相关层：文档链接变更不强制跑所有 C++ 压力测试；工具/模板/枚举变更需要对应回归；代码/协议变化触发切片验证；出版引擎变化触发排版试件和完整渲染。

### 13.2 Manifest 增量目标

在现有脚本上增加，不另建大型供应链平台：[S4]

```text
源 repository + commit + source tree/逐文件摘要
Document ID + document version + suite composition
相关配置、图表、模板、filter 与 lock 摘要
实际工具和字体版本/身份
构建 profile 与原始执行记录引用
输出 PDF 摘要
内容源日期/可复现时间与实际构建时间的区分
候选或正式发布标识
批准记录对内容/制品范围的绑定
```

批准“内容可发布”与最终批准“这组构建制品可以公开”可以是两步，必须标清对象，避免自引用摘要循环。若批准对象或构建内容变化，应重新确认适用性，不允许沿用无关的历史批准。

### 13.3 原始证据与公共仓库

`kb` 公开维护方法、样例、脱敏摘要和必要的小型证据。真实业务数据、凭据、客户标识和敏感完整日志不默认公开；使用获准位置和受控引用，注明保留期及访问边界。不可访问的证据不能被当作外部读者可独立复核的公开证明。

## 17. 质量指标、停止条件与复杂度预算

### 17.1 看什么

| 维度 | 有价值的观察 |
|---|---|
| 可用性 | 首次实例化需要多少额外解释，哪些字段反复被误填 |
| 语义一致性 | 同一输入在不同评审者/工具中是否得到相同分类 |
| 缺陷发现 | 关键反例能否被发现，真实项目因此修复了什么 |
| 采用成本 | 编写、收集证据、审阅与维护的实际投入 |
| 证据可复核性 | 报告能否指向实际源码、命令、原始输出和范围 |
| 演进成本 | 一次规则修订需要同步多少重复定义 |
| 出版可靠性 | 草案误发布、旧制品覆盖、源/版本错绑能否被拒绝 |

不以页数、文件数、全绿比例、模式数量、模板完成率作为主目标。具体耗时先记录实际基线，再决定优化阈值，不预设未经测量的 CI 时间承诺。

### 17.2 应暂停扩张的情况

同一义务出现多套定义；模板维护成本大于实际决策价值；没有原始证据却不断提升验证标签；为通过案例而反复新增持久状态但无运行收益；预览可能污染正式发布；自动化无法解释状态来源。

出现这些情况时，优先修复边界、删除重复、缩小范围或暂停发布，不继续增加上位文档。

### 17.3 主要风险及应对

| 风险 | 应对 |
|---|---|
| 历史多版本同名、同版本不同内容 | 源摘要与差异接收，单一当前入口，保留历史 |
| 历史测试声明无法关联源码 | 待核验而非自动通过；必要时重新执行并产生新证据 |
| 过拟合 CAN 场景 | 使用 R1 有界流程作为对照，明确案例与通用规则边界 |
| 规范产生过多新基础设施 | 比较最小方案，证明每个新增权威状态的价值 |
| 反复新增审批 | 采用现有 GOV 授权，低风险修改简化，不复制权力层级 |
| 出版工具压过正文采用 | 先隔离发布风险，版式大改延期，内容/视觉分别验收 |
| 公共仓库泄露真实业务信息 | 使用脱敏数据、最小公开证据和受控访问引用 |
| 语言 Profile 退化为风格指南 | 每条规则连接性质、机制、剩余风险和验证 |

## 18. 本计划的交付判据

本计划只有被明确采纳后才成为执行路线。它不自动修改 ESD/ECD 版本、Gate 状态、发布资格或仓库权限。

短期成果是：范围清楚、资产可定位、草案不会覆盖历史发布、最小模板能够使用、两个试点产生真实反馈。

中期成果是：ESD 形成有采用依据的正式发布；ECD 的历史证据可复核，第三切片完成，方法、参考和首个语言 Profile 能被新项目使用。

长期成果是：新规则来自真实反例和运行反馈，过期规则可以退役，代码、文档与证据能一起演进，而不是留下越来越多互相重复的“最终版”。

```text

```
