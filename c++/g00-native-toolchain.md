## 1. 从三个文件理解分离编译

### 1.1 问题：编译器没看到函数体，凭什么生成调用？

普通、非模板函数的声明 `int add(int, int);` 足够让当前翻译单元（translation unit，TU）检查调用的参数和结果类型。编译器按照目标应用二进制接口（application binary interface，ABI）约定生成调用所需信息，把尚未解决的符号交给链接阶段。它不需要此刻读到另一个 `.cpp` 的函数体。

例如，把声明放入 `math.hpp`，实现放入 `math.cpp`，调用放入 `main.cpp`：

```text
main.cpp + math.hpp → main.o ─┐
                             ├→ linker → executable → loader → process
math.cpp + math.hpp → math.o ─┘
```

这是传统头文件模型，不是 Modules 的完整说明。`#include` 是文本包含；预处理结果组成翻译单元（TU）。编译每个 TU 时，不能假定编译器天然掌握其他 TU 的定义。

### 1.2 为什么实现文件也包含自己的头文件？

如果调用方手写一份声明，实现方又写另一份，二者可能不一致。让 `math.cpp` 也包含 `math.hpp`，能让同一 TU 内的声明与定义接受类型检查。头文件提供共同声明，**不是保证 ABI 永不变化的证书**。

声明描述实体；定义完成相应实体的定义。不要把“定义”机械理解成“一定生成一段机器码”：内联、常量求值、优化和未使用代码都可能影响实际工件。模板、inline 函数以及完整类型的需求也不能套用“只见声明就够”的普通函数例子。

### 1.3 编译器驱动器在调度什么？

`clang++` 是驱动器，不只是语法检查器。常用停止点如下；具体后端是否分成独立进程由实现决定。

| 命令选项 | 到哪一步 | 你可以检查什么 |
| --- | --- | --- |
| `-E` | 预处理 | 头文件是否找到、宏展开 |
| `-S` | 生成汇编 | 目标指令与调用约定 |
| `-c` | 生成目标文件 | 定义/未定义符号、重定位 |
| 不指定上述停止选项 | 通常继续链接 | 是否把需要的目标文件和库交给链接器 |
| 执行生成文件 | 加载并运行 | 动态库依赖、运行时行为 |

## 2. 实验 G0-L1：缺少的定义在哪里

**先预测：**只编译 `main.cpp` 能成功吗？只链接 `main.o` 呢？加上 `math.o` 后应输出什么？

下面三个文件是完整实验。执行器分别编译两个 TU，先验证缺失 `add` 定义的链接失败，再链接完整程序；只有失败诊断对应缺失符号、完整程序返回 0 且输出精确匹配，才算通过。

<!-- g-lab {"id":"G0-L1","mode":"link","stdout":"sum=7\n","diagnostic":"(?:undefined|Undefined)[\\s\\S]*add"} -->
[完整实验 · G0-L1 · math.hpp]

<!-- g-file {"path":"math.hpp"} -->
```cpp
#pragma once
int add(int a, int b);
```

[完整实验 · G0-L1 · math.cpp]

<!-- g-file {"path":"math.cpp"} -->
```cpp
#include "math.hpp"
int add(int a, int b) { return a + b; }
```

[完整实验 · G0-L1 · main.cpp]

<!-- g-file {"path":"main.cpp"} -->
```cpp
#include "math.hpp"
#include <iostream>

int main() {
    const int result = add(3, 4);
    if (result != 7) return 1;
    std::cout << "sum=" << result << '\n';
}
```

手动练习时，把上面代码保存到一个新的实验目录，在该目录执行：

```sh
clang++ -std=c++23 -E main.cpp -o main.ii
clang++ -std=c++23 -c main.cpp -o main.o
clang++ -std=c++23 -c math.cpp -o math.o
nm -C main.o
clang++ main.o -o missing-definition
clang++ main.o math.o -o demo
./demo
```

其中 `missing-definition` 的链接失败是预期反例，其他命令不应因此被解释成失败；不要用 `&&` 把预期失败后的正例跳过。自动执行方式见[实验说明](learning/README.md)。

**应该看到什么：**`main.o` 使用了 `add` 但没有定义它；在常见 `nm` 输出中它标为 `U`。这对目标文件合法，对当前缺少定义的最终链接不成立。补上 `math.o` 后输出 `sum=7`。符号装饰和报错排版随平台变化，测试不绑定整段诊断文本。

**改变条件：**把头文件声明改成 `long add(int, int);`，保留实现中的 `int` 并重新编译实现。此时应在编译阶段发现冲突，而不必等链接。这个改动是手动练习，不在 G0-L1 的固定判据内。

**边界：**链接成功只说明本次符号与链接要求得到满足，不证明函数语义正确、运行时依赖可用或所有 ABI 合同一致。

## 3. 五层诊断：先找失败的阶段

| 现象 | 阶段 | 首先检查 |
| --- | --- | --- |
| 找不到 `math.hpp` | 预处理 | 文件位置、include 路径、大小写 |
| 参数类型不匹配 | 编译 | 当前 TU 看见的声明与表达式 |
| Undefined / Duplicate symbol | 链接 | 缺失定义、重复定义、参与链接的工件 |
| `Library not loaded: @rpath/…` | 加载 | 动态库位置、依赖记录、运行路径 |
| 错误结果、异常、越界 | 运行 | 输入、状态、生命周期和工具报告 |

“编译报错”可以口语化，但排查时必须落到具体阶段。构建日志中的最后一行不一定是根因；先找第一条有意义的诊断，再检查实际执行命令。

构建系统（CMake、Ninja、Make 等）管理的是输入到工件的依赖关系和执行规则。它们不能消除 C++ 的 TU、单一定义规则（One Definition Rule，ODR）和 ABI 要求；缓存了错误配置，照样可能稳定地产生错误工件。

## 4. 目标文件、库与加载器

### 4.1 三种 Object 不要混淆

`int x = 42;` 中的 object 是语言实体；`main.o` 是目标文件；object code 是机器代码。目标文件通常还包含节、符号表、重定位、常量和调试信息，不是裸指令串。

常见格式是 macOS 的 Mach-O、Linux 的 ELF、Windows 目标文件的 COFF 与可执行镜像的 PE。Mach-O 的 `__text` 等 section 组织细粒度内容；segment 用于更大的映射布局与权限组织。不要把一个平台的节名、权限细节当作通用语言规定。

### 4.2 符号和重定位解决什么？

未定义符号记录“我使用了哪个实体”；重定位记录“某处编码需要根据最终布局或符号绑定修补”。常规链接可能解决一部分，动态加载还可能处理剩余绑定；不是所有地址都在一次静态链接中固定下来。

C++ name mangling 支持在二进制层区分重载等实体。Itanium C++ ABI 中 `add(int,int)` 的编码示例为 `_Z3addii`；Mach-O 显示时还可能带平台前缀。不要手写猜测导出符号，使用工具查看并 demangle。

### 4.3 静态库和动态库的差异

| 工件 | 内容与通常行为 | 最容易误判的点 |
| --- | --- | --- |
| `.a` 静态库 | 一组目标文件归档，通常按未解析符号需要抽取成员 | 不是把所有成员机械复制；整包加载等选项会改变抽取策略 |
| `.dylib` / `.so` | 独立镜像，可执行文件记录动态依赖，加载器映射和绑定 | 构建时找到库，不代表部署时还能找到 |
| 可执行文件 | 连接后的程序镜像及相关依赖信息 | 磁盘文件还不是正在运行的进程 |

已经静态链接进去的那部分代码不在运行时依赖原 `.a` 文件；这不意味着整个程序从此没有任何动态库或数据文件依赖。macOS 的 `@rpath` 是运行时路径机制，具体部署问题留到 G9。

## 5. API、ABI 与跨语言边界

应用编程接口（application programming interface，API）决定源码如何调用；ABI 决定独立编译的机器码怎样协同，包括调用约定、数据布局、符号与语言运行时规则。重新编译后源码仍可用，不等于旧二进制还能使用新库。

例如下面是**布局观察片段，不是跨平台常量**：

[机制片段 · 不承诺独立编译]

```cpp
struct Packet {
    char tag;
    int value;
    short code;
};
// 可用 sizeof(Packet)、alignof(Packet)、offsetof(Packet, value) 观察。
```

常见 Apple ARM64 配置会给出大小 12、对齐 4，成员间及末尾有 padding；标准没有要求所有 C++ 平台都如此。重排字段改变偏移，旧客户端按旧布局读取就可能出错。

Apple ARM64 的简单整数/指针参数常使用 x0～x7（32 位视图为 w0～w7），浮点参数常使用 v0～v7；简单结果常从 x0 或 v0 返回。聚合、间接返回、可变参数等有专门规则，**不能用这两行速记实现完整 FFI**。详见 [Apple ARM64 ABI 说明](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)。

`extern "C"` 指定语言链接，常见工具链据此采用 C 的符号约定；它不会把函数体变成 C，也不会自动转换异常。常用边界形状是 opaque handle：

[反例片段 · 依邻近说明判定失效条件；不要用于生产代码]

```cpp
// 接口形状示意：实际头文件还需处理 C/C++ 兼容声明和错误合同。
struct engine_handle;
extern "C" engine_handle* engine_create() noexcept;
extern "C" void engine_destroy(engine_handle*) noexcept;
```

由创建方提供匹配销毁函数，可以隐藏布局及分配器细节。要求是遵守同一资源协议，不混用不兼容的运行时分配/释放机制。`noexcept` 不是错误转换器：异常逃出会终止程序；实现必须另外设计捕获、错误表示及失败时的后备策略。参见 [FM-8 边界](failure-model/fm8-failure-boundaries.md)。

## 6. 进程、栈与寄存器

### 6.1 局部变量一定在栈上吗？

不是。automatic storage duration 是语言概念；寄存器、栈槽或完全消除是实现选择。as-if 规则约束可观察行为，不要求每个源码变量对应一个物理栈地址。

程序是工件；进程是运行实例，涉及虚拟地址空间、线程、句柄等状态。每次普通嵌套调用通常有相应调用状态，但内联、尾调用和优化会改变观察到的栈形状。

### 6.2 ARM64 回查卡

| 名称 | 作用 | 不要推出的结论 |
| --- | --- | --- |
| SP | 栈指针；使用时须遵守 ABI 对齐约束 | 栈上每个源码变量都有独立槽 |
| x30 / LR | `BL` 写入返回地址；`RET` 常用它返回 | 所有函数都用同样序言保存 LR |
| x29 / FP | 帧指针约定，辅助栈回溯 | 所有优化后函数都保留完整链 |
| x19～x28 | 通用被调用者保存寄存器 | 任意调用都不会改变其他寄存器 |
| x0～x7、x9～x15 | 参数/临时寄存器中的常用部分 | 这是完整的 ARM64 寄存器分配合同 |

caller-saved 意味着调用方若需跨调用保留值，要按约定安排保存；callee-saved 意味着被调用方改变它后须恢复。寄存器不足等原因可导致 spill。叶函数可能不建立普通栈帧；非叶函数需要以 ABI 合法方式保留后续返回所需状态，不能据源码猜固定指令序列。

深递归可能耗尽栈，但是否优化、栈大小、故障表现都依赖实现，不能承诺某个递归次数必报某条 macOS 错误。

### 6.3 为什么旧栈字节不代表旧对象仍存在？

[反例片段 · 依邻近说明判定失效条件；不要用于生产代码]

```cpp
// 错误接口片段：禁止通过返回结果读取 x。
int* bad() {
    int x = 42;
    return &x;
}
```

返回后看到旧 bits，既不能延长 `x` 的生命周期，也不能使后续读取合法。这正是下一章要区分的“存储迹象”与“对象语义”。

<a id="g0-section-8"></a>

## 8. Final Gate · 参考答案与常见误判

1. 预处理得到 TU，编译/汇编形成目标文件，链接形成镜像，加载后运行。反例败在链接，不是语法或类型检查；常见误判是把所有非零退出码叫“编译失败”。
2. 声明足够检查本次普通调用并按 ABI 生成调用信息，定义由其他工件提供。常见误判是把此结论推广给所有模板和 inline 用法。
3. 符号说明实体的定义/使用，重定位说明布局或绑定确定后哪里需要修补。它们相关但不是同一张“函数地址表”。
4. 只能推出被静态纳入的内容不再需要原归档。动态库、配置和数据仍可有依赖；删库试验不是完整部署验证。
5. 新源码可按新偏移重新编译，旧二进制仍按旧偏移访问。常见误判是用“能重新编译”证明“二进制兼容”。
6. LR 保存返回地址，FP 遵守帧指针约定；优化、寄存器分配、spill 和调用约定共同影响栈。常见误判是源码一行对应一个栈槽。
7. 不能。对象已结束生命周期，旧 bits 不是合法读取凭证。没崩溃也不是 UB 的反证。

**完成标准：**不看答案复现缺失定义的链接失败，补齐后运行成功；能把每个工件的责任讲给未来的自己听。汇编细节暂时看不懂，不阻塞进入 G1。
