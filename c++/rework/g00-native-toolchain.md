# G0 从源文件到可执行程序

你修改了一个函数，编辑器没有提示语法错误，构建却报告 `Undefined symbols`。你把另一个 `.cpp` 加进构建，程序终于运行，又发现改过的逻辑似乎没有生效。这些问题很容易被归成“构建配置有问题”，但真正的原因可能分别是缺少定义、声明不一致，或者仍在链接旧目标文件。

要区分它们，需要知道一段源码在什么时候被检查，什么时候变成机器指令，以及哪些信息被推迟到后面处理。本章围绕一个只有三个文件的程序逐步展开。你不需要先了解 CMake、汇编语法或二进制格式；读完后，应当能够沿着工件找到证据，而不只是记住“预处理、编译、链接”几个阶段名。

本章采用 C++23 模式下的传统头文件与分离编译模型。命令以 macOS arm64 上的 Clang 为主；语言规则与本机输出会分别说明。它是重编新稿，不替换 v1 的历史字节；实际执行范围集中记录在[验证说明](g00-verification.md)，不让这些记录打断正文。

## 1 从一个没有函数体的调用开始

先建立一个新的实验目录，把下面三个完整文件放在同一目录。头文件声明接口，`calc.cpp` 提供实现，`main.cpp` 使用接口。本章后续实验都从这三个文件出发；不同变体请放进各自的新目录，不在上一轮输出上反复覆盖。

**文件 `calc.hpp`**

```cpp
#ifndef G0_CALC_HPP
#define G0_CALC_HPP

int add(int a, int b);

#endif
```

**文件 `calc.cpp`**

```cpp
#include "calc.hpp"

int add(int a, int b) {
    return a + b;
}
```

**文件 `main.cpp`**

```cpp
#include "calc.hpp"

int main() {
    const int answer = add(20, 22);
    return answer == 42 ? 0 : 1;
}
```

这里有意不使用输入输出库，使目标文件里需要研究的调用尽量少。程序通过退出状态报告结果：算出 42 时返回 0，否则返回 1。没有输出文字并不表示程序没有执行。输入固定为 20 和 22，不涉及整数加法溢出；我们不是在为任意整数输入设计安全算术接口。

在实验目录运行：

```sh
clang++ -std=c++23 -O0 -g -Wall -Wextra -Wpedantic -c main.cpp -o main.o
```

这一步并没有把 `calc.cpp` 交给编译器。它仍然应当成功：编译器看见了 `int add(int, int);`，便可以检查实参数量、参数类型和返回值的使用方式。它也知道目标平台约定怎样传递两个整数、怎样接收整数结果，因而能够生成一次调用所需的机器指令。

它不知道的是 `add` 的函数体，以及这次调用最终应当连接到哪段实现。因此，编译器在 `main.o` 中留下对 `add` 的未解析外部引用，而不是凭空填入一个地址。可以先把它理解为“这次调用还需要由其他工件提供实现”；后文统一用“未解析引用”描述这一关系。`main.o` 是后续链接的输入，并非一个已经可以独立执行的完整程序。

接着只拿这个目标文件去链接：

```sh
clang++ main.o -o missing-definition
```

这是本章第一个预期失败。诊断应提到未定义的 `add`，而不是找不到编译器、没有写目录权限或缺少系统 SDK。错误虽然由 `clang++` 命令报告，失败的阶段却已经是链接。

下面摘取本机实际诊断的关键部分：

```text
Undefined symbols for architecture arm64:
  "add(int, int)", referenced from:
      _main in main.o
```

第一行说明当前目标架构；第二行给出未找到的函数；第三行指出引用来自 `main.o` 中的 `main`。排查应从这次未解析引用出发，寻找对应定义。诊断最后的 `linker command failed` 只是失败汇总，真正可用于定位的信息在前面。

现在把实现也编译进去：

```sh
clang++ -std=c++23 -O0 -g -Wall -Wextra -Wpedantic -c calc.cpp -o calc.o
clang++ main.o calc.o -o demo
./demo
```

程序应正常返回 0。手工执行时，可以紧接着用 `echo $?` 查看退出状态；中间不要运行其他命令，否则查看的是其他命令的结果。预期失败的链接与后面的正确构建分开执行，不要用一条 `&&` 链让前者阻止后者。

这里已经出现了两个不同的问题：**当前文件里的调用是否合法**，以及**整个程序有没有提供所需实现**。前者不必等待所有源文件汇总，后者不能靠一个声明解决。分离编译正是利用这种边界，让不同源文件可以分别处理。

## 2 头文件究竟改变了什么

### 2.1 翻译单元不是一个目录

翻译单元（translation unit）是理解这个过程的关键。在本章使用的模型中，可以先把它理解为一个源文件经过头文件包含和预处理后，交给后续翻译阶段的内容。它不是整个项目目录，也不是文件名相似的一组文件。

执行以下命令，生成便于阅读的预处理结果：

```sh
clang++ -std=c++23 -E -P main.cpp -o main.ii
```

`-E` 让驱动器停在预处理阶段；`-P` 省略用于标识原始文件位置的行标记，便于本次观察。打开 `main.ii`，你会看见 `add` 的声明和 `main` 的定义，却不会看见 `calc.cpp` 中 `return a + b;` 的实现。`#include "calc.hpp"` 并没有触发“把同名 `.cpp` 自动加进项目”这样的行为。

同样地，`calc.cpp` 也会在自己的翻译单元里包含这份声明。这是两个独立的预处理与编译过程：一个声明可以被许多翻译单元看见，而函数的普通外部定义在这里由 `calc.cpp` 提供。

为什么两个翻译单元里的声明能够指向同一个函数？本例中 `add` 的名称具有外部链接（external linkage）：语言规则允许其他翻译单元中的相应声明指代同一实体。它与“调用外部动态库”不是一回事；本例直接链接两个目标文件，也利用了这种关系。名称的链接属性属于语言模型，链接器怎样利用符号实现连接则属于工具链层面。两者有关，但不能互相替代，详见 [C++23 名称链接规则](https://timsong-cpp.github.io/cppwp/n4950/basic.link)。

这里还要区分三层：**C++ 名称的链接属性、目标文件的符号及其可见性、共享库最终导出的接口**。具有外部链接，不意味着每种优化后的目标文件都必须保留一个相同的全局符号，更不保证最终共享库向使用者导出它。符号生成、优化和二进制导出策略是后续实现环节；[Clang 对可见性的说明](https://clang.llvm.org/doxygen/Visibility_8h_source.html)也将其与语言标准的链接属性区分。G8 再展开，G0 不把这三层当作同一个概念。

```text
calc.hpp ──包含──> main.cpp ──编译──> main.o ──┐
    └──────包含──> calc.cpp ──编译──> calc.o ──┴──链接──> demo
```

图中有两种不同的依赖。编译 `main.cpp` 依赖头文件中的声明；链接 `demo` 依赖实现所在的目标文件。把 `calc.hpp` 放到正确位置，只解决了第一种依赖，不能代替把 `calc.o` 交给链接器。

### 2.2 头文件保护只在一个预处理过程中生效

`#ifndef`、`#define` 和 `#endif` 防止同一份头文件在一个翻译单元中被反复展开。例如 A 头文件和 B 头文件都包含 `calc.hpp`，第一次包含后宏已经定义，第二次便跳过其内容。

但是，两个翻译单元有各自的预处理状态；处理 `main.cpp` 时定义的这个宏，不会自动成为处理 `calc.cpp` 时的宏状态。这与实现是否使用两个操作系统进程无关。因此“有头文件保护”与“全程序只会出现一份函数定义”是两件事。第 6 节会用一个重复定义实验把这一区别直接暴露出来。

头文件也不应被理解为“只允许放声明的文件”。类定义、模板定义、符合规则的内联函数定义，都有放在头文件里的理由。现在先建立普通函数声明与实现分离的模型，后续遇到这些类别时再分析它们为什么需要不同安排。[C++23 草案的翻译阶段](https://timsong-cpp.github.io/cppwp/n4950/lex.phases)描述的是语言层面的过程，不要求实现为每个阶段启动一个独立操作系统进程。

### 2.3 为什么实现文件也要包含接口头文件

假设 `main.cpp` 从头文件看见返回类型是 `int`，而实现者误把定义改成返回 `long`。如果两边各写各的声明，局部编译可能缺少发现冲突所需的信息。

在一个新实验目录中，保留原头文件，把 `calc.cpp` 替换成下面的完整反例：

**文件 `conflicting-return.cpp`**

```cpp
#include "calc.hpp"

long add(int a, int b) {
    return static_cast<long>(a) + b;
}
```

执行：

```sh
clang++ -std=c++23 -c conflicting-return.cpp -o conflicting-return.o
```

这是预期的编译失败，不需要等到链接。当前翻译单元同时看见参数列表相同、返回类型却冲突的声明和定义，编译器能够直接诊断。公共头文件的价值之一，就是让本来隔离的信息在该检查的位置相遇。

这不意味着包含头文件能发现所有接口漂移。把参数改成另一种类型，可能只是定义了一个新的重载，而让原来声明的函数仍然没有定义；类布局宏、编译选项与其他跨翻译单元差异也需要单独分析。共享头文件是必要的工程约束之一，不是完整 ABI 兼容性证明。

## 3 一条 clang++ 命令背后有哪些阶段

### 3.1 驱动器与实际工具

`clang++` 首先是编译器驱动器（compiler driver）：它根据输入类型和选项安排工作，必要时调用链接器，并为 C++ 程序提供适当的默认运行时链接设置。它不等于一个只做语法检查的程序。[Clang 工具链说明](https://clang.llvm.org/docs/Toolchain.html)给出了这些组成部分的关系。

本例可按下面的路径理解：

```text
源文件与头文件
  → 预处理后的内容
  → 语法与类型检查
  → 中间表示与优化
  → 目标指令及目标文件
  → 链接后的程序镜像
  → 装载并开始运行
```

这是一幅理解责任的图，不是一张进程数量表。Clang 可以使用集成汇编器直接生成目标文件，不必先把一份 `.s` 写到磁盘再调用独立汇编器。链接时优化也会使传统阶段之间的信息边界发生变化。本章暂时不启用 LTO，让分离编译的工件比较容易观察。

| 命令 | 本次停在哪里 | 该结果不能说明什么 |
| --- | --- | --- |
| `clang++ -E main.cpp` | 预处理 | 尚未证明表达式和类型合法 |
| `clang++ -fsyntax-only main.cpp` | 语法与语义检查 | 不生成可执行文件，也未解析外部定义 |
| `clang++ -S main.cpp` | 汇编文本 | 不是已经完成链接的程序 |
| `clang++ -c main.cpp` | 目标文件 | 可以仍有未定义符号 |
| `clang++ main.o calc.o -o demo` | 链接产物 | 不证明业务结果或全部运行环境正确 |

表中为突出选项省略了共同的 `-std=c++23`。手工实验继续使用前文的完整选项。阶段选项的准确含义见 [Clang 命令参考](https://clang.llvm.org/docs/CommandGuide/clang.html#stage-selection-options)。

### 3.2 观察驱动器实际准备调用什么

在已有目标文件的目录执行：

```sh
clang++ '-###' main.o calc.o -o demo
```

`-###` 打印拟执行的底层命令而不运行它们，输出通常在标准错误流。引号避免 shell 把选项里的字符解释成别的东西。观察记录中的链接器路径、目标架构、SDK 路径和库选项，比根据 `clang++` 这个名字猜测“它一定使用某个链接器”更可靠。

本机实际命令也说明了为什么需要观察：Apple Clang 选择了 Xcode 下的链接器与 SDK，Homebrew Clang 则使用 `/usr/bin/ld` 和 Command Line Tools 下的 SDK。两者的 SDK 版本字段不同，但都面向同一台 macOS arm64 主机，并链接系统运行库。两套编译器不自动等于两个独立平台；完整命令保存在验证记录中。

如果一个工程只报告“构建失败”，先找到真正执行的命令，再判断它停在哪个阶段。缺少 `calc.hpp`、声明冲突和缺少 `calc.o` 可能都出现在同一个 IDE 面板里，但修复方法完全不同。

## 4 从目标文件追踪一次调用

### 4.1 目标文件保存的不只是指令

`main.o` 中既要保存已经生成的代码，也要保存未解析的外部引用。它通常包含代码和数据所在的节、符号表、重定位记录，以及选项要求的调试信息。语言中的“对象”与这里的“目标文件”不是同一个概念；不要把 `object` 的两个用法混在一起。

本章在 macOS 上得到 Mach-O 工件；Linux 常见的是 ELF。两者都支持符号与重定位，但格式字段、工具输出和具体规则不同。我们先理解记录之间的作用，再观察本机名称，不把一种格式的输出当成 C++ 标准规定。

在 macOS 的命令行工具环境中，先运行：

```sh
nm main.o
nm calc.o
```

自动记录另外使用 LLVM 的 `llvm-nm --demangle`，把 C++ 编码名称尽量还原为便于阅读的形式。你应当能建立下面的对应关系，而不需要记住每一列地址：

| 工件 | 本例中值得关注的符号 | 含义 |
| --- | --- | --- |
| `main.o` | 定义 `main`，未定义 `add(int, int)` | 提供入口实现，并引用另一个函数 |
| `calc.o` | 定义 `add(int, int)` | 提供该外部引用所需的定义 |

常见 `nm` 输出用 `U` 表示未定义符号，用 `T` 表示代码节中的外部定义；完整标记含义应按工具及格式解释，见 [llvm-nm 文档](https://llvm.org/docs/CommandGuide/llvm-nm.html)。符号表里的数值也不能一概读成进程运行时的最终虚拟地址。

本机原始输出中，与这次调用有关的是下面三行；文件名标签是为阅读添加的，局部标签已省略：

```text
main.o:
                 U __Z3addii
0000000000000000 T _main

calc.o:
0000000000000000 T __Z3addii
```

先不要尝试背诵 `__Z3addii` 的编码。重要的是 `main.o` 记录了未解析引用，而 `calc.o` 提供对应定义。`llvm-nm --demangle` 将它显示为 `add(int, int)` 后，便能与源码对应。两个目标文件的代码符号都显示数值 0，也不是它们已经争用进程地址 0；此时还没有为整份程序完成最终布局。

### 4.2 符号与重定位记录各回答什么

只有对 `add` 的符号引用还不够。链接器还需要知道：在目标文件的哪个位置，要用什么规则把最终选中的目标编码进去。重定位（relocation）记录承担的正是这种工作。

可以把两者的关系理解为：符号给出被引用实体的身份；重定位记录指出某个位置依赖这个身份，以及应采用的修补方式。它不是简单地“把一个指针填到文件里”。某些指令编码相对位移，某些地址需要多条指令配合，动态绑定又可能引入桩或间接表项。

安装了 LLVM 工具时，可以在当前实验目录观察：

```sh
llvm-objdump --disassemble --reloc main.o
```

若工具没有加入 PATH，本机 Homebrew 路径是 `/opt/homebrew/opt/llvm/bin/llvm-objdump`。这是观察工具，不是 C++ 语言所需的依赖。命令解释见 [llvm-objdump 文档](https://llvm.org/docs/CommandGuide/llvm-objdump.html)。

下面是本机 `main.o` 的实际输出节选，省略了函数开头和结尾，保留调用前后的关系：

```text
10: 52800280    mov w0, #0x14
14: 528002c1    mov w1, #0x16
18: 94000000    bl  0x18 <ltmp0+0x18>
    0000000000000018: ARM64_RELOC_BRANCH26 __Z3addii
1c: b9000be0    str w0, [sp, #0x8]
```

左侧偏移以十六进制显示。`0x14` 和 `0x16` 分别是 20 和 22；本次代码先把它们放进 `w0`、`w1`，随后执行 `bl` 调用。返回后又把 `w0` 中的结果保存到栈上。这几行让“调用约定”有了具体形态：调用方需要知道参数和结果放在哪里，才可能在没有函数体的情况下先生成自己的代码。

最容易误读的是偏移 `0x18` 处的 `bl 0x18`：只看反汇编，好像在跳回调用指令自身。但紧随其后的记录指出，同一个位置还有 `ARM64_RELOC_BRANCH26` 重定位，目标为 `__Z3addii`。现在看到的是尚待链接处理的分支编码，不能当作最终程序的跳转行为。

因此，符号表与重定位并非重复信息。符号表给出被引用实体的身份，重定位记录给出待处理的位置和方式；本例只引用了一个外部函数，但同一个函数若被调用多次，就可能对应多处重定位。先前链接失败的原因也更具体了：存在对 `add` 的未解析引用，却没有找到对应定义。

把 `calc.o` 加入后，链接器可以安排相关内容、解析符号，并处理本次链接能够确定的重定位。对已链接的 `demo` 使用同一个反汇编工具，本机这处调用变成了：

```text
100000378: 94000008    bl 0x100000398 <__Z3addii>
```

现在它指向布局后的 `add` 实现，分支指令编码也从 `94000000` 变为 `94000008`。这就把“链接器处理重定位”与一个可直接比较的变化联系起来。这里的地址仍是文件工具呈现的镜像地址，不是通过读取运行中进程得到的地址；装载时还可能发生地址调整。

某些动态依赖仍由后续装载和绑定处理，不能把这理解为“可执行文件里从此不存在任何待运行时处理的地址”。完整输出见[验证说明](g00-verification.md)，不是要求你在其他平台看见相同偏移和助记符。

### 4.3 先检查目标文件，再回到源码

假设你确认 `calc.cpp` 中有 `add`，却仍然链接失败。不要立刻重复修改函数：先对实际参与链接的 `calc.o` 查看符号。如果它没有预期定义，可能编译的是另一个同名源文件，也可能条件编译排除了定义，或者你拿到的仍是旧目标文件。

源码表达的是“希望构建什么”，目标文件体现的是“这次实际构建了什么”。两者之间有编译选项、包含路径、宏和时间上的依赖。能够核对这条关系，是排查大型项目中“明明写了实现却找不到”的基础。

## 5 为什么名字相似的定义仍可能连接不上

在第三个独立实验目录里，保留原 `main.cpp` 和 `calc.hpp`，但故意用下面这个文件提供实现。它没有包含公共头文件，参数也不再是 `int`。

**文件 `wrong-parameters.cpp`**

```cpp
int add(long a, long b) {
    return static_cast<int>(a + b);
}
```

这个文件单独编译可以成功。它定义的是另一个函数：`add(long, long)`。本例不调用该函数，因此也不把它作为任意输入的安全整数实现。

```sh
clang++ -std=c++23 -c main.cpp -o main.o
clang++ -std=c++23 -c wrong-parameters.cpp -o wrong-parameters.o
clang++ main.o wrong-parameters.o -o wrong-signature
```

最后一步应因缺少 `add(int, int)` 而失败。链接器看到的两个名称可能经过名称编码（name mangling），不是源码中单独一个 `add`。C++ 允许重载，常见 ABI 用编码名称区分不同参数的函数。比较两个目标文件的原始符号，再使用 demangle，会比盯着报错中的长字符串更容易理解。

然而，这不意味着编码名称保存了完整 C++ 类型合同。例如 [Itanium C++ ABI 的函数名称规则](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#mangle.function-type)不在非模板函数名称中编码返回类型；这不是 C++ 语言对所有 ABI 的统一规定。因此不要从本实验推出“只要类型不一致，链接器就一定报错”。第 2 节让实现包含头文件，正是在编译阶段提供更多直接检查机会。没有诊断的跨文件合同错误仍可能存在；本章不运行一个接口已经不一致的程序来猜测它是否“碰巧能工作”。

到这里，你已经能把两种故障分开：没有提供任何定义，与提供了一个不同身份的定义。修复前者要补全链接输入，修复后者要回到声明、定义及它们实际使用的头文件。盲目增加 `-L`、重复添加库名，未必碰到真正原因。

## 6 把定义放进头文件以后会发生什么

### 6.1 重复包含保护解决不了跨文件重复定义

现在研究另一种常见错误：为了让调用方“直接看见实现”，把普通函数体放进头文件。下面是完整反例头文件，文件名在实验目录中仍保存为 `calc.hpp`。

**文件 `header-definition.hpp`**

```cpp
#ifndef G0_CALC_HPP
#define G0_CALC_HPP

int add(int a, int b) {
    return a + b;
}

#endif
```

保留原 `main.cpp`，再加入一个使用相同接口的源文件：

**文件 `aux.cpp`**

```cpp
#include "calc.hpp"

int twice_sum() {
    return 2 * add(20, 22);
}
```

这一变体不再编译原 `calc.cpp`，因为实现已经放在头文件里。分别编译 `main.cpp` 和 `aux.cpp`，二者都可以成功；将两个目标文件直接链接到一起，本机工具链应报告重复的 `add(int, int)` 定义。

```sh
clang++ -std=c++23 -O0 -c main.cpp -o main.o
clang++ -std=c++23 -O0 -c aux.cpp -o aux.o
clang++ main.o aux.o -o duplicate-definition
```

原因并不在于两个文件是否“重复包含了同一个路径”。每个翻译单元都按自己的预处理状态展开了一次头文件，随后各自产生这个普通外部函数的定义。头文件保护在两个翻译单元内部都正常工作，却没有表达“这份定义可以在整个程序中出现多次”。

### 6.2 inline 的含义不能简化成消除函数调用

把头文件中的函数声明改为 `inline int add(int a, int b)`，在另一个新目录重新编译上述两个翻译单元，再链接并运行。本次使用相同头文件、相同定义和简单一致的名称查找上下文，符合这里所需的内联定义条件，重复定义故障应当消失。

`inline` 在这里影响的是定义可以怎样分布于翻译单元之间，并不命令优化器一定展开函数调用。一个内联函数仍然可能通过普通调用执行，一个没有写 `inline` 的函数也可能被优化器展开。把“语言的定义规则”和“生成代码是否存在 call”分开，才能同时理解头文件设计与机器观察。

也不能把 `inline` 当作消除任意重复定义错误的开关。如果宏使不同翻译单元看见了不同函数体，或者名称查找指向了不同实体，程序可能已经违反规则，而链接器仍未报告问题。一次重复符号诊断不能覆盖全部单一定义规则（One Definition Rule，ODR）情形。有关多个定义允许条件及不要求诊断的情况，见 [C++23 草案 basic.def.odr](https://timsong-cpp.github.io/cppwp/n4950/basic.def.odr)。

本节不是建议把所有实现迁到头文件。它建立的是一个判断起点：普通外部函数常把声明与定义分开；需要头文件定义的实体，应当按相应语言规则安排。模板的定义可见性、显式实例化与编译成本会在 G5 展开。

## 7 优化为什么改变你看到的程序

### 7.1 同一个行为可以有不同的指令实现

先为原来的分离编译版本生成汇编：

```sh
clang++ -std=c++23 -O0 -S main.cpp -o main-O0.s
clang++ -std=c++23 -O2 -S main.cpp -o main-O2.s
```

`-O0` 与 `-O2` 改变优化设置。在本例不启用 LTO 的情况下，编译 `main.cpp` 时仍没有 `add` 的定义，不能仅凭名字就假定它一定实现加法。你可以比较调用附近的指令，但不能据一次结果推导所有编译器都必须保留同样的调用序列。

接着使用这个完整的单翻译单元对照文件：

**文件 `single.cpp`**

```cpp
int add(int a, int b) {
    return a + b;
}

int main() {
    const int answer = add(20, 22);
    return answer == 42 ? 0 : 1;
}
```

```sh
clang++ -std=c++23 -O2 -S single.cpp -o single-O2.s
clang++ -std=c++23 -O2 -c single.cpp -o single-O2.o
clang++ single-O2.o -o single
./single
```

现在优化器看到了函数体和固定实参，可以发现 `answer` 一定是 42，从而让 `main` 直接返回 0。本机观察可用于确认这个特定版本的结果；它不是一条“开启 O2 就必须消除调用”的语言要求。

本次两套 Clang 给出的 `main` 核心指令一致。省略编译器注释和展开信息后，单翻译单元版本只剩：

```asm
_main:
    mov w0, #0
    ret
```

并排理解两种编译输入，比只看优化等级更重要。分离编译时，`main.cpp` 只承诺调用一个返回 `int` 的函数；那个函数完全可能做减法，或者修改某处状态，所以不能仅凭声明代替它执行。合并到 `single.cpp` 后，编译器看见这里的实现确实只有加法，又知道输入常量，才有足够信息在本次优化中省去调用和比较。

如果想直接验证这种差别，把分离编译版本的实现改为减法，重新编译实现并链接。整个构建仍然可以成功，但 `main` 会返回 1：链接阶段解决的是函数身份和连接需求，不会替你判断名叫 `add` 的函数是否真的做加法。我们用这个故意改错的版本验证了程序的结果判据。

另外，即使 `main` 中没有调用 `add`，目标文件中仍可能保留一份外部可见的 `add` 实现。编译这个文件时，它可能需要供其他文件引用。**某个调用被消除**与**被调函数的符号从整个产物中消失**，不能混为一谈。

### 7.2 源码变量不必各自占有一个栈槽

在未经大幅优化的汇编中，你可能看见参数或局部结果被写入栈，再取出来；优化后则可能只经过寄存器，或者不再保留中间计算。不能由此认定一版才是“真实的 C++ 对象”，另一版违反了语言模型。

C++ 对程序行为提出要求，编译器在这些要求允许的范围内改变实现方式，通常用 as-if 规则概括，见 [C++23 抽象机说明](https://timsong-cpp.github.io/cppwp/n4950/intro.abstract)。观察机器码，是为了理解本次实现如何完成工作；不能倒过来用一次机器码观察替代语言语义。

这一点会直接影响后面的学习：G1 讨论对象生命周期时，不能靠“内存里还看得见旧数值”证明访问合法；G3 讨论复制与移动时，不能仅数源码里写了多少次构造；G6 做测量时，需要确认待测工作没有被优化掉。这里先留下这些问题，不提前把对象模型和性能测量全部塞进工具链一章。

## 8 把实现放进静态库

### 8.1 归档并没有替你完成最终链接

项目变大后，不会总把一长串 `.o` 写在命令行上。可以把相关目标文件收进一个静态库归档。本例仍从最初的三个文件构建，再加入一个与 `add` 无关的完整源文件：

**文件 `unused.cpp`**

```cpp
int unused_value() {
    return 99;
}
```

执行：

```sh
clang++ -std=c++23 -O0 -c calc.cpp -o calc.o
clang++ -std=c++23 -O0 -c unused.cpp -o unused.o
ar rcs libcalc.a calc.o unused.o
ar t libcalc.a
clang++ main.o libcalc.a -o static-demo
./static-demo
```

这里的 `main.o` 必须来自最初只含声明的头文件版本，而不是第 6 节的头文件定义变体。为各实验使用独立目录，正是为了避免把这种混用误诊成语言问题。

`ar t` 可以列出归档成员；归档工具收集目标文件并维护相应索引，并没有把它们变成一个正在运行的程序。关于归档和成员的操作可查 [llvm-ar 文档](https://llvm.org/docs/CommandGuide/llvm-ar.html)。

在本次默认链接方式下，`main.o` 对 `add` 的需要导致相关归档成员被取用，而无人引用的 `unused.o` 没有因此自动进入最终程序。查看 `static-demo` 的符号，能把“库里有这个成员”和“程序实际取用了它”区分开。如果需要直接观察链接器选入哪些输入，可以在本机链接命令中增加 `-Wl,-map,static-demo.map`，生成链接映射；它是当前链接器的选项，不是跨平台 C++ 语法。

实际结果中，`ar t` 同时列出了 `calc.o`、`unused.o`；链接映射的输入列表则只出现 `libcalc.a(calc.o)`，没有 `libcalc.a(unused.o)`。最终符号中也能找到 `add(int, int)`，找不到 `unused_value()`。这几份输出从归档内容、链接输入和最终产物三个位置验证了本例的成员选择过程。

这里还要区分两个粒度：归档选择通常以目标文件成员为单位，后续又可能发生节级裁剪。如果把 `unused_value` 与 `add` 放进同一个成员，不能继续直接沿用“两份成员里只取一份”的推理。强制加载归档、保留规则和不同链接器策略也可能改变结果；本章不把一种平台上的归档扫描顺序写成通用定律。

### 8.2 链接时的依赖不必是运行时的文件依赖

把实验目录里的 `libcalc.a` 暂时改成另一个名字，再运行已链接的 `static-demo`。它应仍能执行：本次取用的实现已经进入链接产物，运行时不需要重新打开原来的 `.a` 文件。

这只能说明不再依赖**这个原始归档文件**，不能说明程序没有其他依赖。在 macOS 上运行：

```sh
otool -L static-demo
```

你仍可能看到系统动态库等加载依赖。对 `.dylib`、`.so` 等动态库，部署时是否能找到正确镜像又是另一组问题。可执行文件也仍可能依赖配置、数据、权限及外部服务；静态库链接没有消除这些约束。

因此，源文件、目标文件、静态归档、可执行镜像和进程不能只按“都是程序文件”理解。它们承担的职责不同，存在的时间不同，错误也会在不同位置暴露。动态加载的路径、符号绑定与版本兼容留到 G8/G9，用实际共享库完整展开。

## 9 从手工命令过渡到构建系统

现在再看构建系统，它需要表达的关系已经不神秘了：`main.o` 依赖 `main.cpp` 和本次使用的头文件，`calc.o` 依赖自己的源及头文件，`demo` 依赖两个目标文件和链接配置。

如果只改了 `calc.cpp` 的函数体，而接口与其他输入都没变，重新编译实现并重新链接就能得到新程序；不必因为它属于同一个目录就把每个 `.cpp` 都重新编译。若改的是共享头文件，相关翻译单元则可能都需要重编。真实构建还要考虑编译选项、生成文件、工具变化及被追踪的依赖，不能仅比较 `.cpp` 修改时间。

你可以让 Clang 在编译时同时生成依赖文件：

```sh
clang++ -std=c++23 -MMD -MF main.d -c main.cpp -o main.o
```

打开 `main.d`，核对其中记录了本例的源文件与头文件。`-MMD` 不把系统头文件都列入这个用户依赖文件；它不是完整工具链身份清单。构建系统如何消费依赖、组织目标、安装库，是 G9 的职责。本章先让你理解依赖图里每条边为何存在。

Zig Build、CMake 或其他构建工具，最终都要安排某些编译、归档、链接和生成步骤。学习它们时，应当能够把一次失败还原到本章的具体工件，而不是只记住一个 `add_library` 或 `addCSourceFile` 调用。本章没有新增这些工具的脚本或验证它们的版本化 API。

### 9.1 沿工件回查故障

读到这里，可以把主线压缩成下面的表。阶段表示信息如何逐步确定，不规定进程数量；装载一行只作模型回查，本章没有进行加载器跟踪实验。

| 阶段与主要输入 | 主要工件 | 能确认什么，仍不能确认什么 | 观察入口 |
| --- | --- | --- | --- |
| 预处理：源文件与头文件 | 预处理结果 | 展开了哪些内容；类型检查尚未完成 | `-E` |
| 编译：当前翻译单元 | 目标文件 | 已生成代码与外部引用；所需定义可能仍缺失 | `-c`、`nm`、重定位 |
| 链接：目标文件与库 | 程序镜像 | 本次解析与布局结果；不证明所有 C++ 语义或运行条件正确 | 链接映射、符号、反汇编 |
| 装载：镜像与动态依赖 | 进程中的映射与运行时状态 | 已处理依赖的加载情况；后续绑定和业务行为仍需分析 | 加载器诊断；`otool -L` 仅显示文件声明的依赖 |
| 运行：程序与输入 | 本次可观察行为 | 实际走到的路径及结果；不证明其他输入和路径正确 | 退出状态、调试器 |

## 10 用新情形检查理解

先独立作答，再阅读后面的推理。题目不要求背诵寄存器编号或诊断全文，而是要求说明应查看什么证据。

1. 你把 `calc.cpp` 改成减法，却只重新链接原来的两个 `.o`，程序仍返回 0。为什么这不能证明修改无效或编译器有 bug？下一步检查什么？
2. 构建日志显示 `main.cpp` 编译成功，链接报 `add(int, int)` 未定义。目录里明明有 `libcalc.a`，还缺少哪一步证据？
3. 一份带保护宏的头文件被两个源文件包含，链接仍报告重复定义。保护宏到底保证了什么，应该怎样分析定义的安排？
4. `single-O2.s` 中 `main` 不再调用 `add`，但 `nm single-O2.o` 仍显示 `add` 的定义。这两个观察矛盾吗？
5. 一个程序链接成功且返回了正确结果，能否据此确认所有翻译单元使用了相同的类型布局、所有 ODR 要求均满足？
6. 把 `libcalc.a` 改名后，程序仍能运行。部署时可以因此只复制这个可执行文件而不检查其他依赖吗？

### 10.1 推理与排查路径

**第一题。** 链接器读的是 `.o`，不会因为旁边的 `.cpp` 更新就自动重新编译它。先检查构建命令和实际输入路径，再确认新的实现目标文件已生成并参与链接。把实现改为减法后正确重编，本例主程序应返回 1；这正好把“构建是否执行了新输入”和“结果是否正确”联系起来。不要用文件名相同代替输入身份核对。

**第二题。** 目录中存在归档，不代表它参与了链接，也不代表里面存在所需的精确定义。先检查链接命令中的实际库路径，再用归档列表和符号工具查看成员。若只找到 `add(long, long)`，继续增加相同库路径不能满足 `add(int, int)`；应检查声明与实现。平台特定的归档处理规则在确认这些基本事实后再分析。

**第三题。** 保护宏防止一个翻译单元中的重复展开，不是全程序去重。判断头文件包含的是声明、普通外部定义还是允许按相应条件多次定义的实体。本例可以把普通函数体放回单独实现文件；若采用内联定义，则需满足其定义一致性等条件，而不是随手添加 `inline` 后就认为全部问题消失。

**第四题。** 不矛盾。优化器可以利用已知函数体消除 `main` 中的这次调用，同时仍保留供其他翻译单元使用的外部函数实现。应该分别观察调用位置与全工件符号，不能用其中一个代替另一个。

**第五题。** 不能。链接器不是完整的跨翻译单元 C++ 语义验证器；某些规则违反不要求诊断，名称匹配也不代表所有类型信息都被核对。一次运行只覆盖该次路径。公共头文件、配置一致性、接口约束与针对性检查仍然必要。

**第六题。** 不能。本实验只切断原静态归档的运行时文件依赖。还需检查动态库、加载路径及应用自己的资源。复制部署是否成立，应由具体依赖和目标环境验证，不能从一种依赖已经消失推出全部依赖都消失。

## 11 接下来转向对象模型

本章建立了一条可以来回追踪的链：源码声明决定当前翻译单元能检查什么，目标文件保存已经生成的内容和未解析的引用，链接把这些工件组成程序，运行才让某些行为真正发生。以后遇到问题，可以先找到链上的位置，再选择工具。

下一步不急着记更多编译选项。我们要把同样的追问移到运行中的对象：一个地址上何时存在对象，引用和指针让你获得了什么访问能力，存储仍然存在时为什么对象可能已经结束生命。这是 [G1 第一单元](g01-storage-and-lifetime.md)的主线，也是后面资源管理、容器失效和并发访问共同依赖的基础。
