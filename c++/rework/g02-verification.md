# G2 新稿的实验与验证边界

本记录对应[资源责任与确定性清理](g02-resource-lifecycle.md)和[借用与所有权交接](g02-ownership-and-handoff.md)。批次起点为 `d071bf44fe2713034741197fb3ed7e89d4385cab`；G1 的接受与冻结不变，G2 为 **待精读审核，尚未冻结**。以下结果是本地执行证据，不是 GitHub CI，也不代表全章技术命题已经被自动证明。

## 1 输入与复现方式

[执行器](verify_g2.py)从两份正文提取全部十二份 C++ 文件：三个共享头文件、八个正常运行程序、一个编译负例。每套编译器都在新的临时目录中运行；每个实验是独立进程，计数器不会跨程序累加。完整源码、正文、脚本和复用进程辅助文件的 SHA-256 与全部编译／执行命令保存在 [g02-results.json](g02-results.json)。

在仓库根目录执行以下命令。记录中的本次输出为 `c++/rework/g02-results.json`；再次运行必须选择尚不存在的新路径，不覆盖历史记录。

```sh
python3 c++/rework/verify_g2.py \
  --compiler /usr/bin/clang++ \
  --compiler /opt/homebrew/opt/llvm/bin/clang++ \
  --output /tmp/g2-rework-results-new.json
```

八个运行程序分别检查实际临时流的退出路径、部分构造、移动交接、显式关闭失败、unique ownership 的消费时点、共享与成员别名、延迟任务以及回调环。输出必须完整匹配，程序还检查资源／对象数量、指针关系、数值及失败状态。编译负例只接受 `TempFile` 复制构造已删除的目标诊断，不把缺头文件或任意编译错误当作通过。

执行器复用 `c++/learning/verify_g.py` 的进程、超时与取消处理，没有修改该辅助文件，也没有运行它的 v1 实验。超时、信号退出、错误输出或非预期退出码不能充当错误变体被拒绝的证据。八项判据自检覆盖正常输出、错输出、stderr、超时、崩溃、错误退出码及编译诊断匹配；它们只检查判据逻辑，不是八个额外的 C++ 实验。

## 2 环境与选项

| 项目 | 本机身份与条件 |
| --- | --- |
| 平台 | macOS 26.7，arm64；Python 3.12.14 |
| 编译器 A | Apple Clang 21.0.0，`clang-2100.3.34.2`；`_LIBCPP_VERSION=220106` |
| 编译器 B | Homebrew Clang 23.1.2；`_LIBCPP_VERSION=230102` |
| 语言与诊断 | `-std=c++23 -Wall -Wextra -Wpedantic`；两者 `__cplusplus=202302L` |
| 普通程序 | 分别以 `-O0 -g` 与 `-O2` 编译、运行 |
| ASan/UBSan 正例 | `-O1 -g -fsanitize=address,undefined -fno-sanitize-recover=all -fno-omit-frame-pointer` |
| 错误变体 | `-O0 -g`；必须编译成功，再匹配精确退出码 |

两套编译器均使用 libc++，不是两个操作系统或两类标准库。动态检查设置 `ASAN_OPTIONS=detect_leaks=0:halt_on_error=1:abort_on_error=0:exitcode=86:symbolize=0` 与 `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=0`，不启用外部符号化及泄漏检测。能力探测只说明插桩程序可以在本机编译运行；本批没有新增 ASan 阳性对照，也不借用 G1 的阳性对照冒充本批结果。

## 3 分项结果

| 证据类型 | 本次结果 | 支持范围 |
| --- | --- | --- |
| 正常编译与运行 | 八个程序 × O0/O2 × 两套编译器，32 项 PASS | 这组完整程序的状态、退出码与输出符合判据 |
| 编译负例 | 2 项 PASS | 两套编译器均拒绝复制 `TempFile`，诊断匹配 |
| ASan/UBSan 正例 | 16 项 CLEAN_OBSERVED | 本次运行未报告相应工具可发现的错误，不是完整所有权或生命周期证明 |
| 错误变体 | 两种变体 × 两套编译器，4 项 REJECTED_AS_EXPECTED | 编译成功后，测试拒绝遗漏关闭与吞掉错误这两种实现 |
| 判据自检 | 8 项符合预期 | 检查执行器不会把几个常见的错误结果当成通过 |

两个 sanitizer 能力探测可用，SKIP 为 0。这里的 32／2／16 是同一组文件在不同配置下的结果，4 项变体单独计数，不称作 54 个独立实验。批内先运行了一次初稿检查，随后只校准标题与使用说明；最终提交记录重新绑定并执行定稿正文，不把两次结果重复累加。

第一个变体将 `~TempFile()` 的后备关闭移除，`cleanup-paths.cpp` 必须返回 2；第二个变体仍调用后端关闭，却把返回值一律变成 0，`close-failure.cpp` 必须返回 1。两者都要求 stdout/stderr 为空；编译失败、崩溃和超时不是合格的拒绝方式。精确替换及变体全部源码摘要保存在 JSON 中，正文没有应用这些修改。第一个变体故意把临时流留到测试进程结束，用于检验清理计数判据，不是生产资源处理策略。

## 4 实际资源与故障模型

正常路径实际调用 `std::tmpfile`、`fwrite`、`fseek`、`fread`、`fclose`。获取失败注入直接返回空指针，不调用底层创建；关闭失败注入先真实关闭，再强制返回 EOF。后者检查的是 owner 在“关闭已消费句柄但报告失败”时怎样更新状态与传递结果，**没有制造真实磁盘错误或验证所有 I/O 失败路径**。

文件计数器是程序内的协议观察，不是 OS 资源枚举，也不是泄漏检测器。没有注入短写、分配失败或异常消息构造失败，没有覆盖进程崩溃、断电、持久化、文件事务、任意 C 库句柄及关闭重试协议。`get()` 的调用方前置条件仍靠接口合同维护，不能从这些实验推出借用者无法错误关闭资源。

Batch 的延迟任务在同一线程里稍后调用；强环示例先观察保留，再显式拆环，不把进程退出当成循环收集。没有线程启动、竞争注入、TSan、调度压力或并发取消。性能观察、并发动态检测、Linux/Windows、libstdc++、Zig/Rust 均为 **NOT RUN**；PDF 为 **NOT BUILT / NOT VALIDATED**。

语言条款按正文链接读取 C++23/N4950；C 流语义同时核对 N1570 §7.21.4.3、§7.21.5.1。规则核对与工具运行是两类证据，链接存在本身不构成技术审核通过。文字深度、中文流畅度和章节安排仍待实际精读，不因本地程序符合判据就自动冻结 G2。
