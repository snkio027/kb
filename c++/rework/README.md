## 每个重要主题需要讲到什么程度

一段讲解应让读者沿着具体状态或输入推导结论。例如“vector 扩容可能使指针失效”，不能在解释到这里就结束：应展示旧存储、元素迁移、新存储、旧存储释放之间的关系，区分只追加但未扩容的情况，并说明为什么不能通过某次地址没变判断接口合同。更深入的内容来自条件与因果，不来自再列十种容器。

关键实现不再长期藏在 `acquire()`、`build_state()`、`do_work()` 等占位函数后面。第一次建立模型可以省略细节，随后必须补齐真正影响结论的部分。反例先说明改了什么，再解释为何失败；不把偶发崩溃、特定性能数字或一次工具输出当作语言证明。

中文以完整论述为主。术语首次出现给出必要英文，之后统一使用中文；标识符保留原样。保留决定结论的限制，删除反复出现却不增加理解的“本质”“核心”“不是……而是……”口号。连续的短句、流程块和清单应转成有因果关系的段落，不只是换一种排版。

G0 精读反馈进一步确定了写作尺度：一个主问题贯穿章节，尽量沿同一个对象或程序改变条件；先用直观解释建立理解，再稳定专业术语。语言规则、实现机制和本机观察分层，关键机制由真实工件或状态变化解释，章节最后再压缩成回查模型和迁移题。后续继承这些方法，不要求相同节数、篇幅或实验数量。

**正式理论骨架是 Content v2 的硬标准，与案例可读性同等重要。** 每个重要主题都应让读者找到四层答案，而不必重新从全部实验中猜测规则：定义（Definition）说明术语指什么；关系（Relation）区分并连接相邻概念；规则（Rule）说明哪些前提足以推出结论；边界（Boundary）解释哪些相似情形不能照搬结论。只给工程建议或一次观察，不算完成理论讲解。

写作时从案例与观察进入正式模型，再把模型用于解释原案例及变化后的条件。模型可以是一段完整论述、少量关系步骤或必要的对照表，不要求每节机械使用四个标签，更不把章节改成标准条文摘要。关键语言规则引用固定版本依据；系统机制区分抽象合同与实现选择；实验说明它支持的具体命题，不能代替完整规则。增加深度优先补足关系和推导，不默认增加主题、代码数量或实验矩阵。

这项要求集中维护在本节，补充 Content v2 的内容深度标准，不另建一份平行 Editorial Profile，不追改 v1 冻结稿或历史证据。G5 的理论补充已获精读接受；G6～G12 后续按同一标准审核，但不因此在本批启动。

章节结尾保留少量需要迁移推理的题目，并给出完整答案。不要再连续安排“统一模型、十五条原则、审查协议、常见误判、Final Gate”五种重复总结。进阶材料可以回查，但首次主线必须能够直接顺序读完。

## G4 如何承接 G3

G4 让一批读数持续变化，而不是重新按容器类型罗列知识。第一单元给 Reading 增加编号、数值和有效标记，沿追加、插入、删除与重新分配，区分完整值、逻辑位置、C++ 对象身份、业务记录身份和借用有效性；随后比较句柄间接存储、deque 两端插入与 list 成员排序所提供的不同合同。

第二单元从单遍输入进入遍历能力，再说明排序投影、比较关系、压缩与擦除。filter/transform 的惰性、显式物化、闭包依赖、起点缓存和 borrowed_range 在同一数据任务中逐步出现，不把 view 等同于借用，也不把编译通过等同于生命周期安全。

第三单元从 lower_bound 的缺口查询进入按键组织，再区分 map 查询与更新、unordered_map 的 rehash 和元素引用，最后用整体替换的 IndexedBatch 共同提交序列与索引。它解释标准容器各自有效为何仍不足以保证组件关系正确；示例不扩展为通用数据库或并发快照系统。

[G4 验证说明](g04-verification.md)分别登记正常运行、目标编译诊断、复制／移动计数观察、ASan/UBSan 与错误变体。计数不设固定实现选择为通过条件，不是性能测试；重复键拒绝是实际业务校验失败，不冒充内存故障注入。每个单元保留六道迁移题及普通章节中的推理答案，三单元的中文讲解、章节组织和证据整合已获精读接受。
