## 全书的组织方向

暂以五个部分组织知识，旧 G 编号用于追踪来源，不作为必须保留的最终章节边界。需要拆分的专题按问题和先修关系拆，而不是让一个章节承载所有相关名词。

| 部分 | 建议章节组织 | 如何增加实质深度 |
| --- | --- | --- |
| 程序与对象 | G0 工具链；G1 分为存储与对象、生命周期与访问有效性两个单元 | 从真实工件和具体执行路径建立模型，区分语言规定与实现观察 |
| 资源与值 | G2 资源句柄及借用；G3 复制、移动、赋值与返回；G4 容器、迭代器、算法与视图 | 沿一个资源类型和一个数据批次持续演进，解释失败路径、失效规则和不同实现的代价 |
| 抽象与机器成本 | G5 类型推导、约束与实例化；G6 分为布局与访问、分配策略与测量 | 从调用表达式推导具体类型；从访问工作量解释测量，而不是把泛型等同模板技巧、把性能等同耗时表 |
| 并发与交付 | G7 分为共享状态协议、原子操作与内存模型；G8 二进制接口；G9 构建和部署 | 先把互斥、等待、退出讲完整，再进入内存序；跟踪一份库从编译到外部使用，不提前用框架掩盖步骤 |
| 系统综合 | G10 运行时案例；G11 时间与物理系统；G12 跨语言模型对照 | 用前面已经解释的机制解决组合问题，保留取舍和失败历史，不重讲整本书或变成框架名录 |

这是重编路线，不是已经完成的新目录。G8 与 G9 的必要概念会在 G0 初次出现，后面负责展开 ABI 兼容、动态加载和工程交付，不重复一轮术语定义。Zig 与 Rust 用于检验模型是否可迁移，不在每节末尾强行添加对照；Zig Build 也不替代直接观察编译、链接命令。

## 每个重要主题需要讲到什么程度

一段讲解应让读者沿着具体状态或输入推导结论。例如“vector 扩容可能使指针失效”，不能在解释到这里就结束：应展示旧存储、元素迁移、新存储、旧存储释放之间的关系，区分只追加但未扩容的情况，并说明为什么不能通过某次地址没变判断接口合同。更深入的内容来自条件与因果，不来自再列十种容器。

关键实现不再长期藏在 `acquire()`、`build_state()`、`do_work()` 等占位函数后面。第一次建立模型可以省略细节，随后必须补齐真正影响结论的部分。反例先说明改了什么，再解释为何失败；不把偶发崩溃、特定性能数字或一次工具输出当作语言证明。

中文以完整论述为主。术语首次出现给出必要英文，之后统一使用中文；标识符保留原样。保留决定结论的限制，删除反复出现却不增加理解的“本质”“核心”“不是……而是……”口号。连续的短句、流程块和清单应转成有因果关系的段落，不只是换一种排版。

章节结尾保留少量需要迁移推理的题目，并给出完整答案。不要再连续安排“统一模型、十五条原则、审查协议、常见误判、Final Gate”五种重复总结。进阶材料可以回查，但首次主线必须能够直接顺序读完。

## G0 这次具体改变了什么

旧 G0 的三个文件实验是良好入口，新稿继续使用小型双翻译单元程序，但沿同一个程序逐步回答：声明怎样支持编译、头文件到底带来了什么、符号和重定位各记录什么、改错签名为什么在不同阶段失败、头文件定义为什么可能重复、优化怎样改变可观察工件、静态归档怎样参与链接。

原先 G0 的结构体布局、ARM64 寄存器回查和跨语言句柄接口暂不挤在这一条主线上。它们仍保留在 v1 的 G0，并分别由后续对象模型、机器成本和 ABI 单元承接；不是以删除细节换取简短。G0 对加载器只建立边界，完整动态库故障留给 G8/G9。

新稿的 [验证记录](g00-verification.md)只绑定这次源代码和执行结果。没有把旧测试“全部通过”当作新稿通过，也不声称已经验证 Linux、Windows、Zig 或 Rust。自动结果不能回答文章是否真正易懂，这一项需要实际精读反馈。

## 参考的采用边界

2026-10-01 提供的参考用于确定案例推进方法，不直接转抄其中的技术简写和版本判断。例如 `std::move` 本身不执行资源转移，容器容量不保证按某一固定数列增长，符号数量不等于源码中的模板特化数，并发问题也不能全部归结为内存序。后续正文应把这些条件讲清楚，而不是沿用更响亮的表述。

本轮不创建新课程平台、自动学习计划或通用实验框架，不动 FM，不重建 PDF。先用 G0 的实际阅读效果确定写作尺度，再按上述先修关系推进后续正文。
