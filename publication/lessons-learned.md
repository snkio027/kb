# 技术手册出版工程复盘：从 Markdown 到可核验发布

整理日期：2026-09-27。复盘范围截至 `d1778dd0b9416da465b5578a5f74f84b35e293de`，结合本次协作过程、用户提供的总结，以及仓库中的源稿、构建、审核和发布记录。

本文沉淀经验，不替代操作入口、原始证据或接受记录，也不新增一套出版规范。文中数字和检查结果均引用对应批次的历史证据，不表示本次整理重新运行了 C++ 实验、PDF 构建、视觉审阅或发布验证。

## 1. 交付的不只是 PDF，而是能说明来源与边界的阅读产品

这次实际交付的是《Modern C++ 工程学习手册》v1.0.0：G0–G12、407 页，以及 GitHub Release 中的 PDF、manifest、release notes 和校验清单四个资产。更值得复用的成果，是能够回答以下问题的一套方法：

- 读者拿到的是什么版本，它来自哪些内容？
- 排版转换是否保留了代码、条件、表格关系和引用目标？
- 哪些检查真正执行过，哪些只是用户反馈或仍未验证？
- 本次发布的是哪一组精确字节，如何与旧候选区分？
- 后续修改怎样进入新版本，而不覆盖已交付事实？

因此，工作模型从“Markdown 经 Pandoc／LaTeX 转成 PDF”，变成了以下交付链：

```text
权威内容与编辑基线
    → 输入快照与产品视图
    → 编译、结构检查与渲染
    → 视觉审阅与候选接受
    → 正式身份与新字节检查
    → 授权分发、下载回验与发布回执
```

这不是要求小文档也复制整套流程。此次内容规模大、代码与跨章引用多，且需要公开分发和保护历史制品，才逐步形成了这些检查。复用时应按风险裁剪，而不是把文件数量、检查数量或审批次数当作成熟度。

实际结果见[发布记录](releases/cpp-handbook/v1.0.0/README.md)与[发布回执](releases/cpp-handbook/v1.0.0/publication-receipt.json)。回执记录了当时的远端观察；本文不把它当成一次新的实时远端查询。

## 2. 协作方式：以完整能力划批，不以补丁划批

### 2.1 先明确读者，再决定编辑标准

G 系列从已有章节整理为个人长期使用的专业学习手册，重点并不是继续增加主题，而是让读者能够首次学习、动手验证和按问题回查。全系列编辑基线统一了章节层级、术语、实验身份、Final Gate 与参考答案；各章仍保留不同的证据模型。

例如，G5 的编译期问题适合编译器诊断与静态断言；G6 的机器成本需要测量，不能以固定性能常量判断通过；G7 的并发协议需要推理，动态检测没有报错不能替代协议证明。专业化是让论证与证据更清楚，不是把高密度章节压成速查表。编辑约定和跨章职责分别保存在 [Editorial Profile](../c++/editorial-profile.md) 与[全书阅读约定](../c++/handbook-guide.md)。

### 2.2 小提交有价值，小交付未必有价值

早期准备阶段按安全切片推进，有助于关闭旧写入入口、澄清授权；但每个小修复都经历说明、授权、提交、等待与复审，用户很长时间仍拿不到新版阅读件。检查能力在增长，可用能力却增长较慢。

后续改成一次批准完整能力范围：执行方在同一批内完成设计细化、实现、真实构建、测试、自查和缺陷修复，最后集中审核。先交付可读的独立版与合订版，再将共享引擎重构、ESD 与 C++ 两个真实产品接入、试件和回归作为完整批次。这比逐个批准模板、过滤器或检查器更接近用户目标，过程见[首个完整预览交付](../design/project/publication-preview.md)和 [v2 双产品交付](reviews/v2-pilot/README.md)。

适合保留的协作合同是：

| 批内自主处理 | 需要重新确认 |
| --- | --- |
| 标题重复、锚点冲突、分页缺陷、测试失败、必要的局部重构 | 改变正文技术语义或扩大主题 |
| 补回归、修复取消与失败路径、完善本批说明 | 覆盖历史制品或变更已发布资产 |
| 按可回退单元组织多个提交，最后集中审核 | 新的高权限操作或未授权的正式发布 |

**控制的是目标、风险和不可越过的边界，不是机械限制修改几个文件。** 大批次仍可以有小提交；每次变更推送供审核，也不等于每个内部步骤都要等待一次批准。

### 2.3 冻结是控制变量，不是禁止探索

C++ 主线依次经历分批正文编辑、全书一致性清理、内容冻结、复杂章节 Pilot、视觉冻结、全书构建和发布准备。早期 ESD 出版探索与内容建设并非完全串行；“先冻结再出版”应理解为正式候选取源的约束，而不是禁止提前制作试件。

各阶段只解决自己的问题：内容阶段不为分页删代码；视觉阶段不重新解释技术命题；全书构建验证覆盖面，不借机重开审美设计；发布阶段只处理身份和分发。这样才能判断某次变化究竟影响了什么。

## 3. 身份分离：不要再用“最新 PDF”指代交付物

内容、接受范围、视觉规则、执行尝试和对外版本不是同一种身份。本次发布可以沿下表回查：

| 对象 | 实际基线 | 回答的问题 |
| --- | --- | --- |
| Markdown 内容 | `8f479de` | 具体读取哪一版 G0–G12？ |
| 内容冻结接受登记 | `a2195d9` | 哪个范围获接受，哪些限制继续保留？ |
| 视觉实现／接受登记 | `1c11c59`／`ea2e613` | 用什么版式规则，接受的是哪一版？ |
| 完整预览候选 | `eb7f567` | 全书扩展验证对应哪个候选？ |
| 身份一致的 RC1 | `2f4caf6` | 哪一份仍未发布的 v1.0.0 候选？ |
| 正式发布载荷 | `54f193f` | 签名标签绑定哪些待分发字节？ |
| 发布回执 | `d1778dd` | 后续观察到的公开与下载核对事实是什么？ |

短提交号用于阅读，精确源身份、SHA-256 和标签对象以关联原记录为准。编辑接受表示特定范围的审核结论，不代表所有技术命题、平台或未来字节都已验证。整书出版版本 `1.0.0` 也没有强行统一 G0–G4 的 `1.2.1` 与 G5–G12 的 `1.1.1`。

构建身份还需要源路径及字节、profile、视图、引擎、实际工具和依赖；仅记录 commit 不足以识别未提交输入、不同工具链或不同产品配置。每次重试使用独立 attempt，最终候选绑定具体成功尝试，不能只按同名 PDF 寻找“最近结果”。详细机制见[运行与身份说明](README.md)。

冻结正文中保留的历史“待审核”“PDF NOT BUILT”等文字，不应为了状态整齐而追改。当前状态由外置接受和发布记录表达，生成控制页负责说明来源；否则一次状态登记会悄悄改变已经接受的内容字节。

## 4. 内容保真：同时检查精确字节与语义关系

### 4.1 编辑变动不能偷换历史技术证据

全书一致性修订调整了术语、导航、重复论述和章节过渡，整篇 Markdown 摘要自然变化。当时除了登记新旧文件摘要，还比较了受保护载荷：953 个围栏块、1,714 个显式锚点、26 个 Gate 题目／答案区域，以及 30 个提取实验、68 个源码文件和各自的 ID、mode、oracle。

这里不是只要求数量相同，而是核对对应载荷与关系不变。审计器还用正文、代码、Gate、锚点的小变体检查自己的判据：允许普通编辑，拒绝越界改动。由此能够说明历史实验所对应的源码与判据未变，却不能说实验在本轮重新执行过。见[全书一致性修订与冻结记录](../c++/learning/editorial-sweep.md)。

可复用做法是“双层绑定”：整文件摘要确定输入身份，语义载荷比较解释变化范围。二者互补，不能用语义摘要替代原文件身份，也不能用“hash 不同”直接断言所有历史实验失效。

### 4.2 出版转换要保留内容所属关系

PDF 的保真问题比“有没有少字”更细。宽表转 record 时，某个字段值必须仍属于正确记录；代码续页时，代码必须仍属于正确实验和文件；引用必须指向正确章节，而不只是一个存在的同名标题。

全书阶段检查了 1,014 个源标题区间、6,972 个顺序单元、896 个行内字面量和 268 个表格行关系。这些数字描述已定义检查的覆盖，不是全文逐字形、缩进、技术正确性或全部视觉关系的证明。

因此，转换应能追踪“源块 → 编排结构 → 排版输入 → PDF 内容与位置”。对不能可靠自动判断的区域保留人工审阅范围和缺口；不要放宽检查、删除源代码或忽略未知标记来获得全绿。实际适配与保真记录见[全书构建记录](reviews/full-handbook/README.md)。

## 5. 架构重用：保留行为不变量，而不是旧文件形状

### 5.1 把产品差异放进 profile

从 `design/` 专用构建器迁移到 Publication v2，价值不在于移动目录，而在于分开了共同机制和 ESD 产品假设：

| 层 | 主要职责 |
| --- | --- |
| 权威源 | Markdown、稳定对象身份与固定源提交 |
| Engine | 输入快照、隔离、编译调度、通用审计、渲染、终态和候选冻结 |
| Profile／Adapter | 来源解析、产品视图、元数据、导航、主题和产品检查策略 |
| 共享排版组件 | 代码、表格、record、模板、续页和字形等机械实现 |

ESD 的 Front Matter 和 C++ 的书名式 H1、正文版本、实验标记不是同一种来源格式。把它们变成统一模型，不等于把所有书硬改成一种 Markdown，也不需要在共享引擎里不断增加书名分支。

“新增产品通常只增加 profile”是方向，不是禁止引擎变化。全书别名链接修复和正式出版身份支持属于通用能力，可以在回归约束下补齐。当前经过真实接入的是 ESD 与 C++；Zig、Atlas 或其他手册只是后续复用方向，不能登记成已经验证。

### 5.2 两次安全反例比一份全绿报告更有价值

准备阶段的 25 项测试通过后，独立复审仍发现两个真实盲点，随后在本机临时仓库复现并修复：

| 反例 | 暴露的错误假设 | 实际处理与边界 |
| --- | --- | --- |
| `git status` 触发配置的 clean filter，修改测试 `dist` 哨兵，但入口仍报 `PREPARED` | 禁用 fsmonitor 和限制直接写入，就等于准备过程无外部副作用 | 在 status 前检查有效 Git 配置，遇不支持的 filter 定义即拒绝；不是事后发现损坏才失败 |
| 最终成功 JSON 已写出，`fsync` 失败后无法排他创建同名失败记录 | 非零退出或异常处理足以防止假成功 | 暂存文件完成写入与同步后，以不覆盖的链接操作提交最终名称；明确提交点前后语义 |

修复后的 43 项回归覆盖了新增窗口，但仍不是掉电持久化或完整发布事务证明。真实编译后来另加 macOS Seatbelt 写入隔离、进程组取消及真实工具失败检查；准备阶段的路径防护不能代替这些运行时约束。见 [B1-A 修复记录](../design/project/publication-b1a.md)与[完整预览隔离记录](../design/project/publication-preview.md)。

重构中真正应保留的是：输入绑定、路径边界、漂移拒绝、独立尝试、不覆盖历史、可解释终态，以及冻结候选时不重新编译。不能因为文件还叫 `pub.py` 就认为安全性自动继承，也不能因代码迁移就丢掉已积累的反例。

## 6. 排版经验：阅读任务比几何合格更重要

### 6.1 分页要理解“哪些内容不能失去联系”

没有 overflow，不等于页面好读。危险说明留在上一页、代码下一页才开始，或者新页只剩几个闭合符号，都可能通过纯几何检查，却破坏阅读。

此次定稿把以下对象作为分页语义单元，而不是一串独立段落：

- 危险／反例角色、实验 ID、文件名与首段代码。
- 完整实验的每段续页及其身份。
- 短表、短 record，以及空模板的名称和字段。
- Final Gate 题目与其必要上下文。

页数降低、页面填满不是优化目标。章节开场和完整退出单元可以留白；只有明显无阅读价值的短尾才局部回收。规则尽量绑定源对象而不是物理页码，避免一次合理增文让所有分页补丁失效。

### 6.2 组件应按读者任务分类

| 对象 | 有效做法 | 应避免的统一化 |
| --- | --- | --- |
| 完整实验／危险反例 | 显示源角色、实验 ID、文件名；续页仍可辨认 | 警告与代码分离，或只显示内部 Cxx 标号 |
| 机制片段／输出／字面块 | 使用较轻标签，保留必要边界 | 每个三行片段都像一份审计报告 |
| ASCII／流程块 | 保留行与边的关系，过宽时显式处理 | 静默软折行或为变窄擅自改图 |
| 比较矩阵 | 保留横向扫描能力 | 仅因列多就全部转卡片 |
| 长字段 record | 标签与值首行对齐，字段所属关系清楚 | 用压缩间距掩盖两列起点不齐 |
| Empty Template | 保留名称、有序字段和空值；续页重复身份 | 虚构数据行，或变成无名称字段流 |

内部 block／mapping ID 仍留在审计 JSON，纸面只保留对读者有用的身份。空模板的空白本身有语义，但可手写空值线不等于交互式 PDF 表单。

Soft-wrap 同样需要分级：优先空格，再语义标点，再 `_ / . -` 等标识符边界，最后才用任意字符应急断点。`OPERATIONAL` 被拆成 `OPE / RATIONAL` 成为定向反例；视觉续行通过悬挂缩进和非文本标记区分。已有文本提取检查不等于所有阅读器都能无损复制缩进。

### 6.3 源标题层级与出版角色分别建模

H1–H3 描述来源结构；独立版和合订版中的 Document、Chapter、Section 角色不同。G6 独立成册与作为合订版一章，不宜机械使用相同的开页、目录和页眉规则。反过来，也不应为了 PDF 视觉层级去改冻结 Markdown 的结构。

上述机制经过组件 A/B、真实长块回归和代表页审阅，最终由[视觉合同](reviews/reading-finalization/visual-profile.md)固定。危险身份绑定、record 对齐和长模板等有定向修复；自然留白、极长 token 应急折行、局部节奏与未穷举场景仍按[已知非阻塞限制](reviews/reading-finalization/README.md)保留。不能把两者统称为“全修好了”，也不能统称为“都没修，只是接受了”。

## 7. Pilot 验证设计，全书构建验证覆盖面

G6/G7 被选作 Pilot，是因为它们覆盖长代码、复杂表格、ASCII 图、实验、Gate、参考答案和大量行内技术符号，而不是因为篇幅短或容易排得漂亮。ESD 同时提供了比较矩阵、长记录和空模板，两类产品一起约束共享组件。

视觉规则冻结后，全书仍暴露了 Pilot 未覆盖的真实输入：不同实验标记前缀、连续 HTML 锚点、被误判为 HTML 的 C++ 尖括号、被误判为文献引用的 `@rpath`、缺失字形、长标识符，以及嵌套 Gate 清页。处理目标是让冻结规则正确覆盖来源，不能把未知语法静默丢弃，也不应趁此重开字号和色阶设计。

最有代表性的缺陷是：**HTML alias 已生成 PDF destination，但正文没有可点击区域。** 第一次 `PREVIEW_READY` 后的补充检查才发现它。“目标存在”和“目录能点”都不足以证明正文链接成立。

修复后，导航验证沿源引用、所属章节、目标、重复次数与实际 annotation 核对，不拿目录链接代替正文链接。最终记录包含 9,457 个 destinations、779 个 annotations、335 处正文内部引用（其中 79 处跨章）；计数用于核对映射，不单独作为导航质量指标，也不是逐个阅读器点击的证据。见[全书接入与导航审计](reviews/full-handbook/README.md)。

视觉回归则围绕[语义样本目录](tools/reading-corpus.json)组织：如 `danger-role-binding`、`experiment-continuation`、`empty-template-continuation`、`semantic-soft-wrap`。每次生成“语义对象 → 本次页码 → 页图与摘要”，页码是观察结果，不是永久样本身份。

冻结后的普通留白、偶发短尾和局部折行不再触发重设计；正文丢失、代码截断、链接指错、危险身份消失、表格语义破坏与严重不可读仍须阻断。这条停止规则避免为少数页面反复扰动数百页已经接受的内容。

## 8. 证据分层：每个状态只说明它实际检查的命题

| 证据或状态 | 支持的结论 | 不支持的结论 |
| --- | --- | --- |
| Markdown 结构／链接检查 | 已定义的层级、语法与本地引用检查通过 | 技术命题正确、外网链接可达 |
| C++ 编译／诊断、性能观察、并发动态检测 | 对应源码、工具链、运行及判据的结果 | 跨平台正确、固定性能、完整并发证明 |
| `PREPARED`／`PREVIEW_READY` | 准备完成／声明视图完成相应自动检查与渲染 | 已获人工接受或正式发布批准 |
| `STRUCTURAL_PASS` | 有界内容、结构或几何判据通过 | 所有页面都好看、所有字符与缩进无误 |
| 代表页视觉自查 | 实际查看页的布局观察 | 全书逐页精读、独立用户复审 |
| 阅读器 smoke | 指定字节在指定环境下的交互观察 | 其他阅读器、旧或新候选自动继承通过 |
| `ACCEPTED`／`RELEASED` | 已登记范围的接受／具体版本的分发事实 | 新字节、全部技术内容或所有平台获认证 |

全书候选阶段实际查看了 54 张代表页；最终正式身份构建查看了 10 张新页图。二者都渲染了 407 页，但不能合写为“407 页全部人工验收”。最后的 112 项出版回归是本地执行证据，不是 112 个 C++ 实验，也不是 GitHub CI。

阅读器记录尤其需要克制：旧 RC1 有 Preview 原生观察和 Chrome 用户总体反馈；最终 PDF 的原生控制未成功，用户针对最终路径与摘要回复“通过”，但未注明阅读器和版本。因此最终只能记作 `USER_REPORTED_PASS / READER_UNSPECIFIED`，不能声称 Preview 与 PDFium 均对新字节逐项通过。工具超时也不是 PDF 无法打开的证据。见[最终阅读器证据边界](releases/cpp-handbook/v1.0.0/reader-smoke.md)。

失败历史应与成功证据一起保存。全书阶段 11 次尝试包含 7 次 `FAILED`、2 次 `CANCELLED` 和 2 次 `PREVIEW_READY`，最后一次才绑定交付候选。一项取消的外层清理出现错误、退出码为 1，但已记录终态是 `CANCELLED`；不能只凭退出码改写事实。更不能覆盖旧 JSON，让整段历史看起来从未失败。

同理，中间目录即使叫 `final-checks`，也可能随后发现输入漂移。选择证据要看实际输入绑定、运行前后摘要与终态，而不是相信文件名里的“final”。

## 9. 发布：先得到最终身份的字节，再分发同一组字节

### 9.1 Preview、RC1 与正式版不是同一份文件改名

本次实际有三个不同身份，不能混写：

| 阶段 | PDF 中的生成身份 | PDF SHA-256 前缀 |
| --- | --- | --- |
| 已接受全书预览 | `candidate.1`、`PREVIEW / DRAFT` | `80aabc25…` |
| v1.0.0 RC1 | `RELEASE CANDIDATE RC1`、尚未发布 | `c011cc4e…` |
| 正式版载荷 | `PUBLICATION EDITION / PUBLICATION` | `ce4f6d5f…` |

原预览和 [RC1 记录](reviews/rc1/README.md)保持原样；新生成身份同时覆盖文件名、封面、控制页、页脚、元数据和来源说明，再绑定 manifest、release notes 与标签。只修改名字会留下读者可见的身份冲突。

正式阶段第一次构建虽已 `PREVIEW_READY`，代表页仍发现生成来源说明写着“阅读试件”，因此未被选作发布载荷。修正该提示后第二次构建才成为最终文件。两次都是构建成功，不应把首轮改记为 `FAILED`；它说明自动构建完成与发布适用性是两个判定。

身份修改发生在生成层，冻结正文、实验和视觉规则不变，但 PDF 字节与摘要必然改变。新字节重新检查后再冻结；候选接收和上传阶段只复制这些字节，不重新编译。这才避免了“审核 A、发布 B”。

### 9.2 分发采用分阶段核对，不冒充完整原子事务

本次实际流程是：

```text
核对最终载荷 → 提交载荷 → 创建签名 tag
    → 原子推送 main 与 tag
    → 创建 GitHub draft 并上传四个资产
    → 下载核对文件集合和字节
    → 公开 draft → 再次下载核对
    → 单独提交发布回执，不移动 tag
```

签名标签固定到载荷提交 `54f193f`；回执另在 `d1778dd` 追加，避免为补记录移动标签。下载后的平面文件名可直接配合 `SHA256SUMS` 使用。首次校验命令在错误工作目录找不到清单，记录保留退出 2；切到下载目录后通过，才继续公开。操作失误与载荷错误分别记录，不为日志整齐而抹去。

Git 引用的原子推送不等于 GitHub Release 全流程原子性。draft、上传、公开和回执是分开的操作；此次没有实现或证明跨系统事务、通用恢复／回滚或全部故障窗口。通用引擎 `publish` 仍关闭，实际分发使用了明确获授权的 GitHub CLI。

最终身份为：

```text
Publication  CPP-HANDBOOK / 1.0.0
Filename     Modern-Cpp-Engineering-Handbook-v1.0.0.pdf
Tag          cpp-handbook-v1.0.0
Pages        407
Bytes        2735594
SHA-256      ce4f6d5f6e4b8c1e2789eedd1fc151462d31e929b724ce2eb95c780f90766510
```

公开前后四个下载资产均与仓库载荷吻合，见[回执](releases/cpp-handbook/v1.0.0/publication-receipt.json)。这些是已认证 CLI 下载的结果，不冒充匿名访问实测。回执同时记录 `isImmutable=false`：不替换资产、不移动标签是项目级政策，不是 GitHub 服务端强制不可变保护。

### 9.3 可追溯、可校验与字节级可复现不能混同

目前具备精确源身份、工具与依赖记录、构建命令、制品摘要和下载回验，因此可以追踪来源并核对已发布字节。但工具和字体并未全部封装成可移植环境，也没有建立跨机器重建得到相同 PDF SHA-256 的证明。

准确的成果描述是：**来源可追溯、检查范围可解释、载荷可校验，并由签名标签绑定的发布。** 不是“已经实现完全可复现出版”。后续新机器、新工具链或新产品仍需相应验证；现有 macOS 路径不自动提供 Linux／CI、PDF/UA、打印或全阅读器认证。

## 10. 下次可以直接复用的工作顺序

这是一份裁剪用的经验清单，不是新增授权或待自动执行的工作包：

1. **确定读者与交付物。** 先决定是学习、回查、评审还是填写，明确独立版／合订版，不先争论模板。
2. **一次批准完整能力范围。** 明确可改层、受保护内容和停止条件；普通实现问题在批内解决。
3. **固定来源与变化边界。** 登记精确源提交、文件摘要、实验载荷及接受范围，保留历史证据。
4. **用真实产品检验抽象。** 沿用安全不变量，产品差异进入 profile；新增通用能力同步补反例。
5. **选择覆盖风险的 Pilot。** 长代码、危险标签、比较矩阵、空模板和交叉引用优先，不只选漂亮页。
6. **同时检查结构与实际阅读。** 按语义样本定位页图；把自动判据、人工判断和未测范围分开。
7. **冻结足够好的视觉规则。** 接受已知非阻塞限制；全书只处理覆盖面和 blocker，不无限微调。
8. **检查真正可用的导航。** 从正文引用一路查到目标与点击区域，不能只看目录和 destination 数量。
9. **生成最终身份后重验新字节。** 阅读器反馈绑定具体摘要，缺版本或项目就如实记录，不借用旧候选结果。
10. **只发布已检查的载荷。** 在授权范围内分发、下载回验、追加回执；后续变化进入新版本，不追写旧资产。

最值得保持的不是每一步都留下更多文件，而是每个重要结论都有对应对象、判据、证据和边界。达到当前目标后及时冻结；新的局部审美意见进入后续事项，新的内容或安全 blocker 则按其影响范围处理。

## 11. 本次复盘的落点

此次方法已由 ESD 阅读产品和 C++ 全书交付支撑，但仍有明确限制：既有技术证据的平台范围不变，最终阅读器反馈不完整，视觉检查不是全页人工认证，通用正式发布事务和跨机器字节级复现均未建立。

这些限制不抹去已完成的交付，也不应被“正式发布成功”遮住。后续最有价值的复用，是用同样清楚的身份、阅读任务和证据边界服务下一本书，而不是继续扩大这套流程本身。

**真正的交付，不是文件终于能打开，而是能说明它来自哪里、保留了什么、检查过什么、还有什么限制，以及以后如何安全改变。**
